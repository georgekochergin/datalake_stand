## Структура и ответственность

```text
test/
├── requirements.txt         зависимости хостовых проверок
├── pytest/                  тесты, запускаемые pytest без поднятия стека
│   └── test_*.py
└── e2e/                     всё, для чего нужен реальный стек, и его оснастка
    ├── shell/
    │   └── test.sh          сборка, два стека, проверки, очистка, замер
    ├── docker/
    │   ├── docker-compose.override.yaml
    │   └── Dockerfile       test-runner
    └── python/
        ├── run_flow.py          основной сценарий через Airflow и Trino
        ├── e2e_scale.py         подготовка изолированных рабочих деревьев
        ├── source_ddl.py        DDL для эволюции источников
        ├── check_meta.py        PostgreSQL-интеграция клиента pg-meta
        ├── check_extraction.py  инварианты реестра и публикации
        ├── check_spark_guard.py Spark-приложения и защита повторов
        ├── spark_guard_idle.py  приложение для guard
        ├── schema_evolution.py  схемы Iceberg
        └── temporal_extraction.py
```

`pytest.ini` задаёт сбор только `test/pytest/`. Существующие классы
`unittest.TestCase` поддерживаются pytest и не требуют переписывания.
PostgresTests вынесены в e2e и не собираются хостовым pytest.
Временные `test/.workspace-bank/`, `test/.workspace-broker/` и
`test/.results/` — не исходники, в git не попадают.

Тестируем оркестрацию и интеграцию **стенда**. Генерация распределений,
SQL-инъекции, валидация API и транзакционные гарантии sydafa принадлежат
отдельному проекту sydafa и здесь не проверяются. Успех DAG наполнения
подтверждает работоспособность интеграции. Данные загрузчика проверяются
в raw через Trino. Прямой доступ к источникам нужен только для контрольных
DDL эволюции, а не для повторного тестирования генератора sydafa.

## Порядок запуска и бюджет

Из корня репозитория, Python 3.11+:

```bash
python3 -m pip install -r test/requirements.txt
python3 -m pytest
./test/e2e/shell/test.sh --sources bank broker
```

Это два отдельных обязательных шага. Pytest не поднимает стек.
Некоторые статические тесты вызывают `docker compose config`, поэтому
нужен Compose CLI, но работающий Docker daemon для них не требуется.
Без CLI соответствующие проверки явно пропускаются.

Перед запуском e2e уточни у пользователя, какие источники из
`ingestion/conf/sources.yaml` тестировать: один или два.
Флаг `--sources bank broker` перечисляет имена через пробел.
Без флага выбираются все ключи файла. Если их больше двух, требуется
явный выбор. Неизвестные имена, дубликаты и выбор больше двух запрещены.
Один источник проходит тот же полный сценарий в одном стеке.
Два выбранных стека запускаются параллельно, образы собираются один раз.
Нужны минимум 10 GiB памяти Docker VM на стек.
Для двух стеков рекомендуется настройка 24 GiB. Недостаток памяти — отказ до старта.

Успех: код 0, все выбранные стеки без ошибок и соблюдён бюджет режима:

- Один источник — **E2E_TOTAL_SECONDS ≤420** (7 минут).
- Два источника — **E2E_TOTAL_SECONDS ≤600** (10 минут).
Замер включает подготовку, сборку из тёплого кэша, runtime и очистку.
Холодная сборка не является приёмочным замером: после неё повтори запуск.
При превышении бюджета выбранного режима требуется оптимизировать тест и повторить замер.
Не повышай лимит и не удаляй проверки без разрешения пользователя.
После оптимизации времени выполни минимум два последовательных полных
прогона каждого режима на тёплом кэше. Фиксируй все результаты, не только лучший.

```bash
# Только с уже актуальными образами
TEST_SKIP_BUILD=1 ./test/e2e/shell/test.sh

# Отладка существующего тестового стека с соответствующим рабочим деревом
./test/e2e/shell/test.sh --verify --sources bank
```

Обычный полный запуск всегда удаляет стек и рабочее дерево, поэтому
`--verify` после него сам по себе не создаёт отладочный контур.

## Состав pytest-проверок

- Генератор и манифесты: структура конфигурации, типы incremental-контракта,
  уникальность владельцев таблиц, имена DAG/Asset, состав задач, пулы и слоты.
- Чистая логика: диалекты/JDBC, позиции и окна, partitioning, преобразования
  схем и загрузчики. Spark/Airflow/DB-API заменяются контролируемыми двойниками.
- Метаданные: транзакции, CAS, идентичность и восстановление на двойниках.
  Реальные блокировки и ограничения PostgreSQL относятся к e2e.
- SQL в логах: переносы вложенного запроса, сохранность экранированных значений и
  выполнение исходного параметризованного запроса даже при ошибке рендеринга.
  Для Iceberg `CREATE TABLE` проверяются отдельные строки колонок и секций DDL.
- Формат лога Spark: передача SQL через фактический форматтер драйвера, явная политика
  отображения флагов трёх загрузчиков и совместимость JDBC URL всех зарегистрированных диалектов.
- Сводка фиксации pg-meta: на INFO только изменения при обновлении, полные записи на DEBUG.
- Конфигурация: инициализация Airflow и pg-meta, Connections, credentials,
  Compose-изоляция, правила Python и отсутствие runtime-правок sys.path.
- Оснастка e2e (`test_parallel_e2e.py`, `test_stand_config.py`): профиль
  10/10/100/100 и предел 100, фильтрация источников, неизменность production,
  отключение тестовых retries, перенесённая статика, оба Compose-конфига.
  Подставной Docker проверяет сборку один раз, ошибки, очистку, лимиты
  памяти/времени. Пост-проверки проверяются на параллельность, ожидание
  трёх фоновых ветвей и распространение ошибки любой ветви, включая реестр.
  Проверяются бюджеты: один источник 421 с — отказ, два источника
  421 с — успех, два источника 601 с — отказ.
  Ранний activate проверяется на перекрытие с ожиданием Airflow
  и передачу ошибочного HTTP-статуса в проверку результата.
  Выбор источников проверяется для произвольных ключей манифеста,
  одиночного запуска, двух источников, дубликатов и неверных аргументов.
  Граница памяти проверяется на 10 GiB и 20 GiB для одного и двух стеков.

## Состав e2e-проверок

Исполняемый источник точных SQL и ожиданий — `test/e2e/python/run_flow.py`
и подключённые из `test/e2e/shell/test.sh` скрипты. Состав покрытия:

| Проверка | Что подтверждается | Где выполняется |
|---|---|---|
| Готовность | API источника, ранний activate параллельно ожиданию Airflow, проверка ответа activate, наличие и тип Connections | оба стека |
| Наполнение | DAG обновления источника успешно завершён | оба стека |
| Первая загрузка main/refs | Таблицы непусты, один process_id и timestamp на порцию, общий ID задач DAG, разные ID запусков, правильный S3-префикс | оба стека |
| Дельта после миграции | Incremental получает непустую дельту, предыдущая история сохранена, полный срез deals добавляется отдельной порцией | оба стека |
| Снимок act_snap | Полнота по ID raw-истории, единая порция и время, путь хранения, история Iceberg и автор публикации, обнаружение ещё не опубликованной таблицы | оба стека |
| Повтор снимка | Атомарная замена вместо накопления, стабильное число строк | каждый стек |
| Drop/rename/add источника | Новые колонки заполнены, прежние в новых строках NULL, история сохранена | оба стека |
| Расширение типов | Promotion Iceberg, сохранность значений за прежними пределами и истории, два полных среза | оба стека |
| Несовместимый тип | Окончательный отказ load нужной таблицы, соседняя load успешна, причина в логе, нет новых строк и снапшота Iceberg | оба стека |
| Лог задачи `load` | Подтверждение записи START/END в pg-meta для начальных загрузок и снимка, FAILED при ожидаемом окончательном отказе | оба стека |
| Диагностика загрузки | Лог Airflow API для `transactions` и `deals`: этапы, многострочная команда без реквизитов, совпадение `--name` с именем приложения в Spark, свойства JDBC без повторного подробного блока, многострочный SQL с именем логгера и диапазоны, компактные результаты pg-meta. Подстановка параметров проверяется на стороне Airflow и Spark. Шумные JVM-категории не выводятся на INFO, сообщения JDBC о партициях и Iceberg о фиксации сохраняются. У `transactions` проверяется также регулярное окно, у `deals` — отсутствие инкрементальных операций | оба стека |
| Повтор команды из лога | Команда из Airflow task log выполняется через `sh` на воркере после подстановки реквизитов, скрытых Airflow. Уже завершённая загрузка `transactions` распознаётся без повторной записи | оба стека |
| Реестр (`check_extraction.py`) | Границы, ревизии, process_id, row_count.<br>Синтетические no-op/retry/CAS, запрет устаревшей финализации, публикация Asset только текущей порции.<br>START и END для начальных загрузок и снимка выбранного источника, FAILED при окончательном отказе | оба стека |
| PostgreSQL (`check_meta.py`) | Реальные блокировки и FK, атомарность, повтор, typed regression/underflow, ревизии и no-op | каждый стек |
| Guard (`check_spark_guard.py`) | Оставшееся зарегистрированное приложение после SIGKILL родителя, остановка до JDBC submit, чужая таблица не затронута, недоступный master запрещает submit для трёх операторов | каждый стек |
| Spark schema evolution | Реальный DDL Iceberg: add/drop/rename/смена типа | каждый стек |
| Temporal (`temporal_extraction.py`) | Типизированные позиции/точность, lookback и восстановление после append, восстановление снимка, выбор и реальный путь JDBC partitioning | свой источник каждого стека |
| Очистка | После Compose down нет контейнеров, source volumes и сети проекта | оба стека |

Temporal, schema evolution и PostgresTests запускаются в фоне на каждом
стеке до проверки реестра. Реестр и guard выполняются последовательно
на переднем плане. Все три фоновые ветви ожидаются, ошибка любой ветви
завершает стек с ошибкой. Реестр фильтрует состояние по выбранному source_id,
а temporal использует отдельные e2e source_id. PostgresTests создают отдельную БД.
Temporal/schema используют
максимум два ядра Spark. Их таблицы `raw.e2e_contract` не пересекаются
с таблицами guard `raw.<source_id>`. Guard использует выбранный источник
и префикс таблиц из его манифеста. Подмена недоступного master локальна
процессу guard. Любая ошибка делает стек неуспешным.

## Как расширять тестирование

1. Без реальных сервисов: добавляй `test/pytest/test_<область>.py`.
   Проверяй обычный путь, ошибки и границы. Допустимы pytest-функции
   и существующий стиль TestCase. Не запускай контейнеры из pytest-теста.
2. С Airflow/Spark/Trino/pg-meta или источником: добавляй сценарий в
   `test/e2e/python/run_flow.py` либо отдельный `test/e2e/python/check_<область>.py`.
   Spark-приложения и DDL-помощники добавляй в `test/e2e/python/`,
   shell-скрипты — в `test/e2e/shell/`, Docker-артефакты — в `test/e2e/docker/`.
3. Подключи отдельный скрипт в `test/e2e/shell/test.sh`, копирование в
   `e2e_scale.py` и нужное монтирование. Выполняй диалектные контракты
   и независимые проверки на каждом выбранном стеке. При параллелизме проверь
   отсутствие общих изменяемых таблиц и распространение всех ошибок.
4. Изменение пайплайна/источника/оркестрации требует e2e-покрытия,
   чистая логика дополнительно проверяется pytest. Не заменяй интеграционный
   контракт одним mock-тестом. Не добавляй тесты внутренних гарантий sydafa.
5. Обнови таблицу покрытия и правила в этом скилле для каждого нового теста.
   Выполни pytest, затем полный e2e, проверь очистку и бюджет времени.

## Изоляция и диагностика

- Имена, тома и сети только `dlh-test-bank`/`dlh-test-broker`.
  Публикация портов отключена, живой `dlh-poc` не очищается.
- `e2e_scale.py` копирует актуальный код/конфигурацию в отдельные деревья,
  фильтрует источник и профиль миграций. Production-файлы не переписываются.
  Только в копиях DAG устанавливается retries=0. Production retries=2
  с задержкой 5 минут проверяются pytest.
- DBA-реквизиты DDL читаются из `/state/secrets.json` своего контура.
  Их нельзя печатать, коммитить или передавать в аргументах команд.
- Логи: `TEST_FAILURE_LOG_DIR`, по умолчанию `test/.results/`.
  Метки `E2E_PHASE` показывают время от начала стека: подготовку дерева,
  завершение Compose up, начало и завершение runtime-проверок.
  Смотри статус каждой ветви и хвосты логов. Не называй успехом
  прохождение сценария при ошибке пост-проверок или превышении бюджета.
- DAG не зарегистрирован: смотри `airflow-dag-processor`, ошибки импорта
  и API v2. Airflow 3 использует `airflow.sdk.Asset`, а не Dataset.
- `/health` sydafa означает готовность API, а не лениво запускаемой СУБД.
  Пробуждение выполняют операторы activate/migrate.
- Trino внутри стека — HTTPS 8443, Nessie REST — 19120,
  warehouse `s3://datalake/raw/`. Проверяй конфигурацию текущего дерева.
- Авторизация Airflow: SimpleAuthManager, runtime-файл паролей,
  успешное завершение airflow-init. Учётные данные — README, раздел 2.6.
