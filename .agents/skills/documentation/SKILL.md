## Когда применять

- При создании, изменении или ревью README и документов в `docs/`.
- При изменении кода, если меняется описанное поведение, контракт или порядок эксплуатации.
- Для бэклога этот скилл задаёт только стиль, термины и навигацию.
  Разрешение на изменение задач, их структура и приоритеты определяются
  [скиллом backlog](../backlog/SKILL.md). Не добавляй задачи автоматически.
- Обсуждение формулировки не означает разрешения редактировать файлы.
  Отделяй предложение от согласованного решения.

## Ответственность документов

Один факт хранится в одном каноническом месте. В других документах —
краткий контекст и ссылка, а не копия подробного объяснения.

| Документ | Содержание | Границы |
|---|---|---|
| `README.md` | Первая точка знакомства: назначение стенда, компоненты и их взаимодействие, Docker-образы, версии приложений и языков, требования, запуск, подключения, проверки, статус и планы | Не описывать генерацию и структуру DAG-ов, алгоритмы чтения таблиц и внутренние контракты загрузчика. Ссылаться на архитектуру |
| `docs/architecture.md` | Устройство загрузчика и хранения: конфигурация, DAG-и, режимы загрузки, типы, метаданные, гарантии и ограничения | Не повторять инструкции эксплуатации из README. Обновлять вместе с архитектурным изменением кода |
| `docs/demo.md` | Последовательный сценарий демонстрации с параметрами подключения, командами, запросами и ожидаемыми результатами | Может дублировать сведения из README и архитектуры для самостоятельного прохождения. На определения терминов ссылается в общий глоссарий |
| `docs/glossary.md` | Единые определения специальных понятий проекта | Не превращать в учебник общепринятых технологий или описание внутренностей эмулятора источников |
| `docs/backlog.md` | Согласованные отложенные задачи | Изменять только по скиллу backlog |
| `docs/agents/` | Настройка инструментов агентов, в частности graphify и Spec Kit | Это не проектная документация. Локальные глоссарии и ссылки на проектный глоссарий не нужны |
| `AGENTS.md` | Маршруты к скиллам и мета-правила | Подробные правила документации хранить в этом скилле, не дублировать в AGENTS.md |
| `.specify/memory/constitution.md` | Принципы спек-цикла | Поправки — отдельным PR с обновлением версии и даты |

Не создавай новые документы без необходимости. Сначала выбери подходящий
существующий документ и раздел по его зоне ответственности.
Проработанный пункт планов из README переносится задачей в бэклог со ссылкой
на исходный список только с разрешения пользователя и по скиллу backlog.

## Язык и порядок изложения

- Пиши по-русски. Имена файлов, настройки, команды и идентификаторы сохраняй точно.
- Используй короткие предложения. Одно предложение — одна основная мысль.
- Вместо длинных абзацев и цепочек через точку с запятой используй списки.
  Нумерация нужна для порядка действий, буллеты — для независимых условий.
- Разделяй длинные темы на логичные разделы и подразделы.
  Сначала объясняй необходимые понятия и условия, затем действия и нюансы.
  Читатель не должен изучать следующий раздел, чтобы понять текущий.
- Показывай сложное правило небольшим примером вместо предложения со всеми оговорками.
- Избегай канцелярита, лишних англоязычных дублей и неоднозначных слов.
  Не добавляй `(batch)` к «партии загрузки» без необходимости сопоставить термин с API.
- Не используй разные слова для одного понятия без причины.
  Например, различай файл конфигурации и описанный им процесс:
  манифест — файл, пайплайн — процесс загрузки. Если отдельный термин
  «пайплайн» не нужен для объяснения, предпочитай «набор загрузок» или «DAG загрузки».
- В начале каждого документа размещай содержание с кликабельными ссылками.
  Обновляй его при изменении структуры. Для бэклога формат содержания задаёт backlog.

Пример упрощения:

> Вместо «один DagRun после полного Clear правомерно содержит партии нескольких исполнений»:
>
> «Запуск получил `process_id=42`. После Clear генератора он получил номер 43.
> В реестре сохраняются партии 42 и 43 с одним `run_id`».

В готовом документе специальные термины из такого примера должны быть ссылками
на определения по правилам следующего раздела.

## Термины и глоссарий

- Каноническое место определений — `docs/glossary.md`. Не создавай локальные словари.
- Определяй специальные понятия проекта и общие слова с особым проектным смыслом:
  например, партия загрузки, исполнение, канонический вид позиции.
- Не определяй общеизвестные термины ради полноты списка.
  DAG, задача Airflow, SCD2 и Data Vault не требуют записей и ссылок на глоссарий.
- Не вводи понятия внутренних механизмов источников как понятия datalake.
  Например, «партия наполнения источника» не нужна в глоссарии стенда.
  Значение `_batch_id`, если оно важно для конкретного примера, поясни рядом с примером.
- Для каждого термина из глоссария делай ссылку при **каждом** употреблении
  в поясняющем тексте README, архитектуры, демо и бэклога, включая списки и таблицы.
  Повторные ссылки не сокращай до одной на раздел или документ.
- Исключения: заголовки, блоки кода и Mermaid, копируемые команды,
  пути и идентификаторы в кодовом оформлении, сами определения.
  Не меняй примеры кода ради ссылок.
- Ссылка ведёт непосредственно к записи термина, а не к началу глоссария.
  Используй устойчивые уникальные якоря, например `<a id="term-batch"></a>`.
- Из README используй `[партия](docs/glossary.md#term-batch)`,
  из документов в `docs/` — `[партия](glossary.md#term-batch)`.
  При переносе документа пересчитывай относительные пути.
- Объединяй дубли определений. Разные понятия не объединяй только из-за похожего имени:
  полный срез с добавлением в raw, вспомогательная таблица `act_snap`
  и snapshot Iceberg — не одно и то же.
- При удалении определения удаляй или исправляй все ведущие к нему ссылки.

Определение должно объяснять назначение и связь с другими объектами, а не только механизм.
Например, для `act_snap` важно указать:

- Это **вспомогательная** таблица полного состояния для raw-таблицы
  с инкрементальной загрузкой, а не самостоятельный режим для любой таблицы.
- Её DAG создаётся вместе с конфигурацией инкрементальной загрузки.
  Для таблицы с загрузкой полными срезами `act_snap` не генерируется.
- Связь в конфигурации не означает зависимость порядка запусков:
  DAG снимка может работать до первой основной загрузки и имеет собственное расписание.
- Обновление снимка не меняет watermark основной таблицы.

Подробные алгоритмы и ограничения оставляй в архитектуре, не раздувай определение.

## Техническая точность

- Проверяй утверждения по коду, DDL и конфигурации, а не по прежней формулировке документа.
- Не выдавай заданные версии образов за минимальные поддерживаемые версии.
- Не подменяй упрощением смысл: сохраняй условия, гарантии и ограничения.
  Например, at-least-once не превращается в отсутствие дублей.
- Отделяй реализованное поведение от планов и задач бэклога.
- Иллюстративные номера, времена и результаты помечай как примеры.
  Не представляй их как результаты проведённой проверки.
- SQL должен использовать существующие поля текущего DDL.
  Пример последнего непустого среза не называй безусловным текущим состоянием источника.
- Не обещай равенство числа строк истории raw и текущего снимка.
- Для удаления томов и других необратимых действий явно указывай последствия.
  Не предлагай общий сброс данных как обычную подготовку демонстрации.

## Порядок работы и проверки

1. Установи границы запроса. Прочитай нужный документ и относящиеся к правке определения.
   Для изменения бэклога загрузи backlog. Анализ кода начинай с графа по AGENTS.md.
2. Выбери каноническое место факта. При переносе сохрани полезное содержание,
   удали ненужный дубль и обнови ссылки из других документов.
3. Внеси правки: сначала структура и определения, затем текст и ссылки на термины.
   Не переименовывай API, файлы кода и конфигурационные ключи ради терминологии документа.
4. Проверь результат:
   - содержание соответствует заголовкам;
   - локальные ссылки ведут к существующим файлам и якорям, якоря уникальны;
   - нет ссылок на удалённые определения и старые пути перемещённых документов;
   - повторные употребления специальных терминов связаны с нужным определением;
   - автоматическая замена не затронула код, команды и идентификаторы;
   - нет смысловых ошибок ссылок: JDBC driver — не управляющий процесс Spark;
   - блоки кода закрыты, `git diff --check` проходит.
5. Для чисто текстовых правок не запускай полный стек без необходимости.
   Проверки команд или тестов выполняй по e2e-testing и явно укажи, что не проверялось.
6. Перед коммитом классифицируй изменения по AGENTS.md.
   Новый или перемещённый документ требует локального `graphify update .`.
   Правка текста существующего Markdown-файла сама по себе перестроения не требует.
7. Сообщи результат и ограничения проверок. Не коммить, не отправляй изменения
   и не изменяй PR без соответствующего запроса пользователя.
