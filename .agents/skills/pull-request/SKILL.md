# Создание и оформление Pull Request

## Правила

- Создавай PR только по запросу пользователя, через GitHub CLI `gh`.
- Соблюдай инструкции репозитория. Для новых рабочих веток используй префикс `<github-login>/`, где `<github-login>` — логин активного аккаунта GitHub CLI, подтверждённый через `gh api user --jq .login` после проверки `gh auth status` (например, `georgekochergin/backlog-and-pr-skills`). Не используй фиксированный префикс `kodik/` и не подставляй локальное имя пользователя ОС или `git user.name`. Не коммить и не отправляй изменения в `main`.
- Не включай в коммит чужие или не относящиеся к запросу изменения. Не используй force push без явного разрешения пользователя.
- Никогда самостоятельно не мержи PR. Мерж выполняет исключительно пользователь.
- Обязательно заполняй description PR детальным структурированным описанием реальных изменений. Одного заголовка, списка коммитов или автоматически сгенерированного текста недостаточно.
- Не заявляй об успешных проверках, которые не запускались. Указывай ошибки, пропущенные проверки и непроверенные области явно. Не создавай PR в обход обязательных проверок репозитория.

## Проверка доступа

1. До создания PR выполни `gh auth status` и проверь наличие действующей аутентификации для `github.com`. Если `gh` не установлен, сообщи об этом; для macOS можно предложить `brew install gh`. Не устанавливай утилиты без разрешения.
2. Если аутентификации нет или она недействительна, попроси пользователя выполнить интерактивно:

   ```sh
   gh auth login -h github.com -p https -w
   ```

   Пользователь должен завершить вход в браузере. Не запрашивай токены и не записывай их в файлы или сообщения. После подтверждения пользователя повтори `gh auth status`.
3. Проверь целевой репозиторий и права через `gh repo view OWNER/REPO --json nameWithOwner,viewerPermission`. Не путай успешную аутентификацию с правом записи или проверенным Git push.
4. Если аккаунт выбран неверно, предложи `gh auth switch -h github.com -u USERNAME` для уже авторизованного аккаунта либо новый вход. При ошибках прав или корпоративного SSO попроси пользователя предоставить доступ/авторизовать SSO; не повторяй безуспешные запросы вслепую.
5. Перед HTTPS push при отсутствии настроенного Git credential helper предложи `gh auth setup-git`. При SSH remote отдельно проверь SSH-доступ либо согласуй переход на HTTPS: вход в `gh` по HTTPS сам по себе не настраивает SSH. Не меняй remote без разрешения.

## Подготовка и создание

1. Уточни целевой репозиторий и base branch, если они неоднозначны. Проверь текущую ветку, рабочее дерево и remote. Прочитай применимые инструкции репозитория.
2. Изучи фактический diff и коммиты относительно base branch. Составь описание по всему содержимому PR, а не только последнему коммиту. Проверь, нет ли уже PR для этой ветки через `gh pr list --head BRANCH --state open`; не создавай дубликат.
3. Выполни необходимые проверки по правилам репозитория. Подготовь разрешённые изменения в отдельной рабочей ветке, закоммить и отправь её в согласованный remote. Не используй `git add .`, если есть посторонние изменения. Перед push перестрой граф кодовой базы по критериям раздела «Перестроение графа кодовой базы».
4. Подготовь Markdown-файл с описанием вне отслеживаемых файлов репозитория. Используй шаблон ниже, заполнив его фактами из diff и результатов проверок. Если существует PR template репозитория, сохрани его обязательные разделы и дополни необходимыми деталями.
5. Создай PR с явными параметрами, подставив реальные значения:

   ```sh
   gh pr create --repo OWNER/REPO --base BASE --head BRANCH --title "Краткий заголовок" --body-file /absolute/path/to/pr-description.md
   ```

   Не полагайся только на `--fill`: итоговое описание должно соответствовать требованиям ниже.
6. Проверь результат через `gh pr view PR_URL --json url,title,body,baseRefName,headRefName`. Убедись, что описание сохранено полностью и ветки выбраны правильно. Сообщи пользователю URL и статус проверок. Не выполняй merge.

## Перестроение графа кодовой базы

Перед созданием PR — после последнего коммита ветки, до push — перестрой граф кодовой базы, если ветка меняла файлы, входящие в граф (код, тесты, конфигурации, SQL — не только документацию). Сначала оцени, нужен ли семантический слой (LLM):

**Достаточно локального обновления** — типовые правки кода (структура файлов, функции, вызовы, импорты, переименования): AST-слой графа отражает их без LLM, команда не требует токена и `OPENAI_BASE_URL`:

```sh
graphify update .
```

**Нужен `--backend openai`** — семантические рёбра важны: первичное построение графа (`graph.json` отсутствует), новые модули или контракты между компонентами, крупный рефакторинг с перемещением логики между слоями:

```sh
. ~/.config/graphify/env && graphify extract . --backend openai && graphify cluster-only
```

- LLM нужен, но `~/.config/graphify/env` не настроен (нет ключа или ссылки) — сообщи пользователю, что семантическое перестроение невозможно, и выполни локальное `graphify update .`; в описании PR укажи, что семантический слой не перестроен.
- После локального `update` имена сообществ пересчитываются по хабам без LLM; полную переразметку имён даёт только `cluster-only` с бэкендом.
- Обновлённый `graphify-out/graph.json` — финальный коммит ветки (`git add graphify-out/graph.json && git commit -m "chore: rebuild code graph"`); остальные артефакты `graphify-out/` в коммит не попадают (белый список в `.gitignore`).
- Посреди длительной работы: более 5 изменённых файлов кода с последней перестройки — перестрой граф без промежуточного коммита (`graph.json` войдёт в финальный коммит PR), по тем же правилам выбора команды.
- Ветки только с документацией (`.md`) перестроения не требуют.
- `extract` расходует LLM-API и инкрементателен (повторно обрабатываются только изменённые файлы); `update` локален и токенов не тратит. Если перестроение не выполнялось — явно укажи это в описании PR.

## Обязательная структура description

```markdown
## Контекст и проблема

Что не работало или чего не хватало, зачем нужны изменения и каковы границы задачи.

## Изменения по компонентам

- Компонент / путь: что конкретно изменено и как это влияет на поведение.

## Интеграции, окружение и конфигурация

Изменения зависимостей, API/контрактов, переменных окружения, конфигурации и порядка запуска. Если изменений нет, явно указать это.

## Проверки

- `команда` — фактический результат и существенные показатели.
- Незапущенные или недоступные проверки — причина и непроверенные области.

## Риски и ограничения

Совместимость, необходимые действия при развёртывании и известные ограничения. Если не выявлены, указать это без обещания отсутствия рисков.
```

Описание должно быть достаточно подробным для ревью без восстановления контекста из переписки. Не включай секреты, приватные логи и неподтверждённые утверждения.
