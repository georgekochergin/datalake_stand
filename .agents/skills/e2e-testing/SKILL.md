# Сквозное (e2e) тестирование стенда datalake_stand

## 1. Фундаментальный принцип тестирования кодовой базы

**Любой новый или изменённый функционал пайплайнов, источников и оркестрации
обязан сопровождаться соответствующими проверками в сценарии e2e-тестирования
(`test/run_flow.py` и `test/test.sh`).** Чистые функции дополнительно
покрываются юнит-тестами (`test/unit/`); проверяй обработку краевых случаев.

Тесты стенда тестируют **актуальное состояние репозитория**:

- Если в репозитории настроены источники и DAG-и их наполнения — e2e проверяет
  запуск и успешность исполнения этих DAG-ов.
- Когда добавляются новые слои или пайплайны поверх raw — соответствующие шаги
  расширяют `test/run_flow.py`.

### Разграничение ответственности (Separation of Concerns)

- **Зона ответственности `sydafa`**: синтетическая генерация данных, случайные
  распределения, инварианты, транзакционный коммит/откат (All-or-Nothing). Всё
  это покрыто собственной тестовой базой sydafa.
- **Зона ответственности `datalake_stand`**: оркестрация и интеграция
  платформы. Если вызов `POST /sources/{source}/migrate` завершается со
  статусом `200` и DAG переходит в `state = success`, значит СУБД запущена,
  схема создана, данные сгенерированы и транзакция закоммичена. Прямой
  SQL-доступ к СУБД источников из `test-runner` избыточен и не используется.
- Валидация данных через SQL начинается там, где начинается зона
  ответственности Data Lake, — на raw-слое Iceberg через Trino.

## 2. Архитектура и изоляция тестового контура (`dlh-test`)

Запуск тестов полностью изолирован от живого стенда (`dlh-poc`). Ключевые
механизмы (реализация — `test/test.sh` и `test/docker-compose.override.yaml`;
при изменении контура сверяйся с ними, а не с этим пересказом):

- **Имя проекта**: `COMPOSE_PROJECT_NAME=dlh-test` (скрипт допускает суффиксы
  `dlh-test-<suffix>`); отсюда изолированные имена контейнеров, томов и сети.
- **Изоляция портов**: override отключает публикацию внешних портов на хост —
  конфликты с живым стендом исключены.
- **Изоляция СУБД**: `SYDAFA_CONTAINER_PREFIX` вычисляется скриптом из имени
  проекта, контейнеры источников тестового контура не пересекаются с живыми.
- **`test/.workspace/`**: перед полным прогоном скрипт собирает изолированное
  рабочее дерево (актуальные `conf/`, `airflow/`, `ingestion/`, `trino/`),
  монтируемое override-файлом во все сервисы; по завершении (включая аварию и
  прерывание по trap) дерево удаляется. В git не попадает.

## 3. Режимы запуска тестов

```bash
# 1. Полный сквозной прогон e2e (по умолчанию): статическая валидация,
#    юнит-тесты, подъём изолированного стека dlh-test, e2e, гашение и очистка
./test/test.sh

# 2. Повторные runtime-проверки на уже поднятом ТЕСТОВОМ контуре dlh-test
#    (например, при отладке после полного прогона; требует существующий
#    test/.workspace — полный прогон должен уже быть выполнен)
./test/test.sh --verify

# Полный сценарий без пересборки образов (только после сборки текущих
# Dockerfile/конфигов)
TEST_SKIP_BUILD=1 ./test/test.sh
```

Хостовые prerequisites: Python 3.11+ и PyYAML (валидация манифестов и
юнит-тесты запускаются на хосте до Docker).

**Критерий успешности**: `FAIL=0`, exit-code `0`. Не допускается сдача задач и
мерж при непройденных проверках. Самостоятельный мерж агентом запрещён
правилами репозитория; его выполняет пользователь.

## 4. Сценарий сквозного тестирования

Контейнер `test-runner` исполняет `test/run_flow.py`; фактический состав шагов,
ожидания и контрольные SQL-запросы читай прямо в `test/run_flow.py` (это
исполняемый канон сценария — не дублируй его здесь). Фазы сценария:

1. статическая валидация манифестов источников (`conf/sydafa/sources.json`),
   миграций (`airflow/plugins/migrations/*.json`) и DAG-ов;
2. readiness/health sydafa и Airflow, проверка всех подключений;
3. защита sydafa от SQL-инъекций (ожидание HTTP 422);
4. запуск DAG-ов обновления источников и всех ingest-DAG-ов до
   `state = success` (при провале — печать состояний тасков и хвостов логов);
5. несколько раундов загрузки с проверками raw через Trino: append-only,
   один `__process_id` на запуск, удвоение снапшотов при повторе,
   инкрементальный гейт, дельта после миграций источника, ручной полный
   снимок через conf запуска;
6. в `airflow-scheduler`: инварианты реестра партий (`e2e_check_extraction.py`)
   и отдельные Spark-приложения эволюции схемы и temporal-инкремента;
7. гашение стека и очистка только принадлежащих контуру ресурсов (при неудаче
   логи Airflow выгружаются в `TEST_FAILURE_LOG_DIR`).

Учётные данные стенда — README, раздел 2.6; состав DAG-ов — раздел 2.3.

## 5. Справочник траблшутинга и дебага

### DAG-и не подхватываются в Airflow

- В Airflow 3.x парсингом занимается отдельный сервис: смотрите
  `docker compose logs airflow-dag-processor`.
- Отличия Airflow 3.x от 2.x: `from airflow.datasets import Dataset` удалён —
  используйте `from airflow.sdk import Asset`; `TrinoOperator` удалён —
  `PythonOperator` + `TrinoHook`; REST API — по префиксу `/api/v2/...`.
- Ручная проверка парсинга:
  `docker compose exec airflow-scheduler airflow dags list`.

### Ошибки sydafa: HTTP 422 или 409

- **422 Unprocessable Entity**: нарушение формата DDL/DML; имя колонки вне
  схемы таблицы (allow-list); недопустимый оператор сравнения; нарушение
  инварианта при строгом режиме (`validate_existing: true`).
- **409 Conflict**: каскадная блокировка при `delete`/`truncate` без
  `cascade: true`.
- При любой ошибке 422/409/500 транзакция в СУБД откатывается целиком
  (All-or-Nothing).

### Авторизация Airflow

- Образ использует SimpleAuthManager с пре-сгенерированным файлом паролей;
  действующие учётные данные — README, раздел 2.6.
- Убедитесь, что `airflow-init` завершился успешно
  (`condition: service_completed_successfully`).

### MSSQL / Oracle lazy start

- sydafa создаёт СУБД при **первом обращении** к источнику (`/activate` или
  `/migrate`); `/health` 200 означает готовность API sydafa, а не запущенную
  СУБД. `SydafaActivateOperator` / `SydafaMigrateOperator` будят её сами.

### Trino TLS и Nessie Iceberg REST

- Trino — HTTPS на 8443 (внутренний plain HTTP для Airflow включён через
  `allow-insecure-over-http=true`).
- Nessie REST Catalog — порт 19120 (`/iceberg/v1/config`); хранилище S3 (silo)
  с bucket `datalake`; конфигурация — `conf/trino/`, `conf/spark/`.
