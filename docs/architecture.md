# Архитектура datalake_stand

> Зона ответственности: устройство загрузки и хранения — слои данных, механика
> партиций и DAG-ов, типы и их гарантии, известные ограничения. Эксплуатация
> (запуск, порты, проверки) — в `README.md`; правила ведения документов —
> в `AGENTS.md`.

## 1. Слои данных

Стенд реализует классическую послойную схему КХД → DLH: каждый следующий слой
строится поверх предыдущего трансформациями, нижние слои при этом не меняются.

### raw — зеркало источника

raw — первый слой озера, точное зеркало таблиц источника «AS IS»: все колонки
источника на момент чтения плюс технические колонки загрузки. Никакой
бизнес-логики, преобразований и отбора колонок.

**Общий принцип — append-only:** загрузчик только дописывает строки в raw,
не обновляя и не удаляя ранее загруженные данные. Это не запрещает отдельные
административные операции обслуживания Iceberg.

Есть два метода загрузки:

1. **Полный снапшот** — каждая итерация читает всю таблицу источника и
   дописывает её полный срез с новыми техническими метаданными. Удалённой строки
   не будет в новом срезе, но её ранее загруженные версии останутся в raw.
2. **Инкремент** — изменения отслеживаются по выбранной колонке таблицы
   источника; загрузчик дописывает строки из очередного окна её значений.
   Изменения видны только тогда, когда значение этой колонки попадает в окно
   чтения; удаления таким методом не обнаруживаются (раздел 7).

### ods (планируется)

ODS — слой выше raw, в текущей версии стенда не реализован. Его задачи:

1. Дедупликация строк по ключам сущности.
2. Выделение актуального состояния и, при необходимости, ведение истории
   версий (например, SCD2 с признаком актуальности).

ODS должен строиться идемпотентным merge по ключу/версии источника,
а не агрегированием raw-строк. Это требование к будущей реализации.

### dds / dma (планируется)

DDS (например, Data Vault) и витрины (DMA) — слои обработки и выдачи,
строятся поверх ODS в будущих этапах.


## 2. Манифесты и генерация DAG-ов

DAG-и загрузки не пишутся руками и не строятся динамически при парсинге
Airflow: генератор `ingestion/generator/generate_dags.py` статически превращает YAML-манифесты
в готовые Python-файлы в `airflow/dags/generated/` (каталог в git не попадает).
В сгенерированном Python-файле явно перечислены все задачи, группы задач и
связи между ними. YAML читается **генератором**, но не Airflow при последующем
парсинге DAG-а. Обращений к Connections при парсинге тоже нет: учётные данные
получает оператор во время исполнения задачи.

`ingestion/conf/sources.yaml` ссылается на Connections через `airflow_conn_id`,
но не создаёт их. Настройка подключений и запуск стенда описаны в `README.md`.

Режим генератора `--check` строит ожидаемые Python-файлы в памяти и сравнивает
их с содержимым выходного каталога, **ничего не записывая**. Отсутствующий,
отличающийся или лишний `.py` означает код возврата 1; совпадение — 0.
Это проверка актуальности артефактов перед их передачей Airflow, а не проверка
доступности источников или исполнения DAG-а.

Генератор обходит `ingestion/conf/pipelines/` рекурсивно; один YAML-файл = один DAG.
Идентификатор DAG и имя файла: `ingest__<type>__<source_id>[__<имя_файла_без_расширения>]`
(постфикс опускается, если имя файла совпадает с `source_id`): так четыре
манифеста `{bank,broker}/{main,refs}.yaml` дают четыре DAG-а.

До передачи DAG-ов Airflow генератор выявляет:

- неизвестные ключи и неверные типы значений конфигурации;
- повторяющиеся FQN внутри манифеста;
- одинаковые DAG ID у разных манифестов;
- совпадения целевых таблиц, в том числе после приведения имён к нижнему регистру.

При межфайловой коллизии сообщение указывает оба файла. Обычная генерация
удаляет больше не нужные `ingest__*.py` только с собственной меткой
`Generated DAG for pipeline`. Если ожидаемое имя занято файлом без этой
метки, генерация завершается ошибкой, не перезаписывая его. Посторонние файлы
не удаляются; при этом `--check` считает лишним любой неожиданный `.py`.

**`ingestion/conf/sources.yaml`** — реестр источников (ключ — `source_id`):

| Параметр | Тип | Обязателен | Описание |
|---|---|---|---|
| `type` | `rdbms` | да | Категория источника; участвует в имени DAG. Сейчас поддерживается только `rdbms`; `kafka` зарезервирован на будущее и пока отвергается |
| `airflow_conn_id` | string | да | Ссылка на Airflow Connection с реквизитами источника; конкретная СУБД определяется по его `conn_type` во время исполнения |

**Разница между `type` источника и `conn_type` подключения Airflow:**

- `type` — категория источника, доступная генератору в CI/CD и входящая в DAG ID
  (`ingest__rdbms__bank__main`). Сейчас поддерживается только `rdbms`;
  `kafka` пока отклоняется валидатором. Способ чтения задаётся реализацией
  оператора, а не этим атрибутом: текущая реализация использует JDBC.
- `conn_type` — конкретная технология (`mssql` / `oracle`), определяемая
  в рантайме из Airflow Connection: оператор строит JDBC URL, а Spark
  по его префиксу выбирает драйвер и SQL-диалект.

Генератор не обращается к Airflow Connections: в DAG записываются `source_type`
и `airflow_conn_id`. В рантайме выполняются две независимые проверки:
оператор принимает только `source_type="rdbms"`, а построение JDBC URL
поддерживает только `conn_type` из списка `mssql`, `oracle`.

**Манифест пайплайна** (`pipelines/**/*.yaml`), ключи верхнего уровня:

| Параметр | Тип | Обязателен | По умолчанию | Описание |
|---|---|---|---|---|
| `source_id` | string | да | — | Должен существовать в `sources.yaml`; задаёт схему-неймспейс целевых таблиц |
| `schedule` | string \| null | нет | `null` (ручной запуск) | Расписание Airflow |
| `catchup` | bool | нет | `false` | Догоняющие запуски Airflow |
| `tags` | list[string] | нет | `[]` | Теги DAG-а |
| `entities` | list | да | — | Непустой список сущностей (см. ниже) |

**Ключи сущности:**

Регистр исходных имён сохраняется: для объектов `SCHEMA.TABLE` укажите
`fqn: "SCHEMA.TABLE"`. Это пример латинских идентификаторов: кириллица текущим
парсером FQN не поддерживается. Кавычки YAML не являются SQL-кавычками.
Загрузчик сам оформляет каждый фрагмент как `[SCHEMA].[TABLE]` в MSSQL или
`"SCHEMA"."TABLE"` в Oracle. Для Oracle нужно писать фактический регистр
объекта: некавыченные при создании имена обычно хранятся в верхнем регистре,
кавыченные — как были созданы. Только **целевое** имя приводится к нижнему
регистру: `raw.bank.schema__table`.

| Параметр | Тип | Обязателен | По умолчанию | Описание |
|---|---|---|---|---|
| `fqn` | string | да | — | `<схема>.<таблица>` источника, ровно два фрагмента; преобразуется в имя целевой таблицы по правилам именования (раздел 4) |
| `incremental` | mapping | нет | полный снапшот | Переключает сущность в инкрементальный режим: `source_column` — колонка инкремента (строчный идентификатор); `lookback.size` — неотрицательное число, `lookback.unit` — `h`/`d`. Для целочисленных колонок `unit` запрещён; для date допустим только `d`; для timestamp обязателен всегда, когда блок `lookback` указан (даже при `size: 0`) |
| `spark.parallelism` | bool | нет | `true` | `false` — читать источник одной JDBC-партицией без разведки ключей (раздел 6) |
| `airflow.pool.name` | string | нет | `default_pool` | Пул load-таска; пользовательский пул должен заранее существовать в Airflow |
| `airflow.pool.slots` | int | нет | `1` | Вес load-таска в пуле |

**`ingestion/conf/settings.yaml`** — общие технические настройки: сейчас один ключ
`spark.jdbc.num_partitions` (положительное целое, по умолчанию на стенде `4`) —
запрашиваемое число JDBC-партиций чтения, которое Spark может уменьшить
(раздел 6). Значение записывается непосредственно в
сгенерированный DAG.

Текущие манифесты стенда (демо-набор): в `main.yaml` каждого источника —
`transactions` (инкремент по `_batch_id`) и `deals` (снапшот); в `refs.yaml` —
`clients` и `accounts` (снапшоты, у всех демо-таблиц кроме transactions
JDBC-параллелизм отключён).

## 3. Структура сгенерированного DAG-а

**Операционные метаданные.** `pg-meta` — отдельная PostgreSQL-база фреймворка,
не metadata DB Airflow и не каталог Iceberg. В её схеме `ingestion` хранятся:

- журналы DAG-запусков и задач (`airflow_dagruns_log`, `airflow_tasks_log`);
- текущее состояние загрузки каждой сущности (`extraction_state`);
- реестр батчей — загрузок одной сущности в одном DAG-запуске
  (`extraction_batches`).

`process_id` идентифицирует DAG-запуск, `batch_id` — батч одной его сущности.
Для инкремента состояние содержит **watermark**: максимальное значение
выбранной колонки, которое уже было успешно загружено. Следующее окно
отсчитывается от него. Подробные схемы и переходы — в разделах 7–8.

```text
DAG ingest__rdbms__bank__main
│  schedule=None, catchup=False, max_active_runs=1, tags из YAML,
│  колбэки успеха/провала → события END/FAILED в pg-meta
│
├── generate_process_id   валидация conf запуска; выделение process_id (XCom)
└── activate_source       SydafaActivateOperator: поднять СУБД, TTL 15 минут
    └── TaskGroup "ingest_group"                       (сущности параллельно)
        ├── TaskGroup "load_retail_bank__transactions" (одна сущность)
        │   ├── log_start   событие START в pg-meta
        │   ├── load        IngestAppendOperator → ingestion/spark/raw/rdbms/load_entity.py
        │   ├── log_end     событие END в pg-meta
        │   └── publish_asset  публикация Asset после успешного log_end
        └── TaskGroup "load_retail_bank__deals" ...
```

Зависимости: `generate_process_id >> activate_source >> ingest_group`; внутри
группы сущности независимы, внутри сущности —
`log_start >> load >> log_end >> publish_asset`.
`max_active_runs=1` сериализует запуски одного DAG-а — «последний снапшот» и
watermark каждой сущности однозначен.

Таски:

- **`generate_process_id`** (`GenerateProcessIdOperator`) — прежде всего
  проверяет `dag_run.conf`: допустимы только `force_full_snapshot_fqns` и
  `reason`; список FQN должен состоять из сущностей этого DAG-а без повторов,
  а для непустого списка требуется непустая строка причины. Затем
  `meta.get_or_create_process_id()` создаёт START в `airflow_dagruns_log`,
  используя `nextval('ingestion.process_id_seq')`, либо возвращает ранее
  выделенный номер по `(dag_id, run_id)`. Retry задачи и очистка всего
  DagRun сохраняют номер, если это тот же `run_id` и запись в pg-meta сохранена.
  Новый DagRun получает новый номер. Результат передаётся через XCom.
- **`activate_source`** (`SydafaActivateOperator`, пакет `sydafa-airflow`) —
  будит СУБД источника через REST sydafa с TTL 15 минут, чтобы к моменту JDBC-чтения
  СУБД источника была запущена.
- **`log_start` / `log_end`** (`TableLogOperator`) — события жизненного цикла
  сущности в `airflow_tasks_log`, без публикации Asset и управления состоянием
  извлечения. Таблицы `ingestion.extraction_batches` и `ingestion.extraction_state`
  обслуживает Spark-функция `managed_load()` через `ingestion.meta`;
  `incremental_column` передаётся только задаче `load`.
- **`publish_asset`** (`EmptyOperator` с `outlets`) — отдельная задача публикации
  события обновления Asset `raw://<source_id>/<fqn>`, на который смогут
  подписываться DAG-и следующих слоёв. Выполняется только после успешного
  `log_end`: загрузка завершилась и её успех записан в pg-meta. Ошибка или
  пропуск `log_end` не допускает публикацию.
- **`load`** (`IngestAppendOperator`, наследник `SparkSubmitOperator`,
  client-mode, job `ingestion/spark/raw/rdbms/load_entity.py`) — исполнитель загрузки. Во время
  исполнения проверяет `source_type="rdbms"`, выбирает JDBC-диалект по
  `conn_type`, получает Connection источника и `process_id` из XCom.
  Параметры чтения и реквизиты источника, **включая пароль**, передаются
  аргументами `spark-submit`; реквизиты pg-meta — переменными `PGHOST`,
  `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD`. Пул применяется Airflow и
  Spark-job не передаётся. Текущий способ передачи пароля источника не даёт
  гарантии отсутствия секрета в командной строке процесса.

**Пул `ingest_loads`.** Все load-таски всех ingest-DAG-ов делят один пул на
4 слота (создаётся сервисом `airflow-init`); `transactions` занимает 2 слота,
остальные загрузки — по 1. Пул ограничивает количество одновременно работающих
Spark-приложений (каждое — отдельный driver + executors, что дорого для
Docker-машины), но не выделяет им CPU/память.

**Ручной полный снимок.** У сгенерированных DAG-ов нет объявленных параметров
запуска — обычный запуск не требует ввода: диалог открывается с сразу
активной кнопкой Trigger. Конфигурация передаётся там же, в диалоге запуска:
разверните «Расширенные параметры» (Advanced Options) → поле
**Configuration JSON** (предзаполнено `{}`) → вставьте конфигурацию запуска →
Trigger:

```json
{
  "force_full_snapshot_fqns": [
    "retail_bank.transactions"
  ],
  "reason": "Проверка полноты"
}
```

Выбранная таблица читается целиком (watermark сохраняется), остальные — по
манифесту. Валидация до активации источника: FQN только из этого DAG, без
дублей, `reason` обязателен и непуст.

## 4. Таблицы raw-слоя: структура и наполнение

**Именование.** Полное имя сущности источника кодируется: каждая точка → `__`.
`retail_bank.clients` → таблица `retail_bank__clients` в схеме `bank`
(источник) каталога `raw`: полное имя `raw.bank.retail_bank__clients` (каталог —
слой, схема — источник).

**Структура таблицы.** Колонки — точное зеркало схемы источника на момент
чтения — плюс три технические колонки:

| Колонка | Тип | Смысл |
|---|---|---|
| `__load_dttm` | `timestamp_ltz` | Момент загрузки (одно значение на порцию); аналитическое измерение времени; колонка партиционирования |
| `__process_id` | `bigint` | Номер DAG-запуска из pg-meta; один и тот же у всех таблиц одного запуска |
| `__batch_id` | `bigint` | Номер партии: одной загрузки одной таблицы (подробное объяснение — ниже) |

**Как связаны `__process_id` и `__batch_id`.** Запуск DAG-а получает один
`__process_id` на все свои таблицы. Внутри запуска каждая таблица читается
отдельной **партией**: ещё до обращения к источнику pg-meta заводит для неё
запись в `extraction_batches` с уникальным номером и замораживает границы
чтения. Все строки, дописанные в raw этой партией, получают этот номер в
`__batch_id`. Запуск с четырьмя таблицами оставит в данных один `__process_id`
и четыре разных `__batch_id`. Если load-таск упадёт и Airflow повторит его,
партия не создаётся заново: повтор читает то же замороженное окно, и все
дописанные им строки несут тот же `__batch_id` (повторная запись порции при
at-least-once — тот же номер, а не новый). Значение `__batch_id` — это прямой
ключ к метаданным партии: `SELECT * FROM ingestion.extraction_batches WHERE
batch_id = <значение>` показывает границы окна, режим, статус и результат
именно этой загрузки.

Партиционирование фиксировано фреймворком: `days(__load_dttm)` — дневные
партиции по границам UTC-дня. Первая загрузка создаёт таблицу DDL-ом по
фактически прочитанной схеме источника (колонки источника никогда не
перечисляются в YAML):

```sql
CREATE NAMESPACE IF NOT EXISTS raw.bank;

CREATE TABLE raw.bank.retail_bank__clients (
  `client_id` bigint, `full_name` string, ...,
  `__load_dttm` timestamp_ltz, `__process_id` bigint, `__batch_id` bigint
) USING iceberg
PARTITIONED BY (days(`__load_dttm`))
LOCATION 's3://datalake/raw/bank/retail_bank__clients'
TBLPROPERTIES ('write.spark.accept-any-schema'='true')
```

Namespace проверяется при каждой исполняемой загрузке, таблица создаётся
только при отсутствии. Location задаётся явно по шаблону
`s3://datalake/raw/<source_id>/<имя_таблицы>` (`ingestion/iceberg.py`).

**Режимы наполнения:**

- **Полный снапшот** (по умолчанию) — каждый запуск читает всю таблицу
  источника и дописывает её полное состояние новой порцией. Удаления на
  источнике отражаются (удалённые строки отсутствуют в новом снапшоте, но
  остаются в истории). Текущее состояние источника определяется по метаданным
  партий: последняя успешная (`SUCCEEDED`) партия сущности; если она дописала
  0 строк — источник опустел, хотя запрос по `MAX(__load_dttm)` продолжит
  возвращать последнюю непустую порцию.
- **Инкрементальный** (`incremental.source_column`) — каждый запуск читает окно
  новых строк по колонке инкремента. Первая загрузка без
  сохранённого watermark — первичное наполнение (без нижней границы,
  до максимума, зафиксированного при планировании). Подробно —
  раздел 7.

Каждая загрузка одной таблицы = одна партия: в данных её отмечает тройка
(`__process_id`, `__batch_id`, `__load_dttm`), в pg-meta — строка
`extraction_batches` с тем же `batch_id`.

**Типовые запросы (Trino):**

```sql
SHOW TABLES FROM raw.bank;

DESCRIBE raw.bank.retail_bank__clients;

SELECT count(*) FROM raw.bank.retail_bank__clients;

SELECT * FROM raw.bank.retail_bank__clients
WHERE __load_dttm = (SELECT max(__load_dttm) FROM raw.bank.retail_bank__clients);

SELECT __process_id, __batch_id, count(*) AS rows
FROM raw.bank.retail_bank__clients
GROUP BY 1, 2 ORDER BY 1;

SELECT count(*) FROM raw.bank.retail_bank__transactions WHERE __process_id = 42;
```

Запрос с `max(__load_dttm)` возвращает последнюю **непустую** порцию; про
пустой снапшот смотрите пояснение выше (раздел «Режимы наполнения»).

`__load_dttm` — `timestamp_ltz` (абсолютный момент); партиции следуют UTC-дням,
а «сегодня» — календарное понятие. Сравнивайте с зоной:

```sql
SET TIME ZONE 'Europe/Moscow';
SELECT * FROM raw.bank.retail_bank__clients
WHERE __load_dttm >= current_date
  AND __load_dttm < current_date + INTERVAL '1' DAY;
```

Литералы без зоны (`TIMESTAMP '2026-10-26 00:00:00'`) интерпретируются в зоне
сессии и молча сдвигают окно на часы — избегайте; пишите
`TIMESTAMP '...' AT TIME ZONE 'UTC'`.

**Гарантии и границы.** Данные озера и метаданные pg-meta фиксируются в разных
системах: сбой после коммита Iceberg, но до финализации watermark приведёт
к повторной записи той же порции при повторе запуска (at-least-once, не
exactly-once). Повтор диапазона допустим и не считается ошибкой — следующему
слою требуется идемпотентный merge по ключу/версии источника, а не `sum` по
raw-строкам. Пустой источник тоже создаёт raw-таблицу (проверка схемы без
строк).

## 5. Устойчивость к эволюции схемы источника

Список колонок и их типы не описываются в манифесте: загрузчик получает схему
через JDBC. Исключение — имя колонки инкремента: оно задано явно и вместе с
обнаруженным типом образует сохраняемый контракт (раздел 7.6).
Три настройки интеграции Iceberg со Spark обеспечивают автоматическую
обработку добавленных и отсутствующих колонок, но не произвольную смену типов:

**`write.spark.accept-any-schema=true`** — свойство таблицы, задаётся один раз
в DDL при создании и действует на всех будущих писателей. По умолчанию Iceberg
строго сверяет схему записываемого DataFrame со схемой таблицы: не хватает
колонки или лишняя — запись падает. Это свойство делает проверку сопоставлением
по имени и разрешает DataFrame'у **не иметь** части колонок таблицы: в
дописываемых строках они сохраняются как NULL. Новые колонки на этом уровне
всё ещё ошибка — их добавляет вторая настройка.

**`mergeSchema=true`** — опция Iceberg Spark writer, передаваемая через API
Spark `DataFrameWriterV2` при каждом append; это не универсальная гарантия
Spark для любого формата. Непосредственно
перед записью Iceberg сравнивает схему DataFrame со схемой таблицы и добавляет
каждую колонку DataFrame, которой таблице не хватает (эквивалент `ALTER TABLE
ADD COLUMN` внутри коммита записи). Существующие строки читают новую колонку
как NULL.

**`check-ordering=false`** — также опция Iceberg Spark writer,
отключающая сверку **позиций** колонок.
По умолчанию Iceberg проверяет, что порядок полей записываемого DataFrame
совпадает с порядком полей таблицы. Здесь сопоставление всегда по имени:
источник свободно меняет порядок колонок, а новые колонки после слияния схем
могут оказаться в схеме таблицы после технических колонок — и это корректно
(в Iceberg колонки идентифицируются field id и именем, а не позицией). Проверка
типов при этом сохраняется.

Совместно это даёт полный «белый список» реакции на изменения источника:

| Изменение на источнике | Эффект в raw-таблице |
|---|---|
| добавлена колонка | автоматически добавлена (`mergeSchema`); исторические строки — NULL, новые — со значениями |
| колонка удалена | колонка в таблице сохраняется; новые строки — NULL |
| колонка переименована | распознаётся как удалить+добавить: старая колонка сохраняется (новые строки NULL), новая добавляется (история NULL) |
| изменён тип колонки | фреймворк не выполняет отдельную миграцию типов; Iceberg может принять поддерживаемое безопасное расширение при merge схемы, несовместимое изменение приводит к ошибке; смена типа колонки инкремента отдельно блокируется контрактом pg-meta |
| изменён порядок колонок | никакого (сопоставление по имени, `check-ordering=false`) |

Нельзя обещать, что любое изменение схемы пройдёт без ошибки. Фреймворк
явно разрешает слияние схем при append, а допустимость изменения типов
определяет Iceberg. Удаления/переименования не удаляют старые колонки из raw;
несовместимые типы требуют отдельного решения и миграции.

Физически каждый append пишет только новые Parquet-файлы плюс один коммит
метаданных (новый снапшот таблицы): файлы предыдущих загрузок не меняются,
более поздняя загрузка не может испортить более раннюю историю.

## 6. Параллелизм Spark

Параллелизм загрузки реализован на трёх уровнях: чтение источника по JDBC,
одновременная загрузка сущностей и распределённая обработка в Spark.

**(1) Параллельное чтение источника (JDBC-партиции).** Чтение таблицы по JDBC —
один запрос на партицию: Spark может одновременно выполнять несколько SELECT к
СУБД, каждый читает свой диапазон строк. Фактическая одновременность зависит
от свободных слотов executors. Диапазоны задаёт четвёрка параметров чтения:
`partitionColumn` (колонка, по которой режем), `lowerBound`/`upperBound`
(минимум/максимум этой колонки) и `numPartitions` (на сколько диапазонов
разбить). При диапазоне id 1..1000 Spark формирует до четырёх непересекающихся
предикатов вида `id < граница`, `id >= граница AND id < следующая`,
`id >= последняя_граница`; первая партиция также принимает NULL.
`lowerBound`/`upperBound` задают шаг нарезки, **не фильтруют** всю выборку:
инкрементальное окно ограничено отдельным WHERE внутри подзапроса.

**Выбор колонки параллелизма — автоматический, это не настройка; колонка
всегда одна.** Порядок приоритета:

1. Для сущности с инкрементом используется его колонка, в том числе при
   первичном наполнении и ручном полном снимке. Поддерживаются целочисленная
   позиция и MSSQL `date`; для `timestamp_local`/`timestamp_instant`
   эта ветка сейчас отключена (см. ниже).
2. Для сущности без инкремента собираются колонки PK в порядке объявления
   в составном ключе (`KEY_SEQ` — порядковый номер колонки), затем колонки
   уникальных индексов в порядке ответа JDBC. Выбирается **первая** колонка
   подходящего типа, а не весь составной ключ. Из PK
   `(string_code, numeric_id)` будет выбрана `numeric_id`.
3. Нет подходящего кандидата или метаданные недоступны — один поток чтения.

Подходящий тип проверяется по JDBC-имени: whitelist в
`RdbmsDialect.partition_type_names` включает целые, `NUMBER`/`DECIMAL`/`NUMERIC`,
`DATE`, `DATETIME`, `DATETIME2`, `SMALLDATETIME`, `TIMESTAMP`.
Это проверка имени типа, не анализ уникальности или распределения значений;
приоритета «число перед датой» нет. Строки, GUID и float/double не входят
в список. **Произвольные колонки таблицы не перебираются.** Сумма транзакции
не станет кандидатом сама по себе; если она входит в PK/уникальный индекс
и имеет разрешённый тип, код может выбрать её. Для разбиения монотонность
и уникальность отдельной колонки не обязательны, но перекос распределения
может сделать параллелизм неэффективным.

Кандидаты берутся из стандартного JDBC API `DatabaseMetaData` (`getPrimaryKeys`,
`getIndexInfo`, `getColumns`) — он одинаково работает в MSSQL и Oracle, в отличие
от `INFORMATION_SCHEMA`, которого в Oracle нет. Разведка ключей — best-effort:
если метаданные недоступны или не дали кандидатов, загрузка не падает, а
читает одной партицией. Для выбранной колонки на
источнике выполняется `SELECT MIN(col), MAX(col)` **по окну чтения** (вся
таблица или инкрементный подзапрос), и нарезка на потоки включается **только
при строгом неравенстве MIN < MAX**:

- MIN и MAX равны NULL — нарезка не включается, выполняется чтение одним
  потоком. Это не обязательно пустое окно: выбранная колонка индекса может
  содержать только NULL;
- MIN = MAX — в окне ровно одно значение колонки нарезки, диапазон для
  разбиения отсутствует: чтение идёт **одной** JDBC-партицией при любом
  `num_partitions`;
- MIN < MAX — Spark получает запрошенное `numPartitions`
  (`spark.jdbc.num_partitions` из `settings.yaml`, на стенде 4).
  На узком целочисленном диапазоне Spark 3.5 уменьшает число партиций:
  MIN=11, MAX=12 даст **одну**, MIN=11, MAX=13 — две, а не четыре.
  Решает ширина диапазона, не число различных значений: два значения
  11 и 100 могут дать четыре партиции, часть из них пустые.

Практическое следствие для инкрементальных загрузок: если вся дельта запуска
состоит из строк с одним значением колонки инкремента (например, все строки
одной итерации генерации данных в sydafa несут одинаковый `_batch_id`), эта дельта
читается однопоточным SELECT — это ожидаемое поведение, а не сбой настройки.
Ненулевой диапазон возможен в следующих случаях (число партиций определяется
правилом выше):

- первичная загрузка после нескольких итераций наполнения источника;
- дельта за несколько обновлений источника без загрузки между ними;
- ручной полный снимок накопленных данных.

**Когда параллельное чтение отключается:**

- `spark.parallelism: false` у сущности — намеренно (так настроены все демо-таблицы
  кроме `transactions`): пропускаются разведка ключей и запрос MIN/MAX, чтение
  идёт в один поток;
- temporal-инкремент (колонка типа timestamp): чтение всегда одной JDBC-партиции —
  это явное условие в `_read_extract_frame()`, действующее и для первичного
  наполнения, и для ручного полного снимка такой сущности. Точный watermark
  передаётся отдельной строковой колонкой (раздел 7); из этого требования
  самого по себе не следует запрет параллельного чтения. Это ограничение
  реализации, а не фундаментальное ограничение timestamp или Iceberg.

**(2) Параллельные загрузки сущностей.** Таски `load` разных сущностей внутри
DAG-а и разных DAG-ов исполняются параллельно; их количество сдерживает пул
Airflow `ingest_loads` (4 слота; см. раздел 3). Это допуск к исполнению, а не
выделение ресурсов.

**(3) Внутренние потоки Spark.** Отключение JDBC-параллелизма (одна партиция
чтения) не запрещает распределённую обработку и запись, но само по себе
не создаёт несколько потоков обработки данных. Параллельная запись зависит
от дальнейшего плана и shuffle; явного `repartition()` после JDBC-чтения
в загрузчике нет.

Каждая загрузка — отдельное Spark-приложение: driver работает в контейнере
`airflow-scheduler` (client-mode), executors — на `spark-worker`. В образе
Airflow используется Python 3.11, в образе Spark-кластера — Python 3.10:
JDBC/DataFrame-загрузки не запускают Python-worker'ов, но для Python UDF/RDD
потребуется выравнивание minor-версий (задача изоляции drivers — в
`docs/backlog.md`, задача 1).

## 7. Инкрементальная загрузка

### 7.1. Контракт

Инкрементальная сущность задаётся выбранной колонкой источника
(`incremental.source_column`) и необязательным отступом `lookback`
(`size` + `unit`). **Watermark** — сохранённый максимум этой колонки среди
успешно загруженных строк; он хранится в `extraction_state.watermark`.
Например, watermark `120` означает: последняя успешная обработка дошла до
значения 120; без lookback следующий запуск ищет значения больше 120.
Это не доказательство, что все меньшие значения уже прочитаны: поздние
коммиты могут нарушить такое предположение.

Тип колонки определяется через JDBC. Значение сохраняется текстом, но
сравнивается и участвует в вычитании **как число, дата или время**, а не как
произвольная строка: число `100` больше `99`, хотя текстовое сравнение дало бы
обратное. Дробные секунды позиции сохраняются до точности источника:

| Семейство | Типы источника | Канонический вид позиции |
|---|---|---|
| целочисленные (знаковые) | `smallint`, `int`, `bigint`, `decimal(p,0)` | целое число: `-10`, `0`, `12345` |
| дата | `date` (MSSQL) | `2026-10-26` |
| дата-время без часового пояса (`timestamp_local`) | MSSQL `smalldatetime`/`datetime`/`datetime2(p)`, Oracle `DATE`, Oracle `TIMESTAMP(p)` | `2026-10-26T12:00:00.123456` |
| абсолютный момент (`timestamp_instant`, UTC) | MSSQL `datetimeoffset(p)`, Oracle `TIMESTAMP(p) WITH [LOCAL] TIME ZONE` | `2026-10-26T12:00:00.123456Z` |

Примеры различий:

- `timestamp_local`: `2026-10-26T12:00:00` — показание часов без информации
  о часовом поясе; нельзя однозначно перевести его в UTC. Загрузчик не
  приписывает ему пояс сервера или Spark.
- `timestamp_instant`: `2026-10-26T15:00:00+03:00` и
  `2026-10-26T12:00:00Z` — один момент; в pg-meta сохраняется второй вид.
- Oracle `DATE '2026-10-26'` может иметь также часы, минуты и секунды:
  позиция хранится как `timestamp_local(0)`, например `2026-10-26T12:34:56`.
- MSSQL `datetime2(7)` со значением `2026-10-26T12:00:00.1234567`
  сохраняет все семь цифр в watermark, хотя обычная timestamp-колонка
  DataFrame ограничена шестью. Для этого источник дополнительно возвращает
  позицию строкой (`CONVERT` + `DATEPART(nanosecond)`). В Oracle применяется
  `TO_CHAR` с маской вплоть до `FF9`.
- Oracle `TIMESTAMP WITH [LOCAL] TIME ZONE` проецируется через
  `SYS_EXTRACT_UTC` ещё в SELECT: Spark JDBC не отображает исходные JDBC-типы
  -101/-102. Это касается и обычных колонок raw, не только позиции.

Слово `timestamp` неоднозначно: **Oracle TIMESTAMP поддерживается**,
а **MSSQL `timestamp`/`rowversion` не поддерживается** как позиция. В SQL Server
это бинарный счётчик версий, не дата-время. Lookback в днях не делает его
поддерживаемым: нужны отдельные правила бинарной позиции и SQL-предикатов.

Правила lookback: для целочисленных колонок `unit` запрещён (отступ — просто
число); для date допустим только `d`; для timestamp `unit` (`h`/`d`) обязателен
всегда, когда блок `lookback` присутствует в YAML, даже при `size: 0`. Если
отступ приводит к выходу за минимум типа, нижняя граница не отбрасывается, а
снимается (читается всё от начала — безопаснее потерять производительность,
чем строки).

**Сейчас lookback по умолчанию равен 0, выравнивания по часу/дню нет.**
При watermark `2026-10-26T12:34:56` отступ `1h` даёт нижнюю границу
`2026-10-26T11:34:56`, а `3d` — `2026-10-23T12:34:56`.
Для `date` при watermark `2026-10-26` и `3d` граница — `2026-10-23`;
из-за строгого `>` сам день 23 октября не входит в окно.

Окно чтения регулярной загрузки строгое: `lower < col AND col <= upper`, где
`upper` — максимум колонки источника, зафиксированный **до** чтения, а
`lower` — сохранённый watermark минус lookback. Загрузка-первичное
наполнение (watermark ещё нет) читает строки до зафиксированного `upper`,
без нижней границы и lookback. Если источник меняется во время загрузки,
строки выше этого максимума относятся уже к следующему запуску.
Ручной полный снимок (`force_full_snapshot_fqns`) читает
всё без границ и **сохраняет** watermark нетронутым. NULL в колонке
инкремента блокирует обычную загрузку, включая первичное наполнение.
На этапе `_plan_batch()` функция `source_position()` выполняет по всей
таблице `SELECT MAX(col), COUNT(*), COUNT(col)` (с преобразованием MAX для
временных типов). Разные COUNT означают наличие NULL: до создания нового
батча и до записи raw выбрасывается `NULL incremental value in source`.
При повторе неуспешного батча тип и NULL проверяются снова; MAX не обновляется.
Ручной полный снимок допускает NULL.

Если текущий максимум стал меньше сохранённого watermark либо ранее непустой
источник опустел, обычная загрузка отклоняется: возможен сброс источника.
Ручной снимок не сбрасывает watermark и потому сам по себе проблему не решает.

**Зачем upper фиксируется заранее.** Он ограничивает батч и сохраняет те же
предикаты при Airflow retry/clear. Максимум фактически прочитанных строк
(`observed_max`) всё равно вычисляется после чтения — именно он, а не
запланированный upper, продвигает watermark. MIN/MAX для JDBC-нарезки —
другая операция, выполняемая над уже ограниченным окном.
Даже фиксированные границы **не фиксируют содержимое** источника: общей
snapshot-транзакции на все JDBC-запросы и повторы у загрузчика нет.

**Требования к выбору колонки:**

- Колонка должна иметь поддерживаемый тип и не содержать NULL.
- Для insert-only подходят растущий ID или номер итерации источника;
  обновления старых строк они не обнаруживают, если значение не меняется.
- Для insert/update нужна техническая метка изменения, обновляемая при
  каждом изменении строки; бизнес-дата сделки обычно этого не гарантирует.
- Разработчик должен знать задержки коммитов, возможность заднего числа,
  сброса значений и смены часового пояса. Lookback выбирается с учётом этих
  свойств, индекса на колонке и стоимости повторного чтения.

Lookback снижает риск пропуска поздних коммитов **только внутри своего окна**.
Даже `3d` не обнаруживает более поздний коммит со старой меткой, изменение
без обновления метки или физическое удаление. Поэтому задача 2 в
`docs/backlog.md` не закрывается одним встроенным lookback, в том числе
для временных колонок. Верхняя граница и высокая точность также не дают
гарантии полноты.

### 7.2. Жизненный цикл загрузки

Загрузкой управляет `managed_load()` в
`ingestion/spark/raw/rdbms/load_entity.py`. Она вызывает `ingestion/meta.py`
для коротких транзакций pg-meta и JDBC/Iceberg-функции для данных.
**Батч** — одна загрузка одной сущности в одном DAG-запуске, с номером
`batch_id` (в raw — `__batch_id`). **Попытка** — исполнение этого батча:
Airflow retry и clear того же DagRun не создают новый батч.

`revision` — счётчик изменений строки `extraction_state`, начиная с 1.
Батч сохраняет его как `expected_revision`. При успехе оба изменения —
watermark состояния и статус батча — фиксируются одной транзакцией pg-meta.
Iceberg-коммит в эту транзакцию не входит.

1. **План.** Driver spark-job читает состояние сущности и, если для этого
   DAG-запуска батч ещё не создан, определяет тип и максимум колонки
   инкремента, создаёт при необходимости `extraction_state` с ревизией 1
   и вставляет строку `extraction_batches` со статусом `PLANNED` и
   замороженными границами. Повтор того же DAG-запуска (retry таска, очистка)
   возвращает существующую партию с прежними границами — окно не «плывёт»
   между попытками.
2. **Пустое окно без чтения строк.** Если замороженные границы доказывают, что
   новых строк нет (регулярная партия с нулевым lookback, у которой нижняя
   граница равна верхней), партия сразу закрывается с `row_count=0` и
   `attempt_count=0` для нового батча. Это ветка внутри `managed_load()`:
   оператор не отменяется, `spark-submit` и SparkSession уже запущены,
   диагностические JDBC-запросы выполнены; не выполняется чтение DataFrame
   окна и запись Iceberg. Для первичного наполнения пустого источника эта
   оптимизация не действует: нужен пустой DataFrame для создания raw-таблицы.
3. **Исполнение.** Функция `meta.start_batch()` ставит `RUNNING`, увеличивает
   `extraction_batches.attempt_count` на 1, очищает `last_error` и
   `finished_at`. Затем загрузчик строит SELECT с сохранёнными границами,
   читает его через Spark JDBC и кэширует DataFrame. Агрегация считает строки
   и `MAX(__extract_position)`; временная позиция здесь представлена точной
   строкой. Служебная колонка удаляется перед append в raw.
4. **Финализация.** После Iceberg append функция `meta.finalize_batch()`
   обновляет `extraction_state`: watermark становится максимумом прежней
   позиции и фактически прочитанной (для ручного снимка остаётся прежним),
   `revision` увеличивается на 1, `last_batch_id` указывает на этот батч,
   `updated_at` получает текущее время. В той же транзакции батч получает
   `SUCCEEDED`, `row_count`, `observed_max`, `watermark_after`, `finished_at`.
   Проверка `WHERE revision = expected_revision` называется compare-and-set
   (CAS): записать результат можно лишь поверх версии состояния, с которой
   планировался батч. Чужая финализация или миграция меняет ревизию — старый
   батч отклоняется без частичного изменения pg-meta.
5. **Сбой.** Отдельной короткой транзакцией партия помечается `FAILED` с
   безопасным сообщением об ошибке; состояние (watermark) не меняется. Повтор начинается
   снова с шага 2/3 той же партии.

Каждая операция pg-meta берёт `SELECT ... FOR UPDATE` сначала на строку
`extraction_state`, затем на строку батча. Единый порядок уменьшает риск
взаимных блокировок; блокировки отпускаются при завершении короткой
транзакции и не удерживаются всё время JDBC-чтения.

Если батч уже `SUCCEEDED`, `managed_load()` возвращается **без повторного
чтения источника и append**. Если Iceberg-коммит состоялся, а финализация
pg-meta не состоялась, retry повторит append с тем же `batch_id` — возможны
дубли, причём `__load_dttm` новой попытки может отличаться. CAS защищает
метаданные, но не запрещает двум живым исполнителям одного батча одновременно
дописать данные. Перед retry прежний исполнитель должен быть остановлен.

Ошибки планирования происходят до `start_batch()` и вне блока обработки
ошибок исполнения: они не обязаны оставлять батч со статусом `FAILED`.
Новый батч при таком отказе может вообще не появиться.

### 7.3. `extraction_state` — состояние сущности

Одна строка на пару (источник, сущность); первичный ключ `(source_id,
entity_fqn)`.

| Колонка | Тип | Смысл |
|---|---|---|
| `source_id` | text, PK | Идентификатор источника (`bank`, `broker`) |
| `entity_fqn` | text, PK | Полное имя сущности (`retail_bank.transactions`) |
| `configured_mode` | text | Заданный манифестом режим: `incremental` или `full_snapshot` (у снапшотных сущностей строка создаётся при первой загрузке и хранит только факт контракта) |
| `incremental_column` | text | Имя колонки инкремента (NULL для снапшота); смена значения = смена контракта, требует миграции |
| `incremental_type` | text | Внутреннее, независимое от СУБД имя типа позиции: `bigint`, `decimal(18,0)`, `date`, `timestamp_local(6)`, `timestamp_instant(7)`; например Oracle `DATE` отображается в `timestamp_local(0)`, MSSQL `datetime2(7)` — в `timestamp_local(7)` |
| `watermark` | text | Каноническая позиция последней успешной загрузки (NULL до первичного наполнения); текст хранит позицию без потерь любой точности |
| `revision` | bigint | Версия строки состояния, начиная с 1; увеличивается при успешной финализации и ручной миграции; сравнивается с `expected_revision` батча (раздел 7.2) |
| `last_batch_id` | bigint | Ссылка на последнюю успешную партию (FK на `extraction_batches`, отложенная проверка) |
| `updated_at` | timestamptz | Момент последнего изменения строки |

CHECK-ограничение связывает режим и поля: у `incremental` колонка и тип
обязательны, у `full_snapshot` — колонка, тип и watermark обязаны быть NULL.

### 7.4. `extraction_batches` — батчи извлечения

Одна строка на сущность × DAG-запуск; уникальность `(dag_id, run_id,
source_id, entity_fqn)` — идентичность партии, стабильная между попытками.

| Колонка | Тип | Смысл |
|---|---|---|
| `batch_id` | bigserial, PK | Идентификатор партии; попадает в колонку `__batch_id` raw-строк |
| `process_id` | bigint | Идентификатор DAG-запуска (та же последовательность, что и `__process_id`) |
| `dag_id`, `run_id` | text | Принадлежность DAG-запуску |
| `source_id`, `entity_fqn` | text | Сущность; FK на `extraction_state` |
| `target_table` | text | Целевая raw-таблица |
| `mode` | text | Режим исполнения: `incremental` / `full_snapshot` |
| `reason` | text | Почему этот режим: `bootstrap` (первичное наполнение), `regular` (очередное окно), `manual_full` (ручной полный снимок) |
| `incremental_column`, `incremental_type` | text | Снимок контракта инкремента на момент партии |
| `expected_revision` | bigint | Ревизия состояния, которую партия вправе финализировать (для CAS) |
| `watermark_before` | text | Значение watermark до партии |
| `lookback_size`, `lookback_unit` | numeric / text | Применённый отступ |
| `lower_bound`, `upper_bound` | text | Замороженные границы окна чтения (NULL — границы нет: первичное наполнение, ручной снимок) |
| `empty_at_plan` | boolean | Вся таблица источника была пуста при предварительной проверке перед созданием батча (подробнее ниже); для пустого bootstrap фиксирует пустую выборку через `WHERE 1=0`; для обычного снапшота и manual_full всегда false |
| `status` | text | `PLANNED` → `RUNNING` → `SUCCEEDED` / `FAILED` |
| `attempt_count` | int | Число запусков исполнения (0 у партии, закрытой без чтения) |
| `row_count` | bigint | Дописано строк (заполняется при успехе) |
| `observed_max` | text | Точный максимум колонки инкремента в прочитанном окне |
| `watermark_after` | text | Значение watermark после партии |
| `reason_text` | text | Оператор передаёт причину только для `manual_full`; DDL требует её для этого режима, но не запрещает для остальных. Переименование поля потребует изменения схемы и клиентов |
| `last_error` | text | При ошибке исполнения загрузчик передаёт фиксированную строку `Extraction execution failed; see task logs`, а не текст исключения; сам `meta.fail_batch()` ничего не очищает и доверяет вызывающему коду |
| `created_at`, `finished_at` | timestamptz | `created_at` задаётся DEFAULT `clock_timestamp()` при INSERT батча; `finished_at` — при SUCCEEDED или FAILED; повторный `start_batch()` очищает его |

**Что фиксирует `empty_at_plan`.** До создания батча сущности с настроенным
инкрементом `source_position()` выполняет предварительный SELECT по всей
таблице источника: максимум выбранной колонки, общее число строк `COUNT(*)`
и число ненулевых значений `COUNT(col)`. Для временных типов максимум
дополнительно преобразуется в точную строку. Этот запрос получает границу
и проверяет пустоту/NULL; он не загружает строки таблицы в raw.

Если `COUNT(*)=0`, при первичном наполнении сохраняется
`empty_at_plan=true`. Одного `upper_bound=NULL` недостаточно: NULL также
означает отсутствие верхнего ограничения. Поэтому при чтении такого батча
добавляется `WHERE 1=0`: даже если после проверки в источнике появились
строки, этот батч остаётся пустым. Загрузчик получает схему пустого DataFrame
и создаёт raw-таблицу, если её ещё нет. Watermark остаётся NULL; следующий
новый DagRun снова выполняет первичное наполнение. Это признак пустоты
**источника при планировании**, не признак отсутствия новых строк после
watermark. При retry сохранённый флаг не пересчитывается.

**`observed_max` и `watermark_after`.** Первое поле описывает текущую
успешную выборку, второе — позицию сущности после её обработки:

- Для обычного инкремента и bootstrap `watermark_after` равен максимуму
  прежнего watermark и `observed_max`, с учётом типа позиции.
- При пустой выборке `observed_max=NULL`, но `watermark_after` сохраняет
  прежний watermark. Если watermark ещё не было, он остаётся NULL.
- Если из-за lookback прочитаны только значения ниже прежнего watermark,
  `observed_max` будет меньше него, но `watermark_after` назад не сдвинется.
- Для ручного полного снимка `observed_max` может быть заполнен, однако
  `watermark_after` всегда сохраняет прежнее значение.
- У сущности без инкрементальной колонки оба поля NULL.

Следующий **новый** батч отсчитывает нижнюю границу от
`extraction_state.watermark`, куда при финализации записан `watermark_after`,
с применением lookback. Retry не вычисляет окно заново, а использует
`lower_bound` и `upper_bound` уже созданного батча.

Основные CHECK-ограничения жизненного цикла (полный DDL —
`conf/pg-meta/init/01_ingestion.sql`):

- Инкремент: колонка задана, причина `regular`, прежний watermark известен.
- Bootstrap: режим полного снимка, колонка задана, прежнего watermark
  и нижней границы нет. Верхняя граница при этом может быть задана.
- Manual full: обе границы отсутствуют, причина непуста.
- Успех: число строк и время завершения заполнены, ошибка отсутствует.
- До успеха, включая `FAILED`: поля результата пусты.

```sql
CHECK (mode <> 'incremental' OR
  (incremental_column IS NOT NULL AND reason = 'regular'
   AND watermark_before IS NOT NULL));
CHECK (reason <> 'bootstrap' OR
  (mode = 'full_snapshot' AND incremental_column IS NOT NULL
   AND watermark_before IS NULL AND lower_bound IS NULL));
CHECK (reason <> 'manual_full' OR
  (mode = 'full_snapshot' AND lower_bound IS NULL AND upper_bound IS NULL
   AND reason_text IS NOT NULL AND length(btrim(reason_text)) > 0));
CHECK (status <> 'SUCCEEDED' OR
  (row_count IS NOT NULL AND finished_at IS NOT NULL AND last_error IS NULL));
CHECK (status = 'SUCCEEDED' OR
  (row_count IS NULL AND observed_max IS NULL AND watermark_after IS NULL));
```

Это выражения из определения таблицы, не самостоятельный SQL-скрипт миграции.

### 7.5. Пример одного инкремента и повтора

Условный пример: `bank`, `retail_bank.transactions`, колонка `_batch_id`
типа `bigint`, без lookback. В источнике уже загружены значения до 10,
затем добавились две строки со значением 11. Номера и времена ниже
иллюстративные, не результаты запуска стенда.

1. До запуска строка состояния содержит:

   | Поле | Значение |
   |---|---|
   | `source_id`, `entity_fqn` | `bank`, `retail_bank.transactions` |
   | `configured_mode` | `incremental` |
   | `incremental_column`, `incremental_type` | `_batch_id`, `bigint` |
   | `watermark`, `revision`, `last_batch_id` | `10`, `5`, `40` |
   | `updated_at` | время предыдущего успеха |

2. Новый DagRun получает `process_id=42`. В `airflow_dagruns_log` появляется
   START с новым `id`, этим `process_id`, `dag_id`, `run_id`, логической датой
   запуска и `ts`. `log_start` добавляет в `airflow_tasks_log` новый `id`,
   `process_id=42`, источник, FQN, целевую таблицу, `status=START`, `ts`.
3. Проверка источника возвращает MAX=11, COUNT(*)=COUNT(_batch_id): NULL нет.
   Планирование создаёт следующую строку батча; состояние пока не меняется:

   | Поля батча | Значения при INSERT |
   |---|---|
   | `batch_id`, `process_id` | `41`, `42` |
   | `dag_id`, `run_id` | `ingest__rdbms__bank__main`, идентификатор нового DagRun |
   | `source_id`, `entity_fqn` | `bank`, `retail_bank.transactions` |
   | `target_table` | `raw.bank.retail_bank__transactions` |
   | `mode`, `reason` | `incremental`, `regular` |
   | `incremental_column`, `incremental_type` | `_batch_id`, `bigint` |
   | `expected_revision`, `watermark_before` | `5`, `10` |
   | `lookback_size`, `lookback_unit` | `0`, NULL |
   | `lower_bound`, `upper_bound` | `10`, `11` |
   | `empty_at_plan` | false |
   | `status`, `attempt_count` | `PLANNED`, `0` |
   | `row_count`, `observed_max`, `watermark_after` | NULL, NULL, NULL |
   | `reason_text`, `last_error` | NULL, NULL |
   | `created_at`, `finished_at` | время INSERT, NULL |

4. Для строки `ingestion.extraction_batches` с `batch_id=41` функция
   `start_batch()` меняет `status` на `RUNNING`, увеличивает счётчик попыток
   `attempt_count` с 0 до 1, устанавливает `last_error=NULL` и
   `finished_at=NULL`. Строка `ingestion.extraction_state` не меняется.
   SELECT читает `10 < _batch_id AND
   _batch_id <= 11`. В raw дописываются две строки с `__process_id=42`,
   `__batch_id=41`, временем этого append в `__load_dttm`.
5. Успех меняет в состоянии `watermark=11`, `revision=6`, `last_batch_id=41`,
   `updated_at=время финализации`. В батче меняются `status=SUCCEEDED`,
   `row_count=2`, `observed_max=11`, `watermark_after=11`,
   `finished_at=время завершения`; `last_error=NULL`. Остальные поля неизменны.
   Далее `log_end` добавляет событие END сущности, публикуется Asset,
   при успехе всего DAG-а колбэк добавляет END запуска.
6. Альтернативный исход шага 5: Iceberg append уже закоммичен, но транзакция
   финализации pg-meta не закоммичена. Две строки в raw уже существуют,
   а метаданные ещё не подтверждают успех:

   - В `ingestion.extraction_state` по ключу
     `(bank, retail_bank.transactions)` остаются `watermark=10`,
     `revision=5`, `last_batch_id=40`, прежний `updated_at`.
   - Если обработчик ошибки смог обратиться к pg-meta, в
     `ingestion.extraction_batches` для `batch_id=41` он ставит
     `status=FAILED`, `last_error='Extraction execution failed; see task logs'`,
     `finished_at=время регистрации ошибки`. `attempt_count=1`;
     `row_count`, `observed_max`, `watermark_after` остаются NULL.
     При аварийном завершении driver обработчик может не выполниться,
     и в pg-meta останется `status=RUNNING`.
   - Повторное исполнение load-задачи того же DagRun находит батч 41 по
     прежним `dag_id`, `run_id`, `source_id`, `entity_fqn`. Новый батч
     и новый `process_id` не создаются. `start_batch()` увеличивает
     `attempt_count` до 2, ставит `RUNNING`, очищает `last_error` и
     `finished_at`. Границы остаются `lower_bound=10`, `upper_bound=11`.
   - Если источник не изменился, повтор снова дописывает две строки
     с `__process_id=42`, `__batch_id=41`, но временем новой записи
     в `__load_dttm`. В raw теперь четыре строки этого батча.
   - При успешной финализации метаданные получают значения шага 5,
     а `attempt_count` остаётся 2. Значение
     `extraction_batches.row_count=2` описывает успешную попытку,
     **не все четыре физически дописанные строки**. Это следствие
     отсутствия общей транзакции Iceberg и pg-meta.
7. **Очистка (Clear) задач уже успешного DagRun** — например, через UI
   Airflow для задачи `load` или всех задач запуска — сбрасывает состояния
   задач Airflow, чтобы их можно было исполнить снова. Она не удаляет
   данные Iceberg и записи pg-meta. Если сохраняются прежние `dag_id` и
   `run_id`, `process_id` остаётся 42, а загрузчик находит прежний батч 41
   со статусом `SUCCEEDED`. Он завершает load без чтения источника,
   повторного append, создания батча или изменения `extraction_state`.
   Это не относится к удалению DagRun и созданию нового запуска.
8. **Новый DagRun** — отдельный запуск по расписанию или через Trigger,
   с другим `run_id`, а не Clear существующего. Он получает новый
   `process_id`, например 43, и новый `batch_id`, например 42. Если после
   успеха шага 5 источник не менялся, прежний watermark равен 11,
   MAX источника также 11, lookback=0. Новый батч получает
   `watermark_before=11`, `expected_revision=6`,
   `lower_bound=11`, `upper_bound=11`. Окно `11 < col AND col <= 11`
   пусто, поэтому чтение окна и append не выполняются. При финализации:

   - В `ingestion.extraction_batches` для нового `batch_id=42`:
     `status=SUCCEEDED`, `attempt_count=0`, `row_count=0`,
     `observed_max=NULL`, `watermark_after=11`, `finished_at` заполнен.
   - В `ingestion.extraction_state`: `watermark=11`, `revision=7`,
     `last_batch_id=42`, `updated_at=время новой финализации`.

   Новый батч фиксирует отдельную успешную проверку отсутствия новых данных,
   даже если физических строк в Iceberg не добавилось. При Clear этого
   нового DagRun ещё один батч также не создаётся.

### 7.6. Смена контракта и ручные миграции

Контракт — тройка `configured_mode`, `incremental_column`, `incremental_type`.
Смена режима, колонки или её внутреннего типа блокируется проверкой pg-meta.
Удалённая колонка может привести к SQL-ошибке ещё до этой проверки.
Изменение только lookback миграции не требует; уже созданный батч сохраняет
старые границы.

Порядок ручной миграции:

- Приостановить DAG, чтобы не допускать новые плановые загрузки, и исключить
  ручные запуски на время миграции. Дождаться завершения либо остановить
  каждое Spark-приложение, загружающее эту сущность: текущую load-задачу,
  приложения прежних попыток, если они пережили сбой Airflow, и отдельно
  запущенные загрузки той же таблицы. Проверить, что их driver-процессы
  и выполняющие запись executor-задачи больше не работают. Пауза DAG-а
  или изменение статуса задачи в UI сами по себе этого не обеспечивают.
- Проверить фактическую схему источника и соответствие raw. Новая позиция
  должна поддерживаться диалектом; миграция pg-meta не исправляет
  несовместимую схему Iceberg и не добавляет поддержку нового JDBC-типа.
- В одной транзакции заблокировать состояние, проверить прежний контракт
  и ревизию, вставить аудит, изменить контракт, сбросить watermark и
  `last_batch_id`, увеличить revision. Историю raw и батчей не удалять.
- Изменить манифест и регенерировать DAG. Запустить **новый DagRun**:
  неуспешный батч старой ревизии повторно использовать нельзя.
- При инкрементальном новом контракте отсутствие watermark запускает
  bootstrap; при полном режиме — обычный снапшот. Проверить результат
  и аудит до возобновления расписания.

В коде **нет автоматического заполнения** `extraction_state_migrations`,
триггера или готовой команды миграции. Аудит вставляет администратор явно.
Ниже шаблон PostgreSQL для существующей строки состояния. Это пример,
не проверенная на работающем стенде процедура; старые значения и новую
тройку нужно заменить на проверенные значения своей сущности.

```sql
BEGIN;
DO $migration$
DECLARE
  old_state ingestion.extraction_state%ROWTYPE;
  next_mode text := 'incremental';
  next_column text := 'updated_at';
  next_type text := 'timestamp_local(7)';
BEGIN
  SELECT * INTO STRICT old_state
  FROM ingestion.extraction_state
  WHERE source_id = 'bank' AND entity_fqn = 'retail_bank.transactions'
  FOR UPDATE;

  IF old_state.revision <> 6
     OR old_state.configured_mode IS DISTINCT FROM 'incremental'
     OR old_state.incremental_column IS DISTINCT FROM '_batch_id'
     OR old_state.incremental_type IS DISTINCT FROM 'bigint' THEN
    RAISE EXCEPTION 'Unexpected old extraction contract or revision';
  END IF;

  INSERT INTO ingestion.extraction_state_migrations (
    source_id, entity_fqn, old_revision, new_revision,
    old_mode, new_mode, old_column, new_column, old_type, new_type,
    old_watermark, new_watermark, performed_by, reason_text
  ) VALUES (
    old_state.source_id, old_state.entity_fqn,
    old_state.revision, old_state.revision + 1,
    old_state.configured_mode, next_mode,
    old_state.incremental_column, next_column,
    old_state.incremental_type, next_type,
    old_state.watermark, NULL, current_user,
    'Переход на техническую метку изменения; повторное первичное наполнение'
  );

  UPDATE ingestion.extraction_state
  SET configured_mode = next_mode, incremental_column = next_column,
      incremental_type = next_type, watermark = NULL, last_batch_id = NULL,
      revision = old_state.revision + 1, updated_at = clock_timestamp()
  WHERE source_id = old_state.source_id AND entity_fqn = old_state.entity_fqn;
END
$migration$;
COMMIT;
```

Один шаблон покрывает следующие случаи; меняются объявленные переменные,
проверка старого контракта и осмысленная причина аудита:

| Случай | `next_mode` | `next_column` | `next_type` | Изменение YAML |
|---|---|---|---|---|
| Смена/переименование колонки | `'incremental'` | `'updated_at'` | `'timestamp_local(7)'` для MSSQL datetime2(7) | новое `source_column` |
| Смена типа той же колонки | `'incremental'` | `'_batch_id'` | `'decimal(20,0)'` для decimal(20,0) | имя прежнее; тип обнаруживается автоматически |
| Отключение инкремента, в том числе после удаления колонки | `'full_snapshot'` | NULL | NULL | удалить блок `incremental` |
| Включение инкремента после снапшотов | `'incremental'` | `'_batch_id'` | `'bigint'` | добавить блок `incremental`; старый контракт в проверке — full_snapshot/NULL/NULL |
| Явный сброс позиции после подтверждённого сброса источника | прежний режим | прежняя колонка | прежний тип | без изменений; watermark сбрасывается, следующий запуск — bootstrap |

Для включения после снапшотов проверка прежних полей в шаблоне должна быть:

```sql
IF old_state.revision <> 6
   OR old_state.configured_mode IS DISTINCT FROM 'full_snapshot'
   OR old_state.incremental_column IS NOT NULL
   OR old_state.incremental_type IS NOT NULL THEN
  RAISE EXCEPTION 'Unexpected old extraction contract or revision';
END IF;
```

Неподдерживаемый новый тип не исправляется заменой строки `incremental_type`:
нужно выбрать другую колонку, отключить инкремент или доработать диалект.
Удаление/переименование самой сущности и перенос её в другой `source_id` —
изменение идентичности, не миграция этой тройки.

## 8. База метаданных pg-meta: остальные объекты

`pg-meta` (база `meta`, схема `ingestion`) — выделенная операционная база
фреймворка: последовательность идентификаторов не может жить в озере (нет
атомарного инкремента на объектном хранилище), а операционные метаданные
должны переживать недоступность озера. Каталог Iceberg (pg-catalog) и база
Airflow — отдельные инстансы. DDL — `conf/pg-meta/init/01_ingestion.sql`.

**`ingestion.process_id_seq`** — последовательность идентификаторов процессов.
Каждый DAG-запуск любого ingest-DAG-а берёт `nextval` один раз
(`get_or_create`: строка START с частичным уникальным индексом по `(dag_id,
run_id) WHERE status='START'` — конкурентные повторы и очистка таска получают
тот же идентификатор, а не новый). Это значение становится `__process_id` всех
порций запуска.

**`ingestion.airflow_dagruns_log`** — журнал DAG-запусков (append-only):
`process_id`, `dag_id`, `run_id`, `execution_date`, `ts`, `status` (`START` —
из `generate_process_id`; `END`/`FAILED` — колбэки DAG-а). Текущий статус
запуска — последнее событие; длительность — разность `ts`.

**`ingestion.airflow_tasks_log`** — журнал тасков (append-only): `process_id`,
`source_id`, `entity_fqn`, `datalake_table`, `ts`, `status` (`START` / `END` —
`log_start`/`log_end`; `FAILED` — колбэк неудачи `load`).

**`ingestion.extraction_state_migrations`** — аудит ручных миграций контракта
инкремента: старая/новая ревизия (обязательно +1), режим, колонка, тип и
watermark до/после, `performed_by`, `reason_text`, `created_at`.

**Запросы для просмотра артефактов** (psql; подключение — README, раздел 2.5):

```sql
SELECT process_id, dag_id, run_id, status, ts
FROM ingestion.airflow_dagruns_log ORDER BY id DESC LIMIT 10;

SELECT process_id, entity_fqn, datalake_table, status, ts
FROM ingestion.airflow_tasks_log ORDER BY id DESC LIMIT 20;

SELECT entity_fqn, configured_mode, incremental_column, incremental_type,
       watermark, revision, last_batch_id, updated_at
FROM ingestion.extraction_state ORDER BY source_id, entity_fqn;

SELECT batch_id, process_id, entity_fqn, mode, reason, lower_bound, upper_bound,
       status, attempt_count, row_count, watermark_after, created_at, finished_at
FROM ingestion.extraction_batches ORDER BY batch_id DESC LIMIT 15;
```

## 9. Как расширять стенд

Стенд построен на трёх архитектурных осях: **JDBC-диалекты** (для новых RDB),
**типы источников** (для потоковых/альтернативных протоколов) и **слои данных**
(ODS, DDS, витрины). Каждая ось расширяется отдельно, без пересечений и заимствований.

### 9.1. Добавление JDBC-диалекта (ClickHouse, Greenplum, Teradata)

Диалект определяет, как конкретная RDB встраивается в JDBC-абстракцию: URL,
цитирование идентификаторов, типы позиций инкремента и SQL-выражения для
lossless-чтения временных меток.

**Шаг 1:** Создать наследник `RdbmsDialect` в новом файле
`ingestion/sources/rdbms/dialects/<dbms_name>.py`:

```python
from ..contracts import (
    RdbmsDialect, ConnectionSpec, normalize_type_name,
    integer_kind, decimal_kind, fractional_kind,
)

class ClickhouseDialect(RdbmsDialect):
    conn_type_aliases = ("clickhouse",)
    url_prefixes = ("jdbc:ch:",)
    default_port = 8123
    driver_class = "com.clickhouse.jdbc.ClickHouseDriver"

    def build_jdbc_url(self, spec: ConnectionSpec) -> str:
        return f"jdbc:ch://{spec.host}:{spec.port or self.default_port}/{spec.database}"

    def quote_identifier(self, name: str) -> str:
        return f'`{name.replace("`", "``")}`'

    def position_kind(self, type_name, precision, scale) -> str:
        name = normalize_type_name(type_name)
        if name in ("INT8", "INT16", "INT32", "INT64"):
            return integer_kind(name.replace("INT", ""))
        if name == "DATE":
            return "date"
        if name.startswith("DATETIME"):
            return f"timestamp_local({fractional_kind(3, 7)})"
        raise ValueError(f"Unsupported ClickHouse position type: {name}")

    def _typed_literal(self, text: str, family: str, precision: int) -> str:
        if family == "date":
            return f"parseDateISO8601('{text}')"
        return f"parseDateTime64BestEffort('{text}')"

    def position_expression(self, column: str, kind: str) -> str:
        return column
```

**Шаг 2:** Зарегистрировать диалект в кортеже `_DIALECTS` в
`ingestion/sources/rdbms/registry.py`:

```python
from .dialects.clickhouse import ClickhouseDialect

_DIALECTS: tuple[RdbmsDialect, ...] = (
    MssqlDialect(),
    OracleDialect(),
    ClickhouseDialect(),
)
```

**Шаг 3:** Добавить тесты в `test/unit/test_dialects.py`:

```python
class ClickhouseDialectTests(unittest.TestCase):
    def setUp(self):
        self.dialect = ClickhouseDialect()

    def test_conn_type(self):
        self.assertIn("clickhouse", self.dialect.conn_type_aliases)

    def test_position_kind_int(self):
        self.assertEqual(self.dialect.position_kind("INT64", None, None), "bigint")

    def test_quote_identifier(self):
        self.assertEqual(self.dialect.quote_identifier("col_name"), "`col_name`")
```

**Нарушение контракта запрещено:** диалект может переопределить
`position_expression` (для вывода позиции инкремента из СУБД без потери точности),
но не может добавлять новые колонки в DataFrame, менять JDBC-читатель или
взаимодействовать с Iceberg. Всё остальное — ответственность другой оси (см. ниже).

### 9.2. Добавление типа источника (Kafka, S3, Files)

Тип источника — это полностью новый канал доставки данных, отличный от JDBC.
Kafka не расширяет `RdbmsDialect`; это **отдельная подсистема** с собственными
контрактами чтения и гарантиями.

**Особенность:** файл `ingestion/generator/manifest.py` **явно отвергает**
`type: kafka`. Поддержка нового типа требует отдельного проектирования
контракта чтения и изменения валидатора.

Процесс (кратко):

1. **Определить контракт.** Kafka — streaming (лучше batch для фиксации watermark):
   что такое watermark? Партиция + offset? Timestamp? Как гарантировать
   «одни и те же строки при повторе»?

2. **Создать новую подсистему** `ingestion/sources/kafka/`:
   - `contracts.py` — контракт Kafka-подключения и чтения
   - `reader.py` — чтение партиций в DataFrame
   - тесты в `test/unit/test_kafka.py`

3. **Добавить оператор Airflow** (или расширить `IngestAppendOperator`):
   - новый путь `ingestion/spark/raw/kafka/load_entity.py` для Spark-job
   - валидация в генераторе DAG-ов

4. **Зарегистрировать тип** в `manifest.py`: `if source_type == "kafka":`
   вместо отвержения — вызвать специальную валидацию.

5. **Обновить README** про Kafka и раздел 11 «Известные ограничения» в этом документе.

**Почему отдельно от dialects:**

- Kafka не имеет SQL; watermark — это не `MAX(column)`, а смещение/временная метка
- Чтение streaming-протокола кардинально отличается от JDBC-запросов
- Batch vs. streaming — выбор, пока не реализован; документация не должна его фиксировать

### 9.3. Добавление слоя данных (ODS, DDS, витрины)

Ниже — направления будущего развития, **не реализованные интерфейсы**.
Формат конфигурации, размещение каталогов и способ создания DAG-ов следующих
слоёв ещё требуют проектирования; текущий генератор обслуживает только raw.

Слой — это трансформационный уровень озера, построенный поверх предыдущего.
Raw, ODS, DDS, DMA — это иерархия, не настройка. Каждый слой имеет свои
каталоги Iceberg, правила наполнения и операции Spark.

**Общая структура:**

```
ingestion/
├── iceberg.py        (текущее: build_create_table_sql и schema_columns)
├── spark/
│   ├── raw/
│   │   ├── rdbms/
│   │   │   └── load_entity.py
│   │   └── kafka/     (будущее, при добавлении Kafka)
│   │       └── load_entity.py
│   └── ods/           (новое, при добавлении ODS)
│       ├── __init__.py
│       └── load_entity.py (idempotent merge по ключу/версии)
trino/
├── ods/               (новое, при добавлении ODS: VIEW или SQL-логика)
    └── entities/      (по мере добавления таблиц)
```

**Слой Raw (текущее состояние):**
- Каталог: `raw` в Iceberg
- Режим: append-only (полный снапшот или инкремент)
- Гарантия: at-least-once; история прочитанных состояний, а не всех изменений источника
- DAG-ов: автоматически генерируются генератором из манифестов
- Spark-job: `ingestion/spark/raw/rdbms/load_entity.py` (и будущее `kafka/`)

**Слой ODS (планируется):**
- Каталог: `ods` в Iceberg (отдельный каталог, не raw)
- Режим: **идемпотентный merge** по (`source_id`, ключ сущности, версия)
- Гарантия: актуальное состояние каждой записи (дедупликация за счёт merge)
- DAG-ов: **не генерируются автоматически**
- Пример конфига (в `ingestion/conf/pipelines/ods/` — новая папка):

```yaml
bank.yaml:
  source_id: ods_bank_raw
  schedule: "0 3 * * *"
  entities:
    - raw_fqn: retail_bank.clients
      ods_table: ods.bank.retail_bank__clients
      key_columns:
        - client_id
      order_by_columns:
        - __load_dttm DESC
```

- Возможный Spark-job: `ingestion/spark/ods/load_entity.py`. Сначала нужно
  определить ключ и версию источника, затем реализовать дедупликацию оконной
  функцией и SQL `MERGE INTO` Iceberg. `DataFrameWriter.mode("merge")` не
  является способом выполнения такого merge. Одного времени загрузки
  недостаточно для определения порядка версий источника при повторах raw.

- Никакой автоматической генерации; DAG-ы пишутся вручную, как в продакшене.

**Слои DDS и DMA (дальнейшее развитие):**
- Следуют тому же паттерну: отдельные каталоги, собственные Spark-job'ы
- DAG-ы пишут бизнес-аналитики; никаких генераторов

**Почему правило 3 иерархично:**

- Raw — зеркало источника (фреймворк). Не трогать при добавлении ODS.
- ODS — дедупликация и построение состояния сущностей поверх raw.
- DDS и витрины — бизнес-логика. Живут вне фреймворка raw-инжесшена.

Добавляя ODS, **не переименовывать** raw и **не обобщать** `iceberg.py`. Каждый
слой — свой файл `load_entity.py` с собственной логикой идемпотентности.

### 9.4. Инварианты расширения

| Ось | Где код | Регистрация | Тесты | DAG-генерация |
|---|---|---|---|---|
| Диалект JDBC | `sources/rdbms/dialects/<name>.py` | Кортеж `_DIALECTS` в `registry.py` | В `test/unit/test_dialects.py` | Без изменений (вызывает `by_conn_type`) |
| Тип источника | `sources/<type>/*.py` | Валидация в `manifest.py` (убрать отвержение) | `test/unit/test_<type>.py` | Может потребовать фреймворка или DAG-шаблона |
| Слой данных | `spark/<layer>/load_entity.py` + `trino/<layer>/` | Новый DAG YAML или пусть Airflow | В `test/unit/test_load_<layer>.py` | Ручные DAG-ы (нет автогенератора для non-raw) |

**Проверка:**
- Новый диалект не влечёт изменений в `load_entity.py` и Kafka не появляется в `RdbmsDialect`
- Новый тип источника не трогает `rdbms/` и не создаёт пустые каталоги в git
- Новый слой не переписывает `iceberg.py` и не обобщает `raw/`

## 10. Типы данных и гарантии

Путь типа при загрузке: СУБД источника → JDBC → PySpark (Spark JDBC reader,
у обоих диалектов включён `preferTimestampNTZ=true`) → Iceberg DDL. Схема
raw-таблицы создаётся автоматически по фактически прочитанной схеме источника
и никогда не описывается вручную.

**Поддерживаемые типы колонок (PySpark → Iceberg DDL):**

| PySpark | Iceberg |
|---|---|
| `StringType` | `string` |
| `BooleanType` | `boolean` |
| `ByteType` / `ShortType` / `IntegerType` / `LongType` | `tinyint` / `smallint` / `int` / `bigint` |
| `FloatType` / `DoubleType` | `float` / `double` |
| `DateType` | `date` |
| `TimestampType` / `TimestampNTZType` | `timestamp_ltz` / `timestamp_ntz` |
| `DecimalType(p,s)` | `decimal(p,s)` |
| `BinaryType` | `binary` |

Тип вне этого списка — явная ошибка загрузки (честный отказ, не молчальное
преобразование). Маппинг типов СУБД → PySpark для обычных (не инкрементных)
колонок выполняет Spark JDBC по своей стандартной таблице соответствий;
фреймворк дополнительно гарантирует whitelist DDL выше, проекцию
Oracle timezone-типов и строгую типизацию позиции инкремента (раздел 7.1).

**Гарантии:**

- **Точность позиции инкремента не теряется**: суб-микросекундная точность
  читается из источника строкой (`TO_CHAR … FF9` в Oracle,
  `CONVERT` + `DATEPART(nanosecond)` в MSSQL) и хранится в watermark без
  округления до микросекунд Spark (раздел 7.1). Это гарантия именно для
  позиции инкремента: значения timestamp-колонок в самих raw-строках проходят
  через DataFrame Spark и ограничены его микросекундной точностью.
- **Зеркальность «AS IS»** означает отсутствие бизнес-трансформаций, но не
  побитовое сохранение представления: например, Oracle
  `TIMESTAMP WITH [LOCAL] TIME ZONE` не отображается Spark JDBC вовсе
  (типы -101/-102) и проецируется в UTC выражением `SYS_EXTRACT_UTC` ещё на
  стороне источника.
- **Типизация колонки инкремента** строго ограничена (таблица канонических
  видов — раздел 7.1): целые и `decimal(p,0)` при 1 ≤ p ≤ 38, `date`,
  дата-время без пояса и абсолютные моменты с точностью 0–9 (для MSSQL до 7);
  MSSQL `timestamp`/`rowversion` как позиция не поддерживается,
  Oracle `TIMESTAMP` поддерживается.
- **Смена типа колонки источника** ограничена совместимостью Iceberg при
  слиянии схем; несовместимое изменение прерывает загрузку. Тип колонки
  инкремента дополнительно защищён контрактом pg-meta (разделы 5 и 7.6).

## 11. Известные ограничения

| Ограничение | Где подробнее |
|---|---|
| Тихие пропуски инкремента: транзакция источника, зафиксированная после запроса максимума, может быть потеряна без следа — если её позиция не превышает новый watermark, а lookback её не покрывает; изменения и удаления старых строк вне окна инкремент не видит вовсе | раздел 7; `docs/backlog.md`, задача 2 |
| Поддерживаются только MSSQL и Oracle; `kafka` в манифестах отвергается | раздел 2; планы расширения — README, раздел 1.6 |
| Сущность без инкремента и подходящей колонки PK/уникального индекса читается одним потоком; произвольные колонки не перебираются | раздел 6 |
| Колонка параллелизма всегда одна и выбирается автоматически — это не настройка | раздел 6 |
| Temporal-инкремент (timestamp-позиция) всегда читается одной JDBC-партицией | раздел 6 |
| Дневные партиции `days(__load_dttm)`: несколько загрузок одного дня ложатся в одну партицию | раздел 4 |
| At-least-once: сбой между коммитом Iceberg и финализацией watermark приводит к дублю порции при повторе; следующему слою нужен идемпотентный merge | раздел 4 |
| MSSQL `timestamp`/`rowversion` не поддерживается как колонка инкремента; это не ограничение Oracle TIMESTAMP | раздел 7.1 |
