# Настройка GitHub Spec Kit — спецификации изменений

## 1. Назначение

**Spec Kit** — инструментарий спецификативной разработки: функциональная
доработка описывается артефактами (спецификация → план → задачи), и агент
работает по ним, а не по устному описанию «сделай вот так». Цикл:

```
constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge
```

Обязательные шаги — `specify`, `plan`, `tasks`, `implement`; `constitution`
задаёт принципы проекта один раз; `clarify`, `checklist`, `analyze` —
улучшители качества, применяются по необходимости; `converge` — завершающая
сверка кодовой базы с задачами.

Всё состояние цикла — файлы в репозитории: артефакты фич в
`specs/<NNN-имя>/`, принципы в `.specify/memory/constitution.md`. Поэтому
цикл доступен из обоих агентов команды — **opencode** и **zcode** — и
переключаться между ними можно в любой момент (раздел 4).

Правила применения в этом репозитории — раздел «Спецификации изменений
(GitHub Spec Kit)» в `AGENTS.md`: артефакты пишутся на русском, спек-цикл
не отменяет правил graphify, e2e-тестирования и Pull Request.

## 2. Установка для сопровождающего (выполнена один раз)

Утилита `specify` нужна только сопровождающему репозитория: инициализация,
добавление интеграций и расширений. Разработчикам в повседневной работе она
не требуется (раздел 3).

```bash
brew install uv
uv tool install specify-cli
```

После установки перезапустите оболочку (или выполните
`export PATH="$HOME/.local/bin:$PATH"`). Проверка: `specify --version`.

Инициализация в этом репозитории уже выполнена (specify 1.2.5): дефолтная
интеграция — **opencode**, рядом установлена интеграция **zcode**:

```bash
specify init --here --force --non-interactive --integration opencode
specify integration install zcode
```

Проверка состояния: `specify integration list` → установлены `opencode`
(default) и `zcode`. Дефолт влияет только на то, для какого агента
материализуются команды расширений (раздел 8).

## 3. Инструкция для разработчика

Артефакты обеих интеграций закоммичены в репозиторий, поэтому после
`git pull` настройка не нужна — достаточно установленного агента.

### opencode

1. Установите opencode ([opencode.ai](https://opencode.ai)).
2. Откройте репозиторий: команды подхватятся автоматически из
   `.opencode/commands/`.
3. Вызывайте команды с точкой, текст после команды — описание фичи:

   ```
   /speckit.specify Добавить выгрузку сырых данных в слой ODS
   ```

### zcode

1. Установите ZCode ([zcode.z.ai](https://zcode.z.ai)).
2. Откройте репозиторий и (пере)запустите сессию: скиллы подхватятся из
   `.zcode/skills/`.
3. Вызывайте скиллы через `$`:

   ```
   $speckit-specify Добавить выгрузку сырых данных в слой ODS
   ```

Системные требования для обоих агентов — bash и git (в macOS есть из коробки);
команды вызывают скрипты `.specify/scripts/bash/` сами. Python, uv и
`specify`-CLI на этом этапе не нужны.

## 4. Переключение между opencode и zcode

Оба агента читают и пишут одни и те же файлы. Текущая фича запоминается в
машинно-локальном указателе `.specify/feature.json` (в git не попадает).

| Сценарий | Что делать |
|---|---|
| Оба агента открыты в одном рабочем каталоге (обычный случай) | Ничего: продолжите следующим шагом цикла в другом агенте — артефакты и указатель фичи общие |
| Разные рабочие каталоги или машины | Синхронизируйте артефакты `specs/…` (коммит/push, во втором каталоге — pull) перед переключением |
| Параллельная работа над несколькими фичами | Указатель `.specify/feature.json` один на каталог: перед командой явно передайте `SPECIFY_FEATURE_DIRECTORY=specs/NNN-имя` |

`specify integration use` к переключению агентов отношения не имеет — это
инструмент сопровождающего для смены дефолта (раздел 8).

## 5. Состав артефактов

| Путь | В git | Назначение |
|---|---|---|
| `.specify/memory/constitution.md` | да | Конституция: принципы проекта, загружаются каждой командой цикла |
| `.specify/templates/` | да | Шаблоны спека, плана, задач, чек-листов, конституции |
| `.specify/scripts/bash/` | да | Скрипты подготовки: создание каталога фичи, проверка предусловий, разрешение шаблонов |
| `.specify/init-options.json`, `integration.json`, `integrations/*.manifest.json` | да | Конфигурация: нумерация фич (`sequential`), установленные интеграции, манифесты файлов |
| `.specify/feature.json` | нет | Машинно-локальный указатель текущей фичи |
| `specs/<NNN-имя>/` | да | Артефакты фич: `spec.md`, `plan.md`, `tasks.md`, `checklists/` |
| `.opencode/commands/speckit.*.md` | да | Команды цикла для opencode |
| `.zcode/skills/speckit-*/` | да | Скиллы цикла для zcode |
| `.zcode/plans/` | нет | Сессионные планы ZCode |

Три каталога агентов не дублируют друг друга — у каждого свой владелец:

| Каталог | Владелец | Кто читает |
|---|---|---|
| `.agents/skills/` | команда (рукописные скиллы: `e2e-testing`, `pull-request`, `backlog`) | opencode и zcode — оба нативно читают стандартный каталог Agent Skills |
| `.zcode/skills/speckit-*/` | `specify` (манифест `.specify/integrations/zcode.manifest.json`) | только zcode |
| `.opencode/commands/` | `specify` (манифест `.specify/integrations/opencode.manifest.json`) | только opencode |

Структура уже минимальна: рукописные скиллы лежат в единственном каталоге,
который читают оба агента, а файлы `specify` отслеживаются по манифестам
(`specify upgrade` / `uninstall`) и вручную их перемещать не следует.

Локальные исключения зафиксированы во вложенном `.specify/.gitignore`
(указатель фичи и другие машинно-локальные файлы) и в корневом `.gitignore`
(`.zcode/plans/`).

## 6. Команды цикла

Команды вызываются из корня репозитория; текст после имени — описание фичи
или уточнение. Каталог фичи `specs/NNN-<короткое-имя>/` создаёт команда
`specify` (нумерация сквозная, формат `001`, `002`, …).

| Шаг | Назначение | opencode | zcode |
|---|---|---|---|
| constitution | создать или обновить конституцию | `/speckit.constitution` | `$speckit-constitution` |
| specify | спецификация фичи → `specs/NNN-имя/spec.md` | `/speckit.specify` | `$speckit-specify` |
| clarify | уточнить неоднозначности спека вопросами (по необходимости) | `/speckit.clarify` | `$speckit-clarify` |
| plan | технический план реализации → `plan.md` | `/speckit.plan` | `$speckit-plan` |
| checklist | чек-листы качества по спеку и плану (по необходимости) | `/speckit.checklist` | `$speckit-checklist` |
| tasks | декомпозиция на задачи → `tasks.md` | `/speckit.tasks` | `$speckit-tasks` |
| analyze | сверка согласованности артефактов (по необходимости) | `/speckit.analyze` | `$speckit-analyze` |
| implement | реализация по задачам | `/speckit.implement` | `$speckit-implement` |
| converge | завершающая сверка кодовой базы и пополнение задач | `/speckit.converge` | `$speckit-converge` |

## 7. Пример цикла: что делаете вы, что делает модель

Распределение ролей здесь такое же, как с graphify: там модель сама запускает
команды поиска по графу, чтобы не итерироваться по файлам; в спек-цикле
модель выполняет всю механику — создаёт артефакты по шаблонам, запускает
скрипты предусловий, заполняет и валидирует документы, пишет код, запускает
тесты и отмечает задачи. Модель работает по файлам артефактов, а не по
памяти диалога, поэтому цикл переживает переключение агента и перезапуск
сессии. Ваша роль — три точки: описать фичу, ответить на вопросы (не более
трёх на шаг) и принять работу на контрольных стыках.

Пример: фича «Добавить выгрузку сырых данных в слой ODS».

| Шаг | Что делаете вы | Что делает модель |
|---|---|---|
| `specify` | Пишете `/speckit.specify Добавить выгрузку сырых данных в слой ODS` (одно–два предложения); при развилках выбираете ответ из предложенных вариантов (максимум 3 вопроса) | Придумывает короткое имя, создаёт `specs/001-ods-export/spec.md` по шаблону, формулирует требования и критерии успеха, сама прогоняет чек-лист качества, вписывает ваши ответы |
| `clarify` (по желанию) | Отвечаете на структурированные вопросы по неоднозначностям | Готовит вопросы, обновляет `spec.md` |
| `plan` | Запускаете и **ревьюите `plan.md`** — главная точка контроля до начала работы | Читает спек, конституцию и правила `AGENTS.md`, анализирует код через граф, пишет технический план с рисками |
| `checklist` (по желанию) | — | Генерирует чек-листы качества по спеку и плану |
| `tasks` | Запускаете | Декомпозирует план в `tasks.md`: чек-боксы задач, зависимости, критерии готовности |
| `analyze` (по желанию) | — | Сверяет согласованность `spec.md` / `plan.md` / `tasks.md`, отчёт о расхождениях |
| `implement` | Запускаете; отвечаете на вопросы по ходу | Выполняет задачи по одной: правит код по правилам репозитория (граф-first, e2e-проверки, Python без комментариев), отмечает выполненное в `tasks.md` |
| `converge` | Запускаете | Сверяет кодовую базу с задачами, дописывает пропущенное в `tasks.md` |
| Финал | Ревьюите diff и **мержите PR** | Оформляет PR по скиллу `pull-request`, включая финальный коммит графа |

Коротко: модель отвечает за «как оформлено и как реализовано», вы — за «что
и зачем» и за приёмку. Артефакты — обычный markdown: между шагами их можно
править вручную, модель подхватит изменения на следующем шаге. Если результат
не нравится — правьте артефакт (например, сузьте объём в `spec.md` или
поменяйте решение в `plan.md`), а не переформулируйте задачу с нуля.

## 8. Расширения

Ядро SDD покрывает цикл разработки. Дополнительные расширения ставит
сопровождающий по мере надобности:

```bash
specify extension add bug     # цикл исправления багов: assess → fix → test
specify extension add assess  # цикл оценки идей: intake → research → define → shape → decide
specify extension add git     # ветвление и коммиты по шагам цикла
```

Команды расширений материализуются только для дефолтной интеграции
(opencode). Если команды расширения нужны и в zcode, сопровождающий на время
выполняет `specify integration use zcode` (общие шаблоны пересоберутся под
стиль нового дефолта), а затем возвращает `specify integration use opencode`.

## 9. Взаимодействие с graphify и Pull Request

- Коммиты только с артефактами спек-цикла (markdown-файлы) перестроения графа
  не требуют — «ничего не делать» по таблице раздела «Граф кодовой базы» в
  `AGENTS.md`.
- Правки кода по задачам спек-цикла подчиняются общей таблице перестроения:
  типовые правки — локальный `graphify update .`, семантически значимые —
  `extract` с LLM (детали — `docs/graphify.md`).
- Финализация ветки — по скиллу `pull-request`: обновлённый
  `graphify-out/graph.json` коммитится финальным коммитом PR, описание PR —
  детальное структурированное, мерж выполняет только пользователь.
