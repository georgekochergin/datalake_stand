# Настройка GitHub Spec Kit — спецификации изменений

## 1. Назначение

**Spec Kit** — инструментарий разработки на основе спецификаций: функциональная
доработка описывается артефактами (спецификация → план → задачи), и агент
работает по ним, а не по устному описанию. Цикл:

```
constitution → specify → clarify → plan → checklist → tasks → analyze → implement → converge
```

Обязательные шаги — `specify`, `plan`, `tasks`, `implement`; `constitution`
задаёт принципы проекта один раз; `clarify`, `checklist`, `analyze` —
дополнительные проверки качества, применяются по необходимости; `converge` —
завершающая сверка кодовой базы с задачами.

Всё состояние цикла — файлы в репозитории: артефакты фич в
`specs/<NNN-имя>/`, принципы в `.specify/memory/constitution.md`.

Правила применения в этом репозитории — раздел «Спецификации изменений
(GitHub Spec Kit)» в `AGENTS.md`: артефакты пишутся на русском, спек-цикл
не отменляет правил graphify, e2e-тестирования и Pull Request.

## 2. Установка для сопровождающего (выполнена один раз)

Утилита `specify` нужна только сопровождающему репозитория: инициализация,
добавление интеграций и расширений. Разработчикам в повседневной работе она
не требуется (раздел 3).

```bash
brew install uv
uv tool install specify-cli
```

После установки перезапустите оболочку (или выполните
`export PATH="$HOME/.local/bin:$PATH"`). Проверка: `specify --version`.

Инициализация в этом репозитории уже выполнена (specify 1.2.5): установлена
интеграция **opencode** (дефолтная). Про интеграцию zcode и её удаление —
раздел 12.

```bash
specify init --here --force --non-interactive --integration opencode
```

Проверка состояния: `specify integration list` → установлен `opencode`
(default).

## 3. Инструкция для разработчика: opencode с токеном Z.ai

Команды цикла закоммичены в репозиторий (`.opencode/commands/`), поэтому
после `git pull` нужна только настройка самого opencode.

### Шаг 1. Установите opencode

Инструкция — [opencode.ai](https://opencode.ai).

### Шаг 2. Подключите провайдера Z.ai с вашим токеном

Токен личный, поэтому конфиг — глобальный, вне репозитория:
`~/.config/opencode/opencode.json`:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "model": "zai/glm-5.3",
  "providers": {
    "zai": {
      "name": "Z.AI",
      "env": ["ZAI_API_KEY"],
      "package": "@opencode/ai/providers/openai-compatible",
      "settings": {
        "baseURL": "https://api.z.ai/api/paas/v4",
        "apiKey": "{env:ZAI_API_KEY}"
      },
      "models": {
        "glm-5.3": { "name": "GLM-5.3", "modelID": "glm-5.3" }
      }
    }
  }
}
```

Токен задайте переменной окружения (не пишите его в конфиги репозитория):

```bash
echo 'export ZAI_API_KEY="ваш_токен"' >> ~/.zshrc && . ~/.zshrc
```

Адрес `https://api.z.ai/api/paas/v4` — OpenAI-совместимый эндпоинт Z.AI;
аналогичным образом подключается любой другой провайдер с
OpenAI-совместимым API (замените `baseURL`, имя модели и переменную
окружения).

### Шаг 3. Запустите цикл

Откройте репозиторий в opencode: команды подхватятся автоматически из
`.opencode/commands/`. Вызов — с точкой, текст после команды — описание фичи:

```
/speckit.specify Добавить выгрузку сырых данных в слой ODS
```

Системные требования — bash и git (в macOS есть из коробки); команды вызывают
скрипты `.specify/scripts/bash/` сами. Python, uv и `specify`-CLI на этом
этапе не нужны.

## 4. Состояние цикла: каталоги, машины, ветки

Текущая фича запоминается в машинно-локальном указателе
`.specify/feature.json` (в git не попадает).

| Сценарий | Что делать |
|---|---|
| Работа ведётся в одном рабочем каталоге (обычный случай) | Ничего: указатель и артефакты общие для всех сессий opencode в этом каталоге |
| Другая машина или второй клон | Синхронизируйте артефакты `specs/…` (коммит/push, во втором клоне — pull), затем задайте `SPECIFY_FEATURE_DIRECTORY=specs/NNN-имя`: указатель `.specify/feature.json` машинно-локальный и не переносится, а без него или без явной переменной команды продолжения (`plan`, `tasks`, `implement`) завершатся ошибкой |
| Смена git-ветки в том же каталоге | Указатель может ссылаться на фичу из другой ветки; перед продолжением задайте `SPECIFY_FEATURE_DIRECTORY` нужной фичи либо заново запустите её первый шаг (`specify`) — он перепишет указатель |
| Параллельная работа над несколькими фичами | Указатель один на каталог: перед командой явно передайте `SPECIFY_FEATURE_DIRECTORY=specs/NNN-имя` |

`specify integration use` к этому отношения не имеет — это инструмент
сопровождающего для смены дефолтной интеграции (раздел 9).

## 5. Состав артефактов

| Путь | В git | Назначение |
|---|---|---|
| `.specify/memory/constitution.md` | да | Конституция: принципы проекта, загружаются каждой командой цикла |
| `.specify/templates/` | да | Шаблоны спецификации, плана, задач, чек-листов, конституции |
| `.specify/scripts/bash/` | да | Скрипты подготовки: создание каталога фичи, проверка предусловий, разрешение шаблонов |
| `.specify/init-options.json`, `integration.json`, `integrations/*.manifest.json` | да | Конфигурация: нумерация фич (`sequential`), установленные интеграции, манифесты файлов |
| `.specify/feature.json` | нет | Машинно-локальный указатель текущей фичи |
| `specs/<NNN-имя>/` | да | Артефакты фич: `spec.md`, `plan.md`, `tasks.md`, `checklists/` |
| `.opencode/commands/speckit.*.md` | да | Команды цикла для opencode |

Локальные исключения зафиксированы во вложенном `.specify/.gitignore`
(указатель фичи и другие машинно-локальные файлы) и в корневом `.gitignore`
(`.zcode/plans/` — сессионные планы приложения ZCode, к спек-циклу отношения
не имеют).

## 6. Команды цикла

Команды вызываются из корня репозитория; текст после имени — описание фичи
или уточнение. Каталог фичи `specs/NNN-<короткое-имя>/` создаёт команда
`specify` (нумерация сквозная: `001`, `002`, …).

| Шаг | Назначение | Вызов в opencode |
|---|---|---|
| constitution | создать или обновить конституцию | `/speckit.constitution` |
| specify | спецификация фичи → `specs/NNN-имя/spec.md` | `/speckit.specify` |
| clarify | уточнить неоднозначности спецификации вопросами (по необходимости) | `/speckit.clarify` |
| plan | технический план реализации → `plan.md` | `/speckit.plan` |
| checklist | чек-листы качества по спецификации и плану (по необходимости) | `/speckit.checklist` |
| tasks | декомпозиция на задачи → `tasks.md` | `/speckit.tasks` |
| analyze | сверка согласованности артефактов (по необходимости) | `/speckit.analyze` |
| implement | реализация по задачам | `/speckit.implement` |
| converge | завершающая сверка кодовой базы и пополнение задач | `/speckit.converge` |

## 7. Практики прохождения цикла

### Конституция

- Формулируйте принципы проверяемо: правило работает, когда его можно
  проверить по diff («Python без комментариев», «e2e-проверка на каждый
  функционал»); общие формулировки без проверяемого критерия модель не
  применяет.
- Не перегружайте: конституция загружается на каждом шаге цикла, лишние
  пункты увеличивают расход токенов.
- Это изменяемый документ: столкнулись с проблемой, которую стоило закрепить
  правилом, — добавьте пункт отдельным PR с обновлением версии и даты.

### specify — спецификация

- Описывайте «что и зачем», а не «как»: технические решения относятся к
  `plan`; детали реализации в спецификации ограничивают выбор решений в плане.
- Критерии успеха измеримы: не «быстро и удобно», а «повторная загрузка не
  создаёт дубликаты», «DAG завершается не дольше N минут».
- MVP отделяйте от будущих версий прямо в спецификации.
- Спецификация — изменяемый документ: требования изменились — обновите
  `spec.md`; при существенных правках перезапустите `clarify` и `plan`.

### clarify — уточнение

- Не пропускайте: неочевидные границы видны именно отсюда — поведение при
  недоступном источнике, при повторном запуске, лимиты и таймауты.
- Не отвечайте «потом решим» — модель восполнит пробел произвольным
  допущением; лучше разобраться сразу.
- После ручных правок `spec.md` запустите clarify повторно.

### checklist — чек-листы

- Тему передают аргументом: `/speckit.checklist Security`; чек-листы
  создаются по темам отдельными файлами (`security.md`, `ux.md`, …). Для
  этого репозитория уместен Security.
- Чек-лист работает, только если по нему пройти и каждый провал закрыть
  правкой спецификации, а не отметить галочкой.

### plan — план

- Технологический выбор можно задать явно в аргументах команды — тогда план
  обосновывает заданное решение, а не предлагает своё.
- Проверяйте критически разделы про стек и архитектуру; по ключевым решениям
  запрашивайте альтернативы с плюсами и минусами.
- План создаёт вспомогательные документы по мере уместности: `research.md`,
  `data-model.md`, `contracts/`, `quickstart.md`.
- Изменили решение по ходу работы — сначала обновите `plan.md`, потом
  продолжайте: implement идёт по плану, а не по намерениям.

### tasks — задачи

- Задачи группируются по фазам; у каждой задачи — ID (`T001`, `T002`, …) и
  критерии приёмки; фазы связаны зависимостями и приоритетами (`P1`–`P3`,
  MVP-фаза помечена отдельно).
- Порядок фаз не перепрыгивайте, зависимости соблюдайте, реализацию начинайте
  с задач MVP-фазы.
- Одна задача — один коммит; выполненное отмечайте в `tasks.md`.

### analyze — сверка

- Запускайте перед implement и повторно после каждой правки артефактов — до
  состояния «критичных проблем нет».
- Непонятную проблему просите объяснить на примере и предложить варианты
  решения.

### implement — реализация

- Не запускайте всю реализацию сразу: контекст переполняется, качество
  снижается. Команда выполняет задачи фаза за фазой — ограничивайте сессию
  одной фазой.
- Одна фаза — одна сессия: тест → коммит → следующая фаза.
- Просите объяснять неочевидные решения в написанном коде.

### Когда цикл избыточен

Точечный фикс, правка документации или конфигурации полного цикла не
требуют — спек-цикл предназначен для функциональных доработок (правило в
`AGENTS.md`).

## 8. Пример цикла и распределение работы

Модель выполняет всю механику: создаёт артефакты по шаблонам, запускает
скрипты предусловий, заполняет и проверяет документы, пишет код, запускает
тесты и отмечает задачи. Модель работает по файлам артефактов, а не по
истории диалога, поэтому цикл переносится между сессиями и машинами (раздел
4). Контрольные точки пользователя: описать фичу, ответить на вопросы (не
более трёх на шаг) и принять работу на стыках шагов.

Пример: фича «Добавить выгрузку сырых данных в слой ODS».

| Шаг | Что делаете вы | Что делает модель |
|---|---|---|
| Спецификация и план | Запускаете `/speckit.specify Добавить выгрузку сырых данных в слой ODS`; отвечаете на вопросы (не более 3; при глубоких развилках — `/speckit.clarify`); запускаете `/speckit.plan`; **проверяете `plan.md`** — главная точка контроля до начала работы | Пишет `specs/001-ods-export/spec.md` (требования, критерии успеха, чек-лист качества выполняет сама), затем `plan.md`: технические решения по конституции и правилам `AGENTS.md`, анализ кода по графу |
| Проверка плана | Запускаете `/speckit.checklist`, просите проверить план и дополнить по находкам | Формирует чек-листы полноты по спецификации и плану, находит пробелы и дополняет `plan.md` |
| Задачи и реализация | Запускаете `/speckit.tasks`, затем `/speckit.implement` (фаза за фазой); отвечаете на вопросы по ходу | Декомпозирует план в `tasks.md` (чек-боксы, зависимости, критерии готовности); выполняет задачи по правилам репозитория (сначала анализ по графу, e2e-проверки, Python без комментариев), отмечает выполненное |
| Ревью и финализация | Проверяете diff; при желании `/speckit.analyze` (сверка `spec.md`/`plan.md`/`tasks.md`) или `/speckit.converge` (сверка кодовой базы с задачами); **мержите PR** | Вносит правки по итогам проверки; оформляет PR по скиллу `pull-request`, включая финальный коммит графа |

Кратко: модель отвечает за «как оформлено и как реализовано», вы — за «что
и зачем» и за приёмку. Артефакты — обычный markdown: между шагами их можно
править вручную, модель учтёт изменения на следующем шаге. Если результат не
устраивает — правьте артефакт (сузьте объём в `spec.md`, поменяйте решение в
`plan.md`), а не переформулируйте задачу с нуля.

## 9. Расширения

Ядро SDD покрывает цикл разработки. Дополнительные расширения ставит
сопровождающий по мере надобности:

```bash
specify extension add bug     # цикл исправления дефектов: assess → fix → test
specify extension add assess  # цикл оценки идей: intake → research → define → shape → decide
specify extension add git     # ветвление и коммиты по шагам цикла
```

Команды расширений материализуются для дефолтной интеграции — opencode.

## 10. Обновление Spec Kit

Проект развивается, релизы выходят регулярно. Обновление — задача
сопровождающего, оно двухчастное: сам CLI и артефакты проекта.

Новые релизы: [github.com/github/spec-kit/releases](https://github.com/github/spec-kit/releases)
или локальная проверка `specify self check` (read-only, покажет, есть ли
новая версия).

**1. Обновить CLI** (ставился через `uv tool`):

```bash
specify self check                      # есть ли обновление
specify self upgrade --dry-run          # предпросмотр без изменений
specify self upgrade                    # обновить; проверка: specify --version
```

**2. Обновить артефакты проекта** — общие шаблоны и скрипты `.specify/` и
файлы интеграции приводятся к версии нового CLI:

```bash
specify integration upgrade opencode
```

Команда сверяет хэши файлов со своими манифестами и остановится, если
отслеживаемый файл менялся локально (например, вы правили шаблон). Решите
конфликт: закоммитьте свои правки и продолжите с `--force` либо откатите их.
Пользовательское содержимое — конституция `.specify/memory/constitution.md`
и остальная память — обновлением не затрагивается.

**3. Провести изменение через git**: артефакты версонируются, весь результат
обновления виден в `git diff` — ревью и коммит в рабочую ветку, PR как
обычно. После мержа: `specify integration list` и контрольный запуск одного
шага цикла.

## 11. Взаимодействие с graphify и Pull Request

Правило перестроения графа для артефактов спек-цикла — по канонической
классификации раздела «Граф кодовой базы» в `AGENTS.md`:

- правка текста существующих артефактов (`spec.md`, `plan.md`, `tasks.md`) —
  перестроение не требуется;
- создание новых артефактов (каталог новой фичи, впервые созданные `plan.md`,
  `tasks.md`, `checklists/`) — структурное изменение документации: локальный
  `graphify update .` без токенов;
- правки кода по задачам — общая таблица: типовые правки — `graphify
  update .`, семантически значимые — `extract` с LLM (детали —
  `docs/graphify.md`).

Финализация ветки — по скиллу `pull-request`: обновлённый
`graphify-out/graph.json` коммитится финальным коммитом PR, описание PR —
детальное структурированное, мерж выполняет только пользователь.

## 12. Ограничение: интеграция zcode удалена

Интеграция zcode (скиллы `$speckit-*` в `.zcode/skills/`) устанавливалась
вместе с opencode, но удалена: headless-запуск CLI ZCode завершается ошибкой
`Select a model before sending a message` — без запущенного интерактивного
приложения CLI не имеет настроенной модели по умолчанию, и передать её
аргументом нельзя. Подтверждено было только обнаружение скиллов (`skills
list` видел все десять без ошибок диагностики); выполнение команд цикла в
ZCode не проверено ни в headless, ни в интерактивном режиме, поэтому рабочим
инструментом спек-цикла зафиксирован opencode.

При необходимости вернуть (команда безопасна для артефактов `specs/` и
`.specify/`):

```bash
specify integration install zcode
```

Локальный каталог `.zcode/plans/` (сессионные планы приложения ZCode)
остаётся исключённым из git независимо от интеграции.
