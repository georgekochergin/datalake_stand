## Приоритет: важно

### Подключить Kafka как источник данных для datalake через sydafa

#### Задача Jira

[DATARCH-2254](https://jira.bcs.ru/browse/DATARCH-2254)

#### Контекст

Нужно расширить набор источников datalake данными из Kafka.
Согласованный предпочтительный путь — интеграция через sydafa.
По сообщению пользователя, Kafka сейчас не поддерживается в sydafa.
Поэтому задача включает изменения в репозитории sydafa, а не только
настройку подключения в datalake_stand.

#### Проблема

Требуется воспроизводимый сценарий поступления сообщений из Kafka в озеро
и проверки загруженных данных. Нужно определить контракт подключения,
формат сообщений и правила продолжения чтения после сбоя.

#### Предпочтительный путь решения

В первую очередь добавить поддержку Kafka как источника в репозитории
sydafa, затем подключить этот источник к datalake_stand через интеграцию
с sydafa. При проектировании:

- Спроектировать и реализовать в sydafa управление Kafka-источником
  и подготовку тестовых сообщений. Изменения в репозитории sydafa —
  обязательная часть предпочтительного решения.
- Определить настройки подключения, топики, формат сообщений и отображение
  данных в целевые таблицы [raw](glossary.md#term-raw).
- Согласовать хранение смещений по партициям, начальную точку чтения
  и восстановление после сбоя. Явно описать гарантии доставки и обработку
  повторных сообщений, не обещая отсутствие дублей без проверки.
- В изолированном [e2e](glossary.md#term-e2e)-контуре проверить подготовку
  сообщений через sydafa, загрузку в озеро, поступление новых сообщений
  и продолжение чтения после перезапуска.
- При реализации обновить документацию подключения и демонстрационный
  сценарий. Реализацию выполнять отдельно по спек-циклу.

### Создать демонстрационную витрину остатков из raw и рукописный DAG обновления

#### Задача Jira

- [DATARCH-2255](https://jira.bcs.ru/browse/DATARCH-2255) — Trino SQL витрины.
- [DATARCH-2256](https://jira.bcs.ru/browse/DATARCH-2256) — рукописный DAG обновления.

#### Контекст

Для демонстрации нужна витрина расчётных остатков, построенная непосредственно
из [raw](glossary.md#term-raw)-таблиц. Пример расчёта — сумма транзакций
в разрезе счёта, клиента и валюты. Новый слой хранения в этой задаче
не проектируется.

Опорные файлы и соглашения:

- SQL-скрипты размещаются в корневом каталоге `trino/`.
- Рукописный Python DAG размещается в `airflow/dags/`, вне `generated/`,
  по аналогии с `airflow/dags/update_source_bank.py`. Генерация из YAML не нужна.
- В `conf/sydafa/sources.json` транзакции `bank` содержат `transaction_id`,
  `account_id`, `client_id`, `currency` и `amount`.
- Для выполнения SQL из Python-задач использовать `TrinoHook` провайдера Trino.
  [Предложенная документация API](https://airflow.apache.org/docs/apache-airflow-providers-trino/1.0.0/_api/airflow/providers/trino/hooks/trino/index.html)
  относится к версии `1.0.0`. При реализации сверить API с фактически
  установленной версией, не понижать провайдер ради примера.

#### Проблема

В демонстрации нужен отдельный пример преобразования загруженных данных
в бизнес-агрегат и его обновления через Airflow. Простое суммирование истории
[raw](glossary.md#term-raw) может учитывать несколько версий одной транзакции
и повторно загруженные записи, завышая результат.

Перед агрегацией требуется получить актуальное состояние транзакций,
клиентов и остальных используемых записей по их идентификаторам.
Повторное выполнение не должно добавлять те же суммы ещё раз.
Исправление суммы или изменение счёта транзакции должно отражаться
в соответствующих агрегатах, включая прежнюю группу.

Сумма загруженных транзакций сама по себе не подтверждает бухгалтерский
остаток. Правило знака `amount`, полноту истории и необходимость начальных
остатков нужно определить до реализации. SQL и DAG при оформлении задачи
не выполнялись.

#### Предпочтительный путь решения

Выполнить задачу по спек-циклу двумя последовательными этапами.
Конкретные источники, целевые имена объектов и окончательный состав разрезов
согласовать при проектировании, не вводя новый слой или универсальный
механизм генерации витрин.

##### Этап 1. Trino SQL

- Подготовить в `trino/` все скрипты создания демонстрационных объектов,
  актуализации данных и расчёта витрины.
- Перед `MERGE` сворачивать версии из [raw](glossary.md#term-raw)
  до одной актуальной записи на идентификатор транзакции, клиента
  и других используемых объектов. Определить порядок версий и обработку
  совпадающих признаков актуальности по фактическому контракту данных.
- Реализовать идемпотентный `MERGE` актуального состояния. Явно определить
  обработку удалений и пустых исходных данных с учётом доступных признаков,
  не считать отсутствие строки в очередной выборке доказательством удаления.
- Пересчитывать агрегаты из актуального состояния, а не прибавлять суммы
  очередной загрузки к прежним остаткам. Исключить сохранение устаревших
  групп после изменения ключей транзакции.
- Суммировать денежные значения без смешения валют. Зафиксировать смысл
  расчётного остатка и ограничения полноты данных.
- Подготовить проверочные запросы для сверки сумм и уникальности ключей.
  SQL должен запускаться самостоятельно, до создания DAG.

##### Этап 2. Рукописный DAG

- После проверки SQL создать отдельный `.py`-файл в `airflow/dags/`.
  SQL оставить в файлах `trino/`, без копирования текстов запросов в DAG.
- Выполнять скрипты через `TrinoHook` внутри Python-задач, используя
  Airflow Connection. Не создавать собственный оператор для этого примера.
- Отразить порядок шагов отдельными зависимыми задачами: подготовка объектов,
  актуализация записей, обновление витрины и проверки результата.
- Обеспечить доступ к SQL-файлам в окружении исполнения, понятные ошибки
  и безопасный повтор после частичного сбоя. Не предполагать общую
  атомарную транзакцию для всей последовательности запросов.
- Определить запуск после необходимых загрузок и исключить параллельные
  обновления одних демонстрационных объектов.
- Дополнить `docs/demo.md` порядком запуска и запросами просмотра результата.

##### Проверки и критерии готовности

- SQL выполняется напрямую в Trino, затем те же файлы выполняются из DAG.
- Повтор без изменения входных данных сохраняет строки и суммы витрины.
  Дубли версий не удваивают результат и не создают неоднозначный источник `MERGE`.
- Проверены новая транзакция, исправление суммы, смена группы агрегации,
  обновление атрибутов клиента и согласованное поведение пустых данных
  и удалений. Итоговые суммы сверены независимым проверочным запросом.
- DAG успешно импортируется. Ошибка SQL завершает соответствующую задачу
  ошибкой, повтор после частичного выполнения даёт корректный результат.
- Релевантные проверки выполняются в изолированном
  [e2e](glossary.md#term-e2e)-контуре по скиллу `e2e-testing`.
  Живой стенд и исходные [raw](glossary.md#term-raw)-таблицы не изменяются
  ради проверки витрины.
- Здесь добавляется только задача бэклога, без реализации SQL и DAG.

### Добавить обслуживание raw-таблиц и TTL партиций

#### Задача Jira

[DATARCH-2257](https://jira.bcs.ru/browse/DATARCH-2257)

#### Контекст

Нужно добавить два направления обслуживания [raw](glossary.md#term-raw)-таблиц:

- Обслуживание Iceberg: управление историей версий и файлами метаданных,
  очистка неиспользуемых файлов и оптимизация физической раскладки.
- Управление сроком хранения целых партиций по `days(__load_dttm)`.
  Здесь TTL партиций означает срок хранения данных, а не
  [TTL активированного источника](glossary.md#term-ttl).

Согласованный подход — отдельные DAG обслуживания со своими YAML,
независимыми от конфигураций загрузки. TTL партиций задаётся для каждой
целевой таблицы в YAML обслуживания. По умолчанию сохраняются все партиции.

Опорные материалы:

- [«Лейкхаус на Apache Iceberg»](https://subquery.ru/blog/data-lakehouse-iceberg),
  особенно раздел «Обслуживание: пять операций в правильном порядке».
  Он предлагает последовательность: удаление старых версий → очистка
  осиротевших файлов → компакция → переписывание manifest-файлов →
  обновление статистики.
- [«Apache Iceberg. Обслуживание таблиц»](https://subquery.ru/blog/courses/iceberg/table-maintenance).
  Дополнительно рассматривает автоматическую очистку старых metadata JSON.
- [«Apache Iceberg. Упражнение: Обслуживание таблиц»](https://subquery.ru/blog/courses/iceberg/maintenance-exercise).
  Содержит примеры диагностики фрагментации и обслуживания delete-файлов.

Статьи — ориентир для проектирования, не проверенная инструкция стенда.
Они различаются порядком операций и описанием физического удаления файлов.
Конкретные процедуры, параметры и ограничения нужно сверить с официальной
документацией используемых версий Iceberg, Spark и Nessie.

#### Проблема

Нужны управляемые процессы обслуживания, не привязанные к запуску загрузки.
Без политики хранения партиций нельзя ограничить глубину истории таблицы.
Накопление старых версий, мелких файлов и неиспользуемых объектов может
увеличивать объём хранения и время планирования запросов.

Иллюстративный пример: таблица с `days(__load_dttm)` должна хранить последние
365 календарных дней. Более старые дневные партиции удаляются целиком.
Это не удаление отдельных строк по их возрасту и не сохранение последних
365 непустых партиций независимо от календарных пропусков.

Удаление партиции из актуального состояния не означает немедленного
освобождения места: её файлы могут оставаться доступны через сохраняемые
[snapshots Iceberg](glossary.md#term-iceberg-snapshot).
Очистка файлов напрямую в S3 без учёта ссылок может повредить таблицу.
Объём накопленного мусора и деградация запросов при оформлении задачи
не измерялись, сценарии обслуживания на стенде не выполнялись.

#### Предпочтительный путь решения

Реализовать отдельные конфигурируемые DAG обслуживания с двумя явно
разделёнными политиками: обслуживание Iceberg и TTL партиций.

##### Конфигурация и оркестрация

- Хранить YAML обслуживания отдельно от YAML загрузки, без дублирования TTL
  в двух местах. Точные пути, ключи и схему определить в спек-цикле.
- Задавать полное имя целевой таблицы, расписание и параметры обслуживания.
  Проверять неизвестные поля, некорректные значения и конфликтующие политики
  для одной таблицы до запуска изменяющих операций.
- Разделить настройки срока хранения партиций, срока хранения
  [snapshots Iceberg](glossary.md#term-iceberg-snapshot) и окна безопасности
  очистки файлов. Одно значение не должно неявно управлять всеми тремя.
- Обеспечить координацию обслуживания и загрузок одной таблицы между DAG.
  Одного `max_active_runs=1` в каждом DAG недостаточно для взаимного исключения.
  Согласовать механизм с [задачей управления предыдущими Spark-приложениями](#останавливать-предыдущие-spark-приложения-перед-записью-в-целевую-таблицу):
  обслуживание не должно ошибочно останавливать легитимную загрузку.
- Логировать таблицу, применённую политику, границы удаления, результаты
  операций и ошибки. Предусмотреть предварительный просмотр удалений
  без изменения данных и безопасный повтор после частичного сбоя.

##### TTL целых партиций

- При отсутствии TTL сохранять все партиции. Неверное значение отклонять,
  не трактовать его как разрешение на удаление.
- Для дневных партиций по `days(__load_dttm)` поддержать срок хранения
  в календарных днях для каждой таблицы, например 365 дней.
  Перед реализацией явно определить часовую зону, включение текущего дня
  и граничную дату. Зафиксировать опорное время запуска для повторов.
- Удалять только целиком просроченные партиции через Iceberg, без прямого
  удаления каталогов или объектов S3. Не подменять эту операцию построчным TTL.
- Проверять фактическую схему партиционирования, включая её эволюцию.
  Несовместимую схему или неопределённую границу обрабатывать явным отказом
  до удаления, без автоматического перехода к построчной очистке.
- Не менять состояние загрузки и её [watermark](glossary.md#term-watermark).
  Документировать, что включение TTL ограничивает доступную историю
  [raw](glossary.md#term-raw), а увеличение срока не восстанавливает удалённые данные.

##### Обслуживание Iceberg

- Настроить удаление старых [snapshots Iceberg](glossary.md#term-iceberg-snapshot)
  с минимальным числом сохраняемых версий и очистку старых metadata JSON.
- Добавить очистку осиротевших файлов с предварительным просмотром
  и окном безопасности, учитывающим длительные записи, чтения и повторы.
  Не считать файл осиротевшим только потому, что его нет в текущей версии.
- Предусмотреть компакцию файлов данных, обработку delete-файлов при их
  наличии, переписывание manifest-файлов и обновление статистики.
  Поддержку каждой операции подтвердить для используемого стека.
- Использовать порядок пяти операций из обзорной статьи как основу,
  проверив зависимости по фактическим API. При совместном цикле сначала
  применять TTL партиций, чтобы не компактировать удаляемые данные.
  Учесть, что компакция создаёт новые версии и не обязана освобождать
  все заменённые файлы в том же цикле.
- До физической очистки учесть ссылки Iceberg, ветки и теги Nessie,
  которые могут удерживать файлы. Не переносить однотабличную очистку
  из примеров в общий каталог без проверки безопасности для других ссылок.
- Явно описать потерю доступа к удалённой истории и условия освобождения
  места. Не обещать немедленное удаление файлов после применения TTL.

##### Проверки и критерии готовности

- [Unit-проверки](glossary.md#term-unit) покрывают схему YAML, отсутствие TTL,
  разные сроки у таблиц, ошибки значений и расчёт календарной границы.
- В изолированном [e2e](glossary.md#term-e2e)-контуре проверены:
  - Бессрочное хранение по умолчанию, удаление целых старых партиций,
    сохранение граничной и свежих партиций, календарные пропуски.
  - Предварительный просмотр, повтор запуска, частичный сбой и отказ
    при несовместимой схеме партиционирования.
  - Сохранность данных после компакции, изменения числа и размера файлов,
    соблюдение политики хранения версий и физическое освобождение файлов
    только после снятия удерживающих ссылок и соблюдения окна безопасности.
  - Отсутствие повреждения файлов активной записи, длительного чтения
    и сохраняемых ссылок Nessie. Загрузки и обслуживание координируются
    между разными DAG, состояние загрузки не изменяется обслуживанием.
- Генерация и импорт DAG успешны. Релевантные проверки и полный изолированный
  прогон проходят. Неподдерживаемые операции и непроверенные случаи указаны явно.
- При реализации обновлены архитектура и инструкция эксплуатации:
  схема YAML, расписания, безопасные значения, последствия удаления
  и порядок диагностики. Реализация выполняется отдельно по спек-циклу.

### Сделать генерацию act_snap опциональной и добавить безопасную фильтрацию источника

#### Задача Jira

[DATARCH-2258](https://jira.bcs.ru/browse/DATARCH-2258)

#### Контекст

Ветка `act_snap` создаёт отдельный DAG для вспомогательной
[таблицы-снимка](glossary.md#term-snapshot) при инкрементальной конфигурации.
Текущее определение предполагает чтение полного состояния источника.
Определение и существующие ограничения описаны в [глоссарии](glossary.md#term-snapshot)
и [архитектуре](architecture.md).

Целевой контракт задачи согласован с пользователем:

- Генерация `act_snap` DAG управляется YAML-конфигурацией, а не выполняется
  безусловно для всех инкрементальных таблиц.
- Фильтр регулярного запуска задаётся в YAML. Если фильтр не указан,
  читается вся таблица источника.
- При ручном запуске через Trigger DAG в Web UI условия передаются
  структурированным JSON.
- Каждая успешная загрузка полностью заменяет `act_snap` выбранными данными
  с актуальным DDL источника. Сохранение строк вне фильтра и частичное
  обновление прежней таблицы не предполагаются.

#### Проблема

По сообщению пользователя, DAG создаётся по умолчанию для каждой
инкрементальной таблицы. При большом числе таких таблиц Airflow получает
много неиспользуемых DAG, что создаёт лишнюю нагрузку на оркестратор.

Полное чтение огромной таблицы может оказаться практически невыполнимым.
Наличие ручного запуска не решает проблему объёма: требуется ограничивать
выборку на стороне источника, а не после извлечения всей таблицы в Spark.
Приём произвольного SQL из JSON или YAML создаёт риск SQL-инъекций.

После фильтрации `act_snap` больше не представляет полное состояние источника.
Без сведений о применённых условиях потребитель не сможет определить,
какую часть данных содержит заменённая таблица.

Пользователь предложил проработать хранение границ выгрузки в отдельной
таблице pg-meta: `process_id`, полное имя target вида
`raw.<source_id>.<table>__act_snap` и JSON из Trigger DAG.
Конкретная схема хранения пока не утверждена.

Нагрузочная деградация Airflow и отказ чтения огромной таблицы в рамках
оформления задачи не воспроизводились. Описание этих проблем основано
на сообщении пользователя.

#### Предпочтительный путь решения

Расширить существующую ветку `act_snap`: явное включение генерации в YAML,
единая схема структурированного фильтра для YAML и JSON запуска,
параметризованное чтение источника и полная замена target.

##### Генерация и конфигурация запуска

- Добавить настройку включения `act_snap` DAG для конкретной
  [сущности](glossary.md#term-entity). Отсутствие явного включения
  не должно создавать неиспользуемый DAG.
  При реализации определить точные ключи и описать миграцию существующих YAML.
- При отключении и регенерации исключать прежний сгенерированный DAG
  из актуального набора. Не удалять данные `act_snap` и историю загрузок.
- В YAML задавать фильтр регулярного запуска в той же структурированной
  форме, что и в JSON ручного запуска.
- Определить однозначные правила выбора фильтра:
  - Без переопределения при запуске применяется YAML-фильтр.
  - Явно переданный фильтр запуска заменяет YAML-фильтр целиком,
    без неявного объединения условий.
  - Предусмотреть явный запрос чтения всей таблицы при наличии YAML-фильтра.
    Отсутствие переопределения и явное отключение фильтра должны различаться.
  - Некорректный фильтр приводит к отказу до чтения и изменения target,
    а не к молчаливому чтению всей таблицы.

##### Безопасное чтение и замена таблицы

- Принимать только структурированные условия: колонка, разрешённый оператор
  и типизированные значения. Проверять колонки по актуальной схеме источника,
  операторы — по разрешённому набору. Не принимать SQL-фрагменты,
  выражения или имена объектов для произвольной подстановки.
- Значения передавать JDBC-запросу отдельно через bind-параметры.
  Проверить реализуемость параметризованного чтения в используемом
  Spark/JDBC-пути для MSSQL и Oracle до выбора конкретной реализации.
  Интерполяцию строк и экранирование литералов не выдавать за параметризацию.
- Применять фильтр непосредственно на источнике ко всем запросам извлечения
  и расчёта границ JDBC-чтения. Границы JDBC-партиционирования сами по себе
  не заменяют условие фильтрации.
- Полностью заменять данные и схему `act_snap` по актуальному DDL источника,
  независимо от размера выборки. Пустая выборка также должна давать пустую
  таблицу с актуальной схемой, а не сохранять данные прежнего запуска.
  Это изменение существующего правила для пустого чтения из глоссария.
- Сохранить атомарность замены. Не менять основную инкрементальную таблицу
  и её [watermark](glossary.md#term-watermark).

##### Учёт границ выгрузки в pg-meta

В рамках проектирования проработать отдельную таблицу истории выгрузок
`act_snap` по предложению пользователя:

- Связывать запись с `process_id` и полным именем целевой таблицы.
- Сохранять исходный JSON ручного запуска и фактически применённую
  конфигурацию фильтра с учётом YAML и переопределения.
  Для регулярного запуска также должно быть понятно, какие условия действовали.
- Явно различать чтение всей таблицы и ограниченную выборку.
- До реализации согласовать схему, ключи, состояния выполнения и поведение
  при повторе загрузки. Определить, как найти сведения именно о текущем
  содержимом target, не принимая неуспешную выгрузку за опубликованную.
- Определить обработку сбоя между заменой Iceberg-таблицы и записью pg-meta.
  Не обещать общей атомарной транзакции между этими системами.

##### Проверки и критерии готовности

- Проверены включение и отключение генерации, отсутствие неявных DAG
  и исключение устаревшего сгенерированного файла без удаления данных.
- Проверены YAML-фильтр, JSON-переопределение, отсутствие фильтра,
  явное отключение YAML-фильтра, ошибки структуры, колонок, операторов и типов.
- Через реальные MSSQL/Oracle JDBC подтверждены применение фильтра на источнике
  и отдельная передача значений параметрами. Проверены кавычки, специальные
  символы и попытки SQL-инъекций в значениях, колонках и операторах.
- Повторная загрузка с другим фильтром полностью заменяет прежние строки.
  Проверены изменение DDL и пустая выборка, без сохранения прежних данных.
- Для согласованной схемы pg-meta проверены регулярный и ручной запуск,
  чтение всей таблицы, ограниченная выборка, отказ и повтор загрузки.
  Метаданные позволяют отличить опубликованный результат от неуспешного.
- Генерация/`--check`, релевантные [unit-проверки](glossary.md#term-unit)
  и изолированные [e2e](glossary.md#term-e2e) проходят.
- При реализации обновлены архитектура, определение
  [таблицы-снимка](glossary.md#term-snapshot) и примеры YAML/Trigger DAG.
  В документации явно отражены ограниченная полнота данных и новое
  поведение пустой выборки.
- Здесь добавляется только задача бэклога. Реализация выполняется отдельно
  по спек-циклу.

### Проверять смену инкрементального контракта и режимов загрузки в e2e

#### Задача Jira

[DATARCH-2253](https://jira.bcs.ru/browse/DATARCH-2253) — общая задача усиления
и оптимизации e2e-тестирования, также включает ускорение прогона.

#### Контекст

[Раздел 8.6 архитектуры](architecture.md#86-смена-контракта-и-ручные-миграции)
описывает контракт `incremental_column`/`incremental_type`, ручную миграцию
`ingestion.incremental_state` и переключения между
[полным срезом](glossary.md#term-full) и [инкрементом](glossary.md#term-increment).
Приведённый там PostgreSQL-шаблон явно обозначен как процедура,
не проверенная на работающем стенде.

Текущее покрытие и точки реализации:

- `ingestion/meta/registry.py` блокирует смену контракта и использование
  незавершённой [партии](glossary.md#term-batch) старой ревизии.
- `test/unit/test_meta.py::test_contract_and_revision_rejected_without_partial_success`
  проверяет отказ реестра на реальном PostgreSQL, но без загрузки источника.
- `test/check_extraction.py::check_registry_recovery` выполняет синтетическую
  смену колонки с аудитом и последующим [bootstrap](glossary.md#term-bootstrap).
  Этот SQL не совпадает с шаблоном §8.6 и не проверяет весь его результат,
  в частности сброс `last_process_id`. Здесь нет изменения реального источника,
  [манифеста](glossary.md#term-manifest) и загрузки через DAG.
- `ingestion/spark/raw/rdbms/incremental/load_entity.py` проверяет наличие
  колонки, поддерживаемый JDBC-тип и соответствие `contract.position_type`.
  Эти проверки могут отклонить загрузку раньше проверки контракта pg-meta.
- `test/run_flow.py` проверяет обычные загрузки обоих режимов, но не смену
  режима одной и той же таблицы с сохранением её истории и состояния.

#### Проблема

Нет сквозного подтверждения набора допустимых действий из §8.6 и точных
скриптов для каждого случая: смены/переименования колонки, смены её типа
и явного сброса позиции после подтверждённого сброса источника.
Синтетическая проверка pg-meta не подтверждает совместимость источника,
JDBC, схемы Iceberg, конфигурации DAG и ручной миграции вместе.

Также не подтверждены переходы `full → incremental`, `incremental → full`
и возврат к прежнему контракту. Успех DAG сам по себе не доказывает сохранность
истории, корректное продолжение позиции или отсутствие изменений pg-meta
при [полном срезе](glossary.md#term-full).

Вывод основан на статическом анализе графа, исходников, тестов и документации.
Миграции, переключения режимов и тестовый стек при оформлении задачи
не запускались. Перечисленные ниже результаты — критерии будущей проверки,
а не уже подтверждённые гарантии.

#### Предпочтительный путь решения

Расширить основной [e2e](glossary.md#term-e2e)-сценарий
`test/run_flow.py` и подключение проверок в `test/test.sh`.
Проверять MSSQL и Oracle через реальные источники, штатную генерацию DAG
и загрузочные операторы, а данные озера — через Trino.
Использовать отдельные тестовые таблицы и изменения только внутри
`test/.workspace/` изолированного контура `dlh-test`/`dlh-test-<suffix>`.

##### Матрица ручных миграций

1. Смена колонки на другую существующую и переименование используемой колонки.
   Проверить отказ без миграции, затем миграцию и успешную загрузку.
   Для переименования отдельно проверить отказ при обращении к прежнему имени.
2. Смена внутреннего типа той же колонки на поддерживаемый диалектом тип.
   Согласовать физический DDL, `contract.position_type` и pg-meta.
   Выбрать для каждой СУБД выполнимый DDL и совместимое расширение схемы
   Iceberg, чтобы отказ записи не подменял проверку миграции контракта.
3. Подтверждённый сброс источника с меньшим MAX и отдельно с пустой таблицей.
   Проверить отказ `SOURCE_POSITION_REGRESSION` без ручного сброса позиции.
   После миграции с прежними колонкой и типом проверить
   [bootstrap](glossary.md#term-bootstrap), включая пустой результат
   и последующее поступление данных.
4. Изменение только [lookback](glossary.md#term-lookback) без миграции.
   Уже созданная [партия](glossary.md#term-batch) сохраняет границы,
   новая использует изменённую настройку.
5. Удалённая колонка, неподдерживаемый JDBC-тип, несовпадение физического
   и объявленного типа отклоняются с конкретной диагностикой.
   Изменение строки pg-meta не должно выдаваться за исправление этих причин
   или несовместимой схемы Iceberg. Смену `source_id` или имени таблицы
   не включать в допустимые миграции прежней идентичности.

Для каждого миграционного случая:

- Остановить новые запуски и подтвердить отсутствие работающих загрузок,
  а не только паузу DAG. Использовать порядок §8.6 без параллельных писателей.
- Сохранить полные тексты миграций для каждого случая в отдельных файлах
  внутри `docs/`, отслеживаемых в git. Выполнять в тесте SQL из этих же файлов,
  а не отдельную копию в Python. Для каждого случая зафиксировать точный DDL
  источника, изменения YAML, параметры SQL и порядок команд.
  Объёмные скрипты в §8.6 не встраивать, чтобы не перегружать документ.
  В разделе оставить краткий порядок действий, ссылки на файлы миграций
  и правила подстановки значений.
- В одной транзакции проверить прежние колонку, тип и ревизию под
  `FOR UPDATE`, вставить аудит, обновить контракт, сбросить
  [watermark](glossary.md#term-watermark) и `last_process_id`, увеличить
  `revision` ровно на 1. Проверить все поля состояния и аудита до новой загрузки.
- Проверить неверный старый контракт, неверную ревизию, отсутствие строки
  состояния и повтор уже применённого скрипта. Отказ должен откатывать
  и аудит, и изменение состояния, без частичного результата.
- После регенерации запускать новый [DagRun](glossary.md#term-dagrun).
  Незавершённая старая [партия](glossary.md#term-batch) не переиспользуется
  и не может финализировать новую ревизию. История ранее успешных загрузок
  остаётся доступной.
- Проверить [bootstrap](glossary.md#term-bootstrap) нового контракта,
  затем обычную загрузку новых данных и пустого [окна](glossary.md#term-window).
  Сопоставить строки через Trino, `__process_id`, состояние и аудит pg-meta.
  Прежние строки [raw](glossary.md#term-raw) и история реестра не удаляются.

##### Переключения режимов без миграции

- `full → incremental` без строки `incremental_state`: первая загрузка
  создаёт состояние и выполняет [bootstrap](glossary.md#term-bootstrap),
  следующая читает только ожидаемое [окно](glossary.md#term-window).
  Уже накопленные [полные срезы](glossary.md#term-full) сохраняются.
- `incremental → full`: последующие запуски дописывают всю таблицу источника.
  Строка `incremental_state`, включая `watermark`, `revision`,
  `last_process_id` и `updated_at`, остаётся неизменной.
  Новые записи `incremental_batches` и `incremental_state_migrations`
  для этих запусков не создаются.
- `incremental → full → incremental` с прежним контрактом: продолжение
  от замороженного [watermark](glossary.md#term-watermark), не новый
  [bootstrap](glossary.md#term-bootstrap). Добавить данные во время полного
  режима и проверить ожидаемые границы при возврате.
  Повторное попадание строк, уже записанных полным режимом, допустимо
  в [append-only](glossary.md#term-append) истории и не считается поломкой.
- Возврат из полного режима с другой колонкой/типом при сохранённом состоянии
  требует ручной миграции. Отключение и включение настройки не обходит проверку.
- После каждого изменения конфигурации подтвердить её применение Airflow.
  Проверить актуальный набор генерируемых DAG, включая наличие DAG снимка
  только у инкрементальной конфигурации, без влияния оставшихся старых файлов.

##### Ограничения и критерии готовности

- Подготовку источников выполнять через API sydafa. Нужные изменения типов
  выполнять прямыми DDL по образцу e2e-сценария эволюции схемы
  (`test/source_ddl.py`): DBA-реквизиты читаются только из состояния sydafa
  тестового контура.
  Не расширять публичные права и не выводить секреты.
- Негативные проверки принимают только ожидаемую причину отказа.

### Разделить реестр источников на YAML-файлы и настроить JDBC-параллелизм по источникам

#### Задача Jira

[DATARCH-2242](https://jira.bcs.ru/browse/DATARCH-2242)

#### Контекст

Реестр `ingestion/conf/sources.yaml` содержит настройки всех источников:
ключ, `type` и `airflow_conn_id`. Его читает
`ingestion/generator/manifest.py::load_sources`.

Манифесты [пайплайнов](glossary.md#term-pipeline) находятся в `ingestion/conf/pipelines/`.
Они ссылаются на источник через `source_id`.
Один источник может использоваться несколькими [пайплайнами](glossary.md#term-pipeline).

Число JDBC-партиций задано глобально: `ingestion/conf/settings.yaml`
содержит `spark.jdbc.num_partitions: 4`.
Генератор передаёт его в обычный DAG и DAG снимка, затем оператор —
в `--num-jdbc-partitions` загрузчика.
Переключатель `jdbc_partitioning` задаётся отдельно для [сущности](glossary.md#term-entity) и снимка.

#### Проблема

Параллельное добавление разных источников требует изменения одного общего YAML, повышая риск merge-конфликтов. Единое число JDBC-партиций также не позволяет настроить нагрузку чтения с учётом конкретного источника.

Пример: две ветки добавляют разные источники в конец `sources.yaml`. Изменения логически независимы, но затрагивают один участок файла. Раздельные файлы устраняют эту общую точку редактирования, хотя не гарантируют отсутствие всех merge-конфликтов.

Вывод основан на статическом анализе загрузчика конфигурации и генератора.
Конфликт слияния и [runtime](glossary.md#term-runtime)-параллелизм в рамках оформления задачи не воспроизводились.

#### Предпочтительный путь решения

Заменить общий реестр каталогом `ingestion/conf/sources/`: один источник — один `<source_id>.yaml`. [Pipelines](glossary.md#term-pipeline) не объединять с источниками и не ограничивать их число на источник.

- Выводить `source_id` из имени файла без расширения:
  - Проверять по существующим правилам namespace.
  - Не дублировать идентификатор ключом внутри YAML. Содержимое — настройки одного источника.
- Использовать плоский каталог с `.yaml`, детерминированный порядок загрузки и строгую проверку полей:
  - Сообщать путь файла при ошибке.
  - Отклонять пустой реестр, недопустимые имена, неизвестные поля и повторные идентификаторы, не перезаписывая источник молча.
- Добавить в конфигурацию источника необязательный `spark.jdbc.num_partitions`:
  - Положительное целое, без bool.
  - При отсутствии применять 4.
  - Не добавлять переопределение этого числа на уровне [pipeline](glossary.md#term-pipeline) или [сущности](glossary.md#term-entity).

Пример `ingestion/conf/sources/bank.yaml`:

```yaml
type: rdbms
airflow_conn_id: bank_source
spark:
  jdbc:
    num_partitions: 4
```

- Передавать значение из `SourceConfig` в обычные и [snapshot](glossary.md#term-snapshot) DAG, затем в соответствующие операторы и Spark CLI. Сохранить `jdbc_partitioning` на уровне [сущности](glossary.md#term-entity)/[snapshot](glossary.md#term-snapshot): при отключении чтение остаётся непартиционированным независимо от настройки источника. Фактическое число партиций может быть меньше запрошенного по действующим правилам reader.
- Число партиций ограничивает параллелизм одной загрузки, а не суммарное число JDBC-соединений всех параллельных загрузок источника. Не вводить в этой задаче общий connection budget, [pools](glossary.md#term-pool) или resource limits Spark.
- Мигрировать `bank` и `broker`:
  - Переключить `--sources` генератора с файла на каталог, обновить потребителей и документацию.
  - Удалить глобальный `spark.jdbc.num_partitions`.
  - Поскольку сейчас это единственное содержимое settings, убрать `settings.yaml` и связанные `--settings`/`load_settings`, не оставляя пустую конфигурацию или совместимый двойной источник значения.
  - Миграцию CLI описать явно.
- Сохранить ссылки [pipeline](glossary.md#term-pipeline) по `source_id`, DAG/task IDs, targets и существующие проверки коллизий DAG/target во всём наборе [pipelines](glossary.md#term-pipeline). Добавление независимого источника не должно требовать редактирования центрального списка или общего файла настроек.
- Согласовать с задачей [«Управление ресурсами Spark на уровне отдельной джобы»](#управление-ресурсами-spark-на-уровне-отдельной-джобы):
  - Её описание текущих глобальных JDBC-настроек относится к состоянию до этой миграции.
  - Ресурсы приложения остаются отдельными параметрами [сущности](glossary.md#term-entity).
  - JDBC-параллелизм после миграции задаётся источником.

Проверки и критерии готовности:

- [Unit](glossary.md#term-unit):
  - Идентификатор из имени файла, строгая схема, ошибки с путём, дефолт 4, разные значения для двух источников, отклонение 0/отрицательных/дробных/bool значений и неизвестных полей.
  - Отсутствие зависимости от порядка файлов.
- Генерация обычных и [snapshot](glossary.md#term-snapshot) DAG:
  - Передаёт значение соответствующего источника.
  - Сохраняет отключение `jdbc_partitioning`.
  - При миграции существующих источников с дефолтом 4 семантика и идентификаторы DAG не меняются.
  - Генерация/`--check` успешны.
- Независимые источники добавляются отдельными файлами без изменений центрального реестра.
  - Ссылки на неизвестный источник и коллизии DAG/target по-прежнему отклоняются.
- [E2E](glossary.md#term-e2e):
  - Загрузки MSSQL/Oracle и актуальные снимки проходят в изолированном контуре.
  - Параметры чтения соответствуют источнику.
  - Полный `./test/test.sh` — `FAIL=0`, exit 0.
- README и архитектурная документация обновлены по своим зонам ответственности, граф актуализирован при реализации.
  - Реализация выполняется отдельно по спек-циклу.
  - Здесь добавляется только задача бэклога.

### Останавливать предыдущие Spark-приложения перед записью в целевую таблицу

#### Задача Jira

[DATARCH-2245](https://jira.bcs.ru/browse/DATARCH-2245)

#### Контекст

- Текущие `IngestFullOperator`, `IngestIncrementalOperator` и `IngestActSnapOperator` наследуют `SparkSubmitOperator`, используют Spark Standalone и `deploy_mode=client`.
  - [Driver](glossary.md#term-driver) работает в `airflow-scheduler`, [executors](glossary.md#term-executor) — на Spark worker.
- Базовый архитектурный контракт: одна задача пишет в одну целевую таблицу, другая задача не может писать в ту же таблицу. Параллельная запись в один target запрещена.
  - Все генерируемые DAG имеют фиксированное `max_active_runs=1`, включая DAG [актуальных снимков](glossary.md#term-snapshot).
  - Это обязательная настройка, не параметр пользовательской конфигурации. В `ingestion/generator/generate_dags.py` уже задано `MAX_ACTIVE_RUNS = 1` для обоих шаблонов.
- Генерируемые задачи сейчас не задают `retries`: повтор после отказа процесса возможен только вручную через [Clear](glossary.md#term-clear).
- `ingestion/meta/registry.py::start_batch` предполагает отсутствие живого предыдущего обработчика. [CAS revision](glossary.md#term-cas) защищает финализацию метаданных, но не останавливает старое Spark-приложение и не отменяет выполненную запись в Iceberg.
- Основные файлы: `ingestion/operators/raw_rdbms.py`, `ingestion/operators/process.py`, `ingestion/generator/generate_dags.py`, загрузчики в `ingestion/spark/raw/rdbms/`.

#### Проблема

Airflow может завершить задачу и начать [retry](glossary.md#term-retry), пока её прежнее Spark-приложение ещё работает. `max_active_runs=1` ограничивает запуски DAG в Airflow, но не учитывает оставшееся внешнее приложение после отказа процесса задачи.

В изолированном диагностическом контуре 2026-11-11 с Airflow 3.3.2 и Spark provider 6.3.2 проверено:

- `SIGKILL` task runner оставил живой [driver](glossary.md#term-driver). [Retry](glossary.md#term-retry) создал второе приложение, оба одновременно работали на worker.
- Убийство отдельного [executor](glossary.md#term-executor) не остановило приложение: Spark создал замену.
- `POST /app/kill/` Spark master остановил целое client-mode приложение. В наблюдении завершились и [executors](glossary.md#term-executor), и локальные JVM/Python [driver](glossary.md#term-driver).
- Очистка через `on_retry_callback` сработала после `SIGKILL`, но `on_failure_callback` последней убитой задачи не выполнился в наблюдаемом интервале.
- Исключение из `on_execute_callback` было подавлено Airflow: новый `spark-submit` всё равно запустился.
- Обычное исключение приложения и timeout в проверенных запусках не оставили работающих приложений. При полном убийстве контейнера scheduler Spark штатно освободил [executors](glossary.md#term-executor).

Это проверка жизненного цикла на диагностическом Spark-приложении без записи данных, а не воспроизведение повреждения данных реальной загрузки. Последующее ревью исходников Spark 3.5.5 уточнило:

- Master удаляет приложение из `activeapps` до фактического завершения его [executors](glossary.md#term-executor). Для подтверждения остановки нужны состояния workers.
- Уведомление `ApplicationRemoved` инициирует остановку SparkContext client-mode [driver](glossary.md#term-driver), но не является принудительным завершением всего Python-скрипта. Механика выполнения описана в [архитектуре](architecture.md#как-python-скрипт-выполняется-в-spark).

Повторный диагностический контур 2026-11-12 на том же образе Airflow уточнил поведение callbacks и оставшихся приложений:

- Доставка `on_retry_callback` после `SIGKILL` task runner недетерминированна: в двух прогонах 2026-11-11 callback исполнялся, в трёх прогонах 2026-11-12 — не исполнялся вовсе.
- При штатном отказе задачи callbacks исполняются в самом task runner до перевода задачи в [retry](glossary.md#term-retry) и до отправки нового приложения.
- Очистка по общему имени приложения при двух одновременных запусках одного target останавливает и новое приложение: воспроизведено взаимное уничтожение приложений двух запусков.
- Судьба приложения, оставшегося после `SIGKILL` task runner, недетерминированна: в проверенных прогонах оно завершалось самостоятельно примерно за полторы минуты или доживало до естественного конца работы.

#### Предпочтительный путь решения

Сохранить текущий `SparkSubmitOperator` и client mode. Перед каждым новым `spark-submit` обязательно останавливать все предыдущие приложения записи в тот же target и подтверждать завершение. Решение независимо от [перехода на DockerOperator](#изолировать-spark-drivers-через-dockeroperator).

##### Маркировка и область очистки

- Имя приложения через `spark.app.name` — только полное каноническое имя целевой таблицы, включая каталог и namespace. Без префиксов потока, суффикса попытки, хэша и идентификатора стенда или контура.
  - Кластер для очистки и записи выбирается подключением оператора, а не именем приложения.
  - Целевая таблица уже передаётся загрузчику аргументом `--target-table`. Загрузчик использует это значение дословно в `SparkSession.builder.appName(...)`, без независимого построения другого имени.
  - Идентичность [попытки](glossary.md#term-attempt) в имя не включать: остановка по запуску и попытке в callbacks не используется, а поиск перед отправкой ведётся по целевой таблице.
  - Основная таблица и [актуальный снимок](glossary.md#term-snapshot) имеют разные targets и не должны останавливать друг друга.
- Искать приложения по точному равенству имени, не по подстроке или одному PID. Не зависеть от XCom предыдущего запуска.
  - [Executors](glossary.md#term-executor) сопоставляются по application ID, отдельные теги на каждом процессе не требуются.
- Изоляцию [e2e](glossary.md#term-e2e) обеспечивать инфраструктурой тестового стенда: отдельными Spark master/workers, сетью и Airflow Connections, направленными только в тестовый кластер.
  - Имена приложений не являются границей изоляции. Не добавлять в переносимый код загрузки параметры compose-проекта или специальные ветвления для тестового контура.
  - Управляющие запросы очистки и `spark-submit` должны обращаться к одному и тому же выбранному кластеру. Не использовать адрес основного стенда как fallback.

##### Обязательная проверка перед запуском

- Выполнять очистку в начале `execute` всех трёх существующих операторов, до `super().execute()`, отправки приложения и начала записи.
  - Не использовать `on_execute_callback` как обязательный барьер: его ошибка не запрещает выполнение задачи в проверенной версии Airflow.
- Найти все активные приложения записи с тем же ключом target, включая остатки прежних [retry](glossary.md#term-retry), [Clear](glossary.md#term-clear) и других запусков DAG.
  - Получить состояние через `GET <master_webui>/json/`. Сохранить application IDs и список workers из `workers[].webuiaddress` до отправки остановки.
  - `<master_webui>` строить из того же Connection оператора, что и submit: хост соединения и порт UI из ключа `webui_port` в extra. Один Connection описывает весь кластер. Отдельная настройка или константа в коде не допускаются.
- Для каждого приложения вызвать остановку через Spark master: `POST /app/kill/` с `id=<application_id>` и `terminate=true`.
  - Это UI endpoint Standalone, не REST submission API для cluster-mode `driver-...`.
  - Проверить доступность endpoint, `spark.ui.killEnabled` и UI ACL. HTTP-ответ после redirect не подтверждает исполнение команды.
  - В текущем стенде master UI уже опубликован на порту хоста 8080, worker UI — 8081, аутентификация не настроена. Зафиксировать это существующее ограничение исследовательского контура, не расширять доступ ради очистки и не переносить такую конфигурацию в production как безопасную.
- С ограниченным временем ожидания подтвердить завершение приложений и освобождение связанных [executors](glossary.md#term-executor).
  - Опросить master до исчезновения приложения из `activeapps` и появления `KILLED` в `completedapps`. Корректно обработать естественное завершение приложения одновременно с очисткой.
  - Опросить `GET <worker_webui>/json/` всех workers, которые могли исполнять приложения. Подтвердить отсутствие соответствующих `appid` в активном массиве `executors`. Записи в `finishedexecutors` не являются работающими процессами.
  - Использовать сохранённый список workers и учитывать обновления состава кластера. Исчезновение worker из списка master не считать подтверждением остановки его [executors](glossary.md#term-executor).
  - HTTP 200, `KILLED` в master или одно исчезновение из `activeapps` без проверки workers недостаточны.
- При недоступности master или необходимого worker, некорректном ответе, ошибке остановки, неизвестном состоянии или истечении ожидания завершать задачу ошибкой. Новый `spark-submit` не вызывать.
  - Гарантия — запрет новой загрузки до подтверждения остановки предыдущих, а не возможность завершить приложение при любой аварии.
- Сохранить и проверить обязательное `max_active_runs=1` во всех генерируемых DAG и уникальность задачи-владельца target. Не вводить отдельную блокировку target при соблюдении этих контрактов.
  - Генератор уже отклоняет коллизии targets в общем наборе, включая пересечения основной таблицы и [актуального снимка](glossary.md#term-snapshot). Закрепить существующее поведение тестами.
- Задать всем задачам генерируемых DAG `retries=2` через `default_args` шаблонов генератора. Штатные повторы после отказа процесса задачи заменяют ручной Clear.
  - `retry_delay` зафиксировать явно: сейчас он не задаётся, и Airflow применяет значение по умолчанию.

##### Callbacks и метаданные

- Использовать `on_retry_callback` и `on_failure_callback` только для логирования: событие [retry](glossary.md#term-retry), application IDs, причина и результат проверки без credentials. Остановку приложений в callbacks не выполнять.
  - Доставка callback после `SIGKILL` task runner недетерминированна, обязательную очистку на неё не возлагать.
  - При штатном отказе задачи callback исполняется в самом task runner до перевода задачи в retry и не может встретить новое приложение.
  - Очистка по общему имени приложения останавливает и новое легитимное приложение, поэтому без идентичности попытки в имени она в callbacks недопустима.
  - Не заменять существующее логирование FAILED. Компоновать callbacks с ним, а не заменять.
  - Callbacks задавать только функциями уровня модуля: замыкание теряется при постановке в очередь.
- Сохранять `process_id` и идентичность [партии загрузки](glossary.md#term-batch) при повторе задачи загрузки.
  - Повтор `generate_process_id` по действующему контракту выделяет новый номер.
- Сохранять фиксированное [окно](glossary.md#term-window), no-op для успешно завершённой [партии загрузки](glossary.md#term-batch) и гарантии [watermark](glossary.md#term-watermark).

##### Границы решения

- Не управлять PID, группами процессов или отдельным принудительным kill JVM/Python. Управлять Spark-приложением через менеджер кластера.
  - Подтверждать освобождение [executors](glossary.md#term-executor). Spark инициирует остановку SparkContext, но завершение всего Python-процесса [driver](glossary.md#term-driver) не гарантируется.
  - Обычный Python-код, включая финализацию pg-meta после уже выполненного Iceberg append, может продолжить работу. Остановка приложения не отменяет уже выполненные операции хранения.
- Восстановление после полного отказа Airflow, периодический внешний сборщик оставшихся приложений и production-платформа не входят в задачу.
- Поиск в master покрывает зарегистрированные приложения. Зависший до регистрации [driver](glossary.md#term-driver) не покрывается этой механикой и не должен выдаваться за решённый сценарий.
- Не обещать exactly-once: авария между Iceberg append и финализацией pg-meta по-прежнему допускает повторную запись по модели at-least-once.
  - Если прежняя финализация ещё не завершилась, новый запуск может увидеть незавершённую [партию](glossary.md#term-batch) и повторить загрузку. Это существующее ограничение контракта, а не основание вводить отдельный kill Python-процесса.
  - Повторная запись того же [окна](glossary.md#term-window) отличается служебной колонкой `__load_dttm` и сворачивается идемпотентным merge слоя [ODS](glossary.md#term-ods) по плану архитектуры.
  - [CAS revision](glossary.md#term-cas) защищает финализацию метаданных, но не является общей блокировкой не-Spark действий [driver](glossary.md#term-driver).

##### Проверки и критерии готовности

- [Unit](glossary.md#term-unit):
  - Имя приложения равно полному имени target без идентификатора контура и загрузчик использует его дословно. Точное сравнение target, различение `main` и `act_snap`, независимость от XCom. Очистка и submit используют один кластер.
  - Очистка нуля, одного и нескольких старых приложений, идемпотентность, ожидание и запрет submit при любой неподтверждённой остановке.
  - Обработка некорректных ответов master/workers, изменения состава workers и естественного завершения одновременно с остановкой.
  - Callbacks логируют и не останавливают приложения, логирование FAILED сохранено.
  - Все обычные и [snapshot](glossary.md#term-snapshot) DAG имеют неизменяемое `max_active_runs=1` и `retries=2` для всех задач, коллизии задачи-владельца target отклоняются.
- [E2E](glossary.md#term-e2e) для всех трёх операторов:
  - Старое зарегистрированное приложение остаётся после убийства task runner. Перед новым submit оно завершается вместе со связанными [executors](glossary.md#term-executor).
  - Несколько оставшихся приложений одного target очищаются до старта нового.
  - Ошибка/недоступность master и отсутствие подтверждения остановки не допускают нового приложения.
  - Master уже показывает `KILLED`, но [executor](glossary.md#term-executor) ещё активен на worker: новый submit запрещён до фактического завершения.
  - Необходимый worker недоступен или возвращает некорректное состояние: новый submit запрещён.
  - Callbacks завершённой [попытки](glossary.md#term-attempt) логируют событие и не останавливают новое приложение.
  - Другие targets и [актуальный снимок](glossary.md#term-snapshot) не затрагиваются. Одинаковый target в независимом кластере основного стенда не затрагивается благодаря изоляции тестовой инфраструктуры, а не отличию имени приложения.
  - Обычная ошибка и timeout, [retry](glossary.md#term-retry) со сквозным `process_id` и повтор после окончательного отказа сохраняют контракты загрузки.
  - Для реальной загрузки [инкремента](glossary.md#term-increment) проверен сбой около границы Iceberg append → финализация pg-meta. Сохранены идентичность [партии](glossary.md#term-batch) и гарантии [watermark](glossary.md#term-watermark), отсутствие повторных записей не требуется.
    - Партия может быть успешно финализирована или помечена FAILED прежним driver уже после остановки приложения. Повтор корректно обрабатывает оба состояния.
- Генерация/`--check`, [unit-тесты](glossary.md#term-unit) и полный `./test/test.sh` проходят: `FAIL=0`, exit 0.
- При реализации обновлены README, архитектурная документация и граф. Ограничения endpoint и непроверенные аварийные сценарии указаны явно.
  - В архитектуру встроена сводная таблица функций всех callbacks: DAG-уровень, `log_task_failed`, логирующие `on_retry_callback`/`on_failure_callback` задач загрузки — с уровнем, назначением и границами каждого.

### Шаблонизация кода в generator/generate_dags.py

#### Задача Jira

[DATARCH-2243](https://jira.bcs.ru/browse/DATARCH-2243)

#### Контекст

Генератор DAG-ов (`ingestion/generator/generate_dags.py`) преобразует декларативные манифесты YAML в готовые Python-файлы DAG-ов. Функции `generate_dag_source`, `generate_snapshot_dag_source`, `_entity_block` и `_snapshot_entity_block` строят код строками, объединяемыми в список:

```python
lines = [
    "    with TaskGroup(...) as load_group:",
    "        log_start = TableLogOperator(...)",
]
```

Затем список объединяется в один файл через `"\n".join(lines)`.

SQL также встроен в Python, но используется по-разному:

- Пакет `ingestion/meta/`: статические запросы PostgreSQL, включая многострочные INSERT/UPDATE реестра [инкремента](glossary.md#term-increment).
  - Значения передаются отдельно через DB-API-параметры `%s`.
  - Транзакции, порядок блокировок и [CAS revision](glossary.md#term-cas) управляются Python-кодом.
- `ingestion/spark/raw/rdbms/reader.py`:
  - `build_extract_query` собирает вложенный SELECT с проекциями и необязательным WHERE.
  - `read_bounds` строит MIN/MAX по запросу чтения.
- `ingestion/spark/raw/iceberg.py::build_create_table_sql` и `ingestion/spark/raw/rdbms/incremental/load_act_snap.py::build_rtas_sql`: составные Spark SQL DDL для создания [raw](glossary.md#term-raw)-таблицы и атомарной замены актуального снимка.
- `ingestion/sources/rdbms/dialects/mssql.py` и `oracle.py`: короткие диалектные выражения, quoting идентификаторов и точное представление временных позиций. Это не самостоятельные запросы.

#### Проблема

1. **Хрупкость отступов**: форматирование пробелов и табуляции требует ручного контроля, поэтому легко допустить ошибку.
2. **Сложность модификации**:
   - При добавлении новых операторов или параметров нужно изменять текстовые шаблоны.
   - Логика читается как строки, а не как объекты.
3. **Отсутствие структурной проверки при рендеринге**:
   - Строковая сборка сама по себе не проверяет синтаксис Python.
   - Такую проверку можно и нужно выполнять до записи файла.
   - Шаблонизация сама по себе также не даёт типизации или гарантии корректности.
4. **Дублирование логики**: некоторые конструкции (например, TaskGroup, цепочки операторов) повторяются с незначительными вариациями.
5. **Смешение SQL и управляющего кода**: SQL приходится читать как набор строковых литералов, а изменение проекций, условий и DDL затрагивает Python-форматирование. При этом механическое вынесение каждого однострочного выражения лишь усложнит навигацию, а подстановка значений через Jinja вместо DB-API-параметров ухудшит безопасность.

Пример: `build_extract_query` соединяет вложенные SELECT, проекции и условный WHERE, а `plan_batch` содержит длинный INSERT с отдельным кортежем из 17 параметров. SQL-файлы облегчат чтение этих конструкций, но не отменят проверку соответствия параметров.

[Runtime-кейс](glossary.md#term-runtime) и прототип шаблонизации в рамках оформления задачи не выполнялись.

#### Предпочтительный путь решения

Отделить тексты от управляющей логики:

- Jinja2 — только для шаблонов DAG.
- Обычные `.sql`-файлы — для выносимых SQL-запросов.
- Не использовать Jinja для SQL и не вводить `.sql.j2`.
- Не создавать AST-генератор или собственный язык шаблонов.
- Не переносить бизнес-логику в шаблоны.

##### Генерация DAG

- Вынести обычный и [snapshot](glossary.md#term-snapshot) DAG в `.py.j2` с общими фрагментами там, где это устраняет повторение:
  - Python готовит контекст из проверенных манифестов.
  - Шаблон отвечает за текст, отступы и простые циклы/условия.
- Сохранить публичные функции генератора, имена файлов, конфигурационный контракт и полностью развёрнутые DAG-и: без YAML/Jinja-рендеринга при разборе DAG в Airflow.
- Сериализовать значения как корректные Python-литералы, а не вставлять необработанные строки:
  - Проверять результат через `ast.parse` или `compile` до записи.
  - Сохранить детерминированность вывода и `--check`.

##### SQL-файлы и шаблоны

- Вынести полные статические запросы пакета `ingestion/meta/` в `.sql`, загружать их как текст без Jinja:
  - Сохранить `%s` и отдельную передачу параметров в `execute`.
  - Не менять транзакции, порядок блокировок, [retry](glossary.md#term-retry)/idempotency и [CAS revision](glossary.md#term-cas).
- Вынести составные запросы `build_extract_query`, `read_bounds`, `build_create_table_sql` и `build_rtas_sql` в `.sql` с именованными полями подстановки через стандартный `str.format_map`. Сохранить существующие функции как точки подготовки SQL-фрагментов и подстановки, без изменения их контрактов и семантики запросов. Необязательный WHERE и списки проекций готовить в Python, без условий и циклов в SQL-файлах.
- Оставить в Python валидацию, выбор диалекта, quoting идентификаторов, канонизацию и экранирование литералов, вычисление временных выражений, границ и предикатов:
  - В именованные поля SQL-файлов подставлять только подготовленные фрагменты, а не произвольные непроверенные значения.
  - Строковая подстановка не заменяет bind-параметры и не защищает от SQL injection.
  - Значения запросов pg-meta по-прежнему передаются отдельно через `%s`.
- Ограничить объём выноса SQL:
  - Короткие запросы-проверки и диалектные выражения не выносить ради единообразия.
  - Не заменять DataFrame API SQL-шаблонами.
  - SQL инициализации `conf/pg-meta/init/` не затрагивать.

##### Загрузка и окружение

- Хранить файлы рядом с владеющими компонентами, а не в общем несвязанном каталоге:
  - Загружать независимо от текущего рабочего каталога.
  - Кэшировать загруженные тексты SQL и скомпилированные DAG-шаблоны в пределах процесса.
- Ограничить средства шаблонизации:
  - Для Jinja в генераторе DAG использовать `StrictUndefined` и отключённый HTML autoescape.
  - Для SQL ограничиться загрузкой текста и стандартной подстановкой подготовленных фрагментов.
  - Не строить универсальный SQL-конструктор.
- Обеспечить зависимости и доставку:
  - Явно объявить Jinja2 в окружении генератора DAG. Для SQL новая зависимость не нужна.
  - Включить `.sql`-файлы в доставку кода Airflow и Spark [driver](glossary.md#term-driver) в основном и тестовом контурах.
  - Не полагаться на транзитивную зависимость Airflow или пути исходного checkout.

### Управление ресурсами Spark на уровне отдельной джобы

#### Задача Jira

[DATARCH-2247](https://jira.bcs.ru/browse/DATARCH-2247)

#### Контекст

Модель выполнения Spark:

- Стенд использует Spark Standalone 3.5.5.
- Дефолты параметров — по документации Apache Spark 3.5.x.

##### Выполнение и обмен данными

- [Driver](glossary.md#term-driver) создаёт SparkSession, строит план и распределяет задачи между [executors](glossary.md#term-executor).
  На него возвращаются результаты `collect` и агрегаций.
- [Executors](glossary.md#term-executor) выполняют задачи и записывают данные. При нехватке памяти
  промежуточные данные выгружаются на локальный диск — это **[spill](glossary.md#term-spill)**.
- На стенде [driver](glossary.md#term-driver) работает в `airflow-scheduler`, [executors](glossary.md#term-executor) — на `spark-worker`.
  Изоляция описана в [отдельной задаче DockerOperator](#изолировать-spark-drivers-через-dockeroperator).
- `filter`, `join`, `groupBy` строят план. Действия `count`, `show`, `write`
  запускают вычисления — **[job](glossary.md#term-job)**.
- [Job](glossary.md#term-job) делится на стадии (**[stages](glossary.md#term-job)**) по границам обмена данными.
  Стадия состоит из задач (**tasks**), каждая обрабатывает одну партицию.
- При стандартной настройке одна одновременно выполняемая задача занимает одно ядро [executor](glossary.md#term-executor).

**[Shuffle](glossary.md#term-shuffle)** — перераспределение данных для соединений, группировок и сортировки:

1. Map-задачи записывают блоки на диск [executors](glossary.md#term-executor).
2. Reduce-задачи забирают нужные блоки по сети.

Сеть и диск могут делать [shuffle](glossary.md#term-shuffle) дорогим. Возможные приёмы оптимизации самих джоб:

- **Broadcast join:** малая таблица копируется в память каждого [executor](glossary.md#term-executor).
  Большую таблицу не нужно перераспределять для соединения.
- **Key salting:** к ключам добавляют суффиксы, чтобы распределить
  слишком многочисленные строки одного ключа между несколькими партициями.

##### Память executor

Heap JVM включает:

- зарезервированную память Spark — около 300 МБ.
- user memory — структуры приложения и пользовательские функции.
- unified-область: storage для кэша и broadcast, execution для [shuffle](glossary.md#term-shuffle),
  соединений, сортировок и агрегаций.

Storage и execution динамически делят память. Execution может вытеснять кэш.

Управляемые параметры и их роль (в скобках — дефолты Spark 3.5.x):

| Параметр | Что задаёт | Дефолт |
|---|---|---|
| `spark.executor.cores` | число [слотов](glossary.md#term-slot) (одновременно выполняемых задач) в [executor](glossary.md#term-executor).<br>В Standalone также определяет, сколько [executors](glossary.md#term-executor) приложения размещается на worker | не задан — в Standalone [executor](glossary.md#term-executor) получает все ядра worker |
| `spark.cores.max` | суммарное число ядер, которое приложение может занять на кластере Standalone.<br>Ограничивает приложение целиком, тогда как `spark.executor.cores` — один [executor](glossary.md#term-executor) | не задан — приложение получает все ядра кластера |
| `spark.executor.memory` | heap JVM [executor](glossary.md#term-executor).<br>Определяет, сколько данных обрабатывается без [spill](glossary.md#term-spill) | `1g` |
| `spark.sql.shuffle.partitions` | на сколько партиций делятся данные после [shuffle](glossary.md#term-shuffle).<br>Ориентир — 2–3 партиции на [слот](glossary.md#term-slot) | `200` |
| `spark.driver.memory` | heap JVM [driver](glossary.md#term-driver): хранит план и метаданные приложения, принимает результаты действий.<br>Вычисления и запись данных выполняют [executors](glossary.md#term-executor) | `1g` |

В эту задачу не входит внутреннее распределение памяти [executor](glossary.md#term-executor):

- `spark.memory.fraction=0.6` — доля unified-области после вычета зарезервированной памяти.
- `spark.memory.storageFraction=0.5` — защищённая от вытеснения доля storage внутри неё.

Эти настройки меняются только по результатам диагностики [spill](glossary.md#term-spill) или отказов памяти.

Ресурсы на стенде сейчас не заданы нигде:

- `conf/spark/spark-defaults.conf` содержит только настройки каталога Iceberg/Nessie/S3 и действует на все приложения кластера.
- `spark-worker` стартует без `--cores`/`--memory` и объявляет все ресурсы хоста.
- Операторы загрузки передают в `SparkSubmitOperator` только application и deploy_mode, без `conf`.

Существующий маршрут параметров джобы:
`ingestion/conf/settings.yaml` (`spark.jdbc.num_partitions` — глобальный дефолт) и секция `spark:` [сущности](glossary.md#term-entity) манифеста (`jdbc_partitioning`) → генератор DAG-ов → оператор → аргументы джобы.

Переименование выполнено, включая CLI `--no-jdbc-partitioning`, аргумент оператора и поле `EntityConfig`.
Повторное переименование не требуется.

Пример влияния настроек на [сущности](glossary.md#term-entity) DAG-а `ingest__rdbms__bank` (целевая конфигурация):

```yaml
entities:
  - fqn: retail_bank.transactions
    spark:
      jdbc_partitioning: true
      cores_max: 4
      executor_cores: 4
      executor_memory: 4g
      shuffle_partitions: 12
  - fqn: retail_bank.deals
    spark:
      jdbc_partitioning: false
      cores_max: 2
      executor_cores: 2
      executor_memory: 1g
```

Что изменится по сравнению с дефолтами Spark:

- Параметры spark-submit:
  - Для `transactions` — `--conf spark.cores.max=4 --conf spark.executor.cores=4 --conf spark.executor.memory=4g --conf spark.sql.shuffle.partitions=12`.
  - Для `deals` — аналогично своим значениям.
- Приложения ограничены 4 и 2 ядрами: при одновременном запуске ([пул](glossary.md#term-pool) `ingest_loads` допускает) они размещаются на единственном `spark-worker` одновременно, а не последовательно — сейчас первое приложение занимает все ядра worker.
- Heap [executor](glossary.md#term-executor):
  - Для `transactions` — 4 ГБ вместо дефолтного 1 ГБ: больше данных обрабатывается без [spill](glossary.md#term-spill) на диск.
  - Для `deals` остаётся 1 ГБ.
- [Shuffle-стадия](glossary.md#term-shuffle) агрегации count/max в `transactions` использует 12 партиций вместо 200: меньше мелких задач и файлов данных.

#### Проблема

Все загрузки [raw-слоя](glossary.md#term-raw) исполняются с одинаковыми дефолтными ресурсами, и настроить их под конкретную джобу нельзя:

- Heap [executor](glossary.md#term-executor) 1 ГБ:
  - При обработке крупной таблицы возникает [spill](glossary.md#term-spill) на диск или отказ по памяти (OOM).
  - Увеличить его невозможно.
- Не заданные `spark.cores.max` и `spark.executor.cores`: каждое приложение запрашивает все ядра единственного worker одним [executor-ом](glossary.md#term-executor), и допущенные [пулом](glossary.md#term-pool) `ingest_loads` параллельные загрузки ожидают освобождения ядер вместо одновременного выполнения.
- `spark.sql.shuffle.partitions=200` не согласован с масштабом стенда:
  - Избыточные мелкие задачи и файлы.
  - Затрагивает и текущую загрузку: агрегация count/max порождает [stage](glossary.md#term-job) с [shuffle](glossary.md#term-shuffle).

Пример: `retail_bank.transactions` (крупная таблица) и `retail_bank.deals` (малая, `spark.jdbc_partitioning: false`) получают идентичные ресурсы.

Кейс воспроизведения (не проверен в рамках оформления бэклога):

1. Запустить две загрузки одновременно и наблюдать Spark Master UI (`:8080`) — приложения, их [executors](glossary.md#term-executor), cores и memory.
2. Сравнить с последовательным запуском.

Ожидаемое после решения — одновременное выполнение с заданными на уровне [сущности](glossary.md#term-entity) ресурсами вместо ожидания освобождения ядер.

#### Предпочтительный путь решения

Передавать ресурсы приложения по существующему маршруту:
манифест → генератор → оператор → spark-submit.
Не расширять `ingestion/conf/settings.yaml`.

1. Сохранить действующий контракт `spark.jdbc_partitioning` и `--no-jdbc-partitioning`: он управляет только JDBC-нарезкой, независимо от новых ресурсных ключей.
2. Добавить в секцию `spark:` [сущности](glossary.md#term-entity) ключи ресурсов:
   - `cores_max`, `executor_cores`, `executor_memory`, `shuffle_partitions`, `driver_memory` без префикса `spark.`. Префикс добавляется при формировании `--conf`.
   - Валидация с белым списком допустимых ключей в `ingestion/generator/manifest.py`.
   - [Сущность](glossary.md#term-entity) без ключей ресурсов запускается без `--conf` — с дефолтами Spark.
3. Передать параметры конкретному приложению:
   - Генератор рендерит параметры в операторы загрузки.
   - Оператор передаёт их в `SparkSubmitOperator` через `conf` → `spark-submit --conf spark.<ключ>=<значение>`.
   - Конфигурация не затрагивает общий `spark-defaults.conf`.
4. Валидация значений:
   - `cores_max`, `executor_cores` и `shuffle_partitions` — положительные целые.
   - `executor_memory` и `driver_memory` — строки вида `<число><k|m|g>`.

Границы решения:

- Глобальные дефолты в `ingestion/conf/settings.yaml` не добавляются:
  - `spark.jdbc.num_partitions` остаётся единственным глобальным параметром.
  - Ресурсы задаются только на уровне [сущностей](glossary.md#term-entity).
- Значения по [сущностям](glossary.md#term-entity) выбираются так, чтобы сумма ядер и памяти одновременно выполняемых загрузок из [пула](glossary.md#term-pool) `ingest_loads` помещалась в единственный `spark-worker`.
  - [Сущность](glossary.md#term-entity) без явных ресурсов запрашивает все ядра worker и блокирует параллельные приложения.
- `driver_memory` согласован с контейнером, где работает [driver](glossary.md#term-driver):
  - Сейчас — `airflow-scheduler`.
  - После [перехода на DockerOperator](#изолировать-spark-drivers-через-dockeroperator) — лимиты контейнера [driver](glossary.md#term-driver).
- `shuffle_partitions` критичен прежде всего для будущих слоёв с join/groupBy.
  - Текущая [raw](glossary.md#term-raw)-загрузка порождает мало [shuffle](glossary.md#term-shuffle).
- Задача управляет только ресурсами запуска:
  - JDBC-параллелизм чтения (`num_partitions`, `jdbc_partitioning`) — отдельный существующий механизм.
  - Broadcast-соединения, размножение ключей и управление числом партиций (repartition/coalesce) — приёмы реализации самих джоб, а не параметры запуска.

#### Проверки и критерии готовности

- [Unit](glossary.md#term-unit):
  - Белый список и форматы валидации ресурсных ключей без изменения `jdbc_partitioning`.
  - Оператор корректно формирует `--conf`-параметры из ключей [сущности](glossary.md#term-entity).
  - Для [сущности](glossary.md#term-entity) без ключей ресурсов `--conf` не передаётся.
- Генерация `python3 -m ingestion.generator.generate_dags --check` без расхождений после добавления ресурсов.
- [E2E](glossary.md#term-e2e):
  - Загрузка с нестандартными cores/memory/shuffle_partitions выполняется.
  - Параметры видны в Spark Master UI (`:8080`) и в команде spark-submit в логах задачи.
  - Полный `./test/test.sh` — `FAIL=0`.
- Схема секции `spark:` манифеста (ключ — тип — дефолт — назначение) обновлена в документации проекта по его правилам.

### Ускорить e2e-тестирование до 7 минут параллельными стеками

#### Задача Jira

[DATARCH-2253](https://jira.bcs.ru/browse/DATARCH-2253) — общая задача усиления
и оптимизации e2e-тестирования, также включает смену инкрементального контракта
и режимов загрузки.

#### Контекст

Полный [e2e](glossary.md#term-e2e)-прогон `./test/test.sh` поднимает один
изолированный стек `dlh-test` с обоими источниками (MSSQL `bank`, Oracle
`broker`) и исполняет сценарий `test/run_flow.py` для них последовательно.
Контрольный замер 2026-11-12 (exit 0, PASS=1373 FAIL=0): **18 мин 32 с**.
Подтверждённый профиль:

- хост-фазы (валидация, [unit](glossary.md#term-unit)-тесты, генерация DAG) — 3 с;
  подъём стека — 75 с; пост-проверки в scheduler — 56 с; гашение и очистка — 2 с;
- генерация данных дешёвая: [DagRun](glossary.md#term-dagrun) обновления
  источника ≈ 15 с (MSSQL) и 11 с (Oracle), включая пробуждение СУБД;
- один DAG-ран ≈ 25 с: две задачи загрузки, каждая — отдельное Spark-приложение
  (~12 с; преимущественно JVM-стартап, от объёма данных не зависит);
- в шагах 8 и 9 сценария DAG-и запускались последовательно
  (запуск → ожидание → следующий);
- проверки через Trino REST ≈ 2 с на запрос (пауза опроса 0.5 с на страницу),
  всего ~30 запросов;
- пик памяти одного стека ≈ 9 GiB (Spark-[drivers](glossary.md#term-driver)
  в scheduler ≈ 2.1; Oracle ≈ 2.0; Trino ≈ 1.4; MSSQL ≈ 1.3).

Целевой вид тестирования — два шага: сначала python-тесты отдельной командой,
затем параллельный e2e. Согласованное правило объёмов: одна тестовая операция
не затрагивает более 100 строк.

#### Проблема

Полный прогон занимает 18.5 минуты — слишком долго для итераций разработки.
По замеру время уходит не в данные, а в организацию прогона:

- проверки обоих источников исполняются последовательно в одном стеке;
- часть проверок — статика, не требующая стенда: структура манифестов,
  миграций и DAG-файлов проверяется дважды (на хосте и снова в контейнере);
- часть семантики дублируется на уровне Airflow, хотя уже покрыта
  python-проверками реестра [партий](glossary.md#term-batch)
  (`test/check_extraction.py`: гейт нулевой дельты, [retry](glossary.md#term-retry)/
  [CAS](glossary.md#term-cas) реестра).

Кейс воспроизведения: контрольный прогон 2026-11-12, профиль выше.

#### Предпочтительный путь решения

##### Параллельные стеки

`./test/test.sh` остаётся единственным режимом: сборка образов один раз,
затем два изолированных прогона параллельно и агрегация результатов.

- Стеки `dlh-test-bank` (MSSQL, `bank`) и `dlh-test-broker` (Oracle, `broker`).
  Суффиксы `dlh-test-<suffix>` и `SYDAFA_CONTAINER_PREFIX` уже поддерживаются
  скриптом; публикация портов в тестовом контуре отключена.
- Изолированные рабочие деревья `test/.workspace-bank` / `test/.workspace-broker`
  (сейчас один жёсткий путь `test/.workspace`); пути в
  `test/docker-compose.override.yaml` — через подстановку переменной.
- Фильтрация дерева по источнику: `conf/sydafa/sources.json`,
  `ingestion/conf/sources.yaml`, `airflow/plugins/migrations/`,
  `update_source_*.py` и сгенерированные `ingest__rdbms__<источник>__*.py`.
- Параметризация `E2E_SOURCE`: `test/run_flow.py` (кортежи DAG-ов и таблиц,
  проверка уникальности `process_id` 4 → 2), `test/check_extraction.py`
  (реестр одного источника; убрать ожидание clear-прогонов),
  `test/temporal_extraction.py` (аргумент источника; ветвления по диалектам
  уже есть).
- Диалектно-независимые проверки — по одному разу: `test/schema_evolution.py`
  и PostgresTests `test/unit/test_meta.py` в одном стеке; повторный снимок
  (атомарная перезапись) — в одном стеке.
- Режим `--verify` для отладки на поднятом стеке сохраняется с указанием стека.
- Предварительное требование — память Docker VM: двум стекам нужно ~18 ГБ;
  при доступной памяти ниже 20 ГБ скрипт отказывает с понятным сообщением
  до старта (сейчас лимит VM 15.6 ГБ, требуется повышение).

##### Состав сценария и лимит

- Лимит: оба стека завершаются не более чем за 7 минут — прогон при тёплом
  кэше образов и запущенном Docker; холодная сборка после изменения Dockerfile
  в лимит не входит.

  загрузка всех DAG-ов (шаг 8), совместный запуск инкремента и снимка
  (шаг 12), Clear полный и частичный (шаг 13). Замещение: гейт нулевой
  дельты и retry/CAS реестра уже проверяются пост-проверками реестра;
  удвоение полных срезов подтверждается повторными загрузками эволюции;

- Третья загрузка (дельта по `_batch_id`) — только main-пайплайн; первая

## Приоритет: можно отложить

### Изолировать Spark drivers через DockerOperator

#### Задача Jira

[DATARCH-2244](https://jira.bcs.ru/browse/DATARCH-2244)

#### Контекст

- Сейчас Spark Standalone 3.5.5 и Airflow LocalExecutor запускают `spark-submit` и [driver](glossary.md#term-driver) в контейнере `airflow-scheduler`, [executors](glossary.md#term-executor) — на `spark-worker`.
- `IngestFullOperator`, `IngestIncrementalOperator` и `IngestActSnapOperator` в `ingestion/operators/raw_rdbms.py` наследуют `SparkSubmitOperator`, `deploy_mode=client`.
- Spark Standalone 3.5.5 не поддерживает `cluster` deploy mode для Python-приложений. Смена одного параметра не изолирует текущий PySpark [driver](glossary.md#term-driver).
- Окружение описано в `docker-compose.yaml`, `conf/airflow/Dockerfile` и `conf/spark/Dockerfile`.

#### Проблема

[Drivers](glossary.md#term-driver) разных загрузок делят CPU и память с оркестратором. Airflow [pools](glossary.md#term-pool) ограничивают допуск, но не обеспечивают отдельные CPU/memory limits. Образ Airflow содержит Java, Spark и JDBC-зависимости.

Пример: разные DAG запускают несколько JVM рядом со scheduler. Убийство его контейнера завершает все размещённые в нём [drivers](glossary.md#term-driver).

Кейс размещения подтверждается конфигурацией. Нагрузочное измерение влияния параллельных загрузок на scheduler не проводилось. Остановка контейнера scheduler в диагностическом контуре завершила текущую загрузку и освободила [executors](glossary.md#term-executor).

#### Предпочтительный путь решения

Перевести все три оператора загрузки на `DockerOperator`: один запуск — отдельный контейнер со `spark-submit` и [driver](glossary.md#term-driver), Spark Standalone и `deploy_mode=client` сохраняются.

```text
Airflow → контейнер загрузки: spark-submit + driver
             → Spark Standalone: executors на worker
```

Это независимая задача изоляции ресурсов, не предварительное условие [остановки предыдущих Spark-приложений](#останавливать-предыдущие-spark-приложения-перед-записью-в-целевую-таблицу).

##### Образ и зависимости

- Адаптировать существующую Spark-сборку без необоснованного дублирования. Включить загрузчик, Spark/Python, Iceberg и MSSQL/Oracle JDBC drivers в образ без host bind mounts кода для каждого запуска.
- Проверить совместимость Java/Python и библиотек [driver](glossary.md#term-driver)/[executors](glossary.md#term-executor), включая совпадение minor-версий Python для Python workers.
- Передавать конфигурацию каталога и credentials при запуске, не запекать secrets в образ.
- Определить воспроизводимые build/tag и сборку образа до запуска основного и [e2e](glossary.md#term-e2e)-контуров.
- Добавить совместимый Docker provider. Убирать Spark/Java/SparkSubmit provider и JDBC JAR из Airflow только после проверки остальных потребителей, включая пользовательские DAG.
  - Сейчас JDBC JAR установлены в обоих образах, причины описаны в [README](../README.md#почему-jdbc-драйверы-установлены-в-обоих-образах).
  - В целевой схеме JAR должны быть в контейнере загрузки и на Spark workers, с согласованными версиями.
  - Проверить доступность JDBC-классов в обоих местах без JDBC JAR в Airflow, если проверка позволяет их удалить.

##### Контракт оператора

- Сохранить [runtime](glossary.md#term-runtime)-разрешение Connections/source.type, получение `process_id` и [watermark](glossary.md#term-watermark), [pool](glossary.md#term-pool)/pool_slots и фиксированное `max_active_runs=1` для всех генерируемых DAG.
- Сохранить маркировку и обязательную очистку старых Spark-приложений по target из [отдельной задачи](#останавливать-предыдущие-spark-приложения-перед-записью-в-целевую-таблицу), независимо от порядка реализации.
- [Retry](glossary.md#term-retry) задачи загрузки запускает новый контейнер, но сохраняет `process_id` и контракты [партии загрузки](glossary.md#term-batch).
- Собирать команду без небезопасной shell interpolation. Исключить пароли из команды, logs и rendered fields.
  - Environment не является защищённым secret store: значения доступны привилегированному Docker API.
- Ожидать завершения контейнера, передавать stdout/stderr в task logs, ненулевой exit code трактовать как failure.

##### Сеть и ресурсы

- Подключать контейнер к сети соответствующего compose-проекта, не смешивать основной и тестовый контуры.
- Обеспечить доступ к Spark master, источникам, Nessie/SILO и обратное подключение [executors](glossary.md#term-executor) к [driver](glossary.md#term-driver).
  - Настроить уникальные адреса запусков, `spark.driver.host`, bind address и отсутствие конфликтов портов параллельных [drivers](glossary.md#term-driver) разных targets.
- Определить конфигурацию образа, CPU/memory limits и Spark resources по версии DockerOperator.
  - Согласовать её с задачами [реестра источников](#разделить-реестр-источников-на-yaml-файлы-и-настроить-jdbc-параллелизм-по-источникам) и [ресурсов Spark](#управление-ресурсами-spark-на-уровне-отдельной-джобы), не дублировать значения.
  - Не расширять существующий `ingestion/conf/settings.yaml` настройками DockerOperator и не восстанавливать его после запланированного удаления. Контракт конфигурации запуска определить отдельно в спек-цикле.
- Согласовать JVM memory с лимитом контейнера, оставить запас для Python, JVM overhead и native memory.
- Разделять Airflow [slots](glossary.md#term-slot), Docker limits и Spark/JDBC parallelism.

##### Жизненный цикл и риски

- Определить удаление контейнеров после success/failure и доступность логов после удаления.
- При управляемой отмене останавливать контейнер и проверять освобождение [executors](glossary.md#term-executor).
- Задавать labels контура, target, DAG, задачи и запуска для адресного поиска оставшихся контейнеров. Определить восстановление управления и их очистку после аварии Airflow.
- Проверить temporary mounts DockerOperator: пути внутри Airflow не обязательно доступны Docker daemon host.
- Docker socket даёт широкие права на хост. Read-only mount не ограничивает операции API.
  - Доступ предоставлять только исполняющему задачи компоненту, без глобального небезопасного chmod и privileged-контейнеров.
- Контейнеризация не гарантирует продолжение загрузки после сбоя Airflow, автоматическое восстановление и отсутствие повторных записей. Она не создаёт строгую границу безопасности сама по себе.
- Production-топология и выбор иной платформы выполнения не входят в объём задачи.

##### Проверки и критерии готовности

- [Unit](glossary.md#term-unit): команда, credentials transport, Connections, [pool](glossary.md#term-pool)/[slots](glossary.md#term-slot), labels/сеть, limits, exit code и cancellation. Пароли отсутствуют в команде/logs/rendered fields.
- [E2E](glossary.md#term-e2e):
  - Демонстрационные загрузки и [актуальные снимки](glossary.md#term-snapshot) работают из отдельных контейнеров, [driver](glossary.md#term-driver) не выполняется в scheduler.
  - Проверены обратная связь worker с контейнером, параллельные загрузки разных targets, cleanup success/failure/cancel и изоляция контуров.
  - Сохранены очистка приложений по target, [retry](glossary.md#term-retry) со сквозным `process_id`, [incremental](glossary.md#term-increment), [snapshot](glossary.md#term-snapshot) и schema-evolution проверки.
- Генерация/`--check`, [unit-тесты](glossary.md#term-unit) и полный `./test/test.sh` проходят: `FAIL=0`, exit 0.
- При реализации обновлены README, архитектурная документация и граф. Недоступные аварийные проверки и ограничения контейнеризации указаны явно.

### Автоматически формировать теги DAG и исключать дубликаты

#### Задача Jira

[DATARCH-2259](https://jira.bcs.ru/browse/DATARCH-2259)

#### Контекст

`ingestion/generator/generate_dags.py::generate_dag_source` передаёт в DAG только `pipeline.tags`. Например, `ingestion/conf/pipelines/bank/main.yaml` вручную задаёт `ingestion`, `bank`, `main`.

`generate_snapshot_dag_source` уже добавляет `act_snap`, идентификатор источника и нормализованное имя target-таблицы, затем `entity.act_snap.tags`. Общий парсер tags в `ingestion/generator/manifest.py` проверяет список непустых строк, но не удаляет повторы.

#### Проблема

Ручное повторение имени [pipeline](glossary.md#term-pipeline) и источника в тегах создаёт лишние изменения YAML и риск рассинхронизации после копирования или переименования файла.

- Общего обязательного тега загрузки нет.
- Дополнительные теги могут дублировать автоматические или друг друга.

Пример: новый [pipeline](glossary.md#term-pipeline) без `tags` создаёт обычный DAG без тегов, хотя имя файла и источник известны генератору. [Snapshot](glossary.md#term-snapshot) с дополнительным тегом `act_snap` получает его повторно в генерируемом списке.

Вывод основан на статическом анализе генератора, парсера и манифеста.
Отображение и обработка повторов в работающем Airflow в рамках оформления задачи не проверялись.

#### Предпочтительный путь решения

Формировать теги при генерации DAG: автоматическая база плюс дополнительные теги соответствующей конфигурации, с детерминированным исключением дубликатов.

- Для обычного DAG автоматически добавлять имя исходного [pipeline](glossary.md#term-pipeline) YAML без расширения (`path.stem`), `source_id` и точный тег `ingest`, затем `pipeline.tags`.
  - Под именем файла понимать YAML-манифест, а не сгенерированный `.py`.
  - Для `bank/main.yaml` база — `main`, `bank`, `ingest`.
- Для [snapshot](glossary.md#term-snapshot) DAG добавлять ту же базу исходного [pipeline](glossary.md#term-pipeline), затем существующие служебные `act_snap` и нормализованное имя target-таблицы, затем `incremental.act_snap.tags`. Дополнительные теги основного DAG не наследовать: настройки двух DAG остаются независимыми.
- Удалять точные повторы строк, сохраняя порядок первого появления, в том числе совпадение имени файла с `source_id` и совпадения дополнительных тегов с автоматическими:
  - Не менять регистр и не нормализовать пользовательские теги неявно.
  - Сохранить проверку списка непустых строк.
  - При отсутствии `tags` использовать пустой список дополнений.
- Вынести сборку тегов в небольшую общую функцию генератора, без [runtime](glossary.md#term-runtime)-вычислений в Airflow и новых настроек. Не менять DAG/task IDs, расписания, Assets или обработку данных.
- Убрать из существующих YAML вручную перечисленные автоматические теги:
  - Текущий общий маркер `ingestion` заменить на `ingest`.
  - Прочие осмысленные дополнительные теги сохранить.
  - В документации явно отметить смену маркера для пользователей фильтров Airflow.
- Описать контракт автоматических и дополнительных тегов в документации генерации по правилам проекта. Учесть задачу шаблонизации DAG: правило сборки должно оставаться в Python-подготовке контекста, а не дублироваться в шаблонах.

Проверки и критерии готовности:

- [Unit](glossary.md#term-unit):
  - Автоматическая база без `tags`, дополнения, повторения внутри списка и пересечения с базой, одинаковые имя файла и источник.
  - Стабильный порядок повторной генерации.
- Обычный и [snapshot](glossary.md#term-snapshot) DAG получают общую базу:
  - [Snapshot](glossary.md#term-snapshot) сохраняет служебные теги и только собственные дополнения.
  - Одинаковые имена файлов у разных источников дают соответствующие source-теги.
  - Вложенный путь не попадает в тег имени файла.
- Сгенерированные DAG содержат ожидаемые уникальные теги и корректно импортируются:
  - Генерация/`--check` успешны после обновления артефактов.
  - В изолированном Airflow проверены теги и фильтрация по `ingest` без запуска загрузок ради проверки метаданных.
- Документация и примеры YAML согласованы:
  - Неприменимые и непроведённые проверки указаны явно.
  - Здесь добавляется только задача бэклога, реализация выполняется отдельно по спек-циклу.

### Разделить пулы Airflow для загрузок и служебных задач

#### Задача Jira

[DATARCH-2261](https://jira.bcs.ru/browse/DATARCH-2261)

#### Контекст

Airflow [pools](glossary.md#term-pool) ограничивают допуск задач, но не выделяют CPU и память.
Генератор `ingestion/generator/generate_dags.py` создаёт для каждой таблицы
цепочку `log_start → load → log_end → publish_asset`.

- `airflow.pool.name` и `airflow.pool.slots` применяются только к `load`.
- Остальным задачам генератор сейчас не назначает отдельный служебный [пул](glossary.md#term-pool).

#### Проблема

Нет единой автоматической политики, разделяющей тяжёлые задачи загрузки и короткие служебные задачи. Без явного назначения служебного [пула](glossary.md#term-pool) их допуск определяется общими настройками Airflow, а не правилами фреймворка.

Пример целевого поведения:

- [Сущность](glossary.md#term-entity) без настройки [пула](glossary.md#term-pool) отправляет `load` в общий [пул](glossary.md#term-pool) загрузок, а `log_start`, `log_end`, `publish_asset` — в отдельный служебный [пул](glossary.md#term-pool).
- Если для [сущности](glossary.md#term-entity) указан пользовательский [пул](glossary.md#term-pool), только `load` переходит в него.
- Служебные задачи остаются в служебном [пуле](glossary.md#term-pool).

[Runtime-кейс](glossary.md#term-runtime) в рамках оформления задачи не проверялся.

- Для проверки назначения достаточно сравнить поля `pool` и `pool_slots` задач сгенерированного DAG-а.
- Влияние заполнения [пулов](glossary.md#term-pool) на допуск нужно проверить в изолированном Airflow.

#### Предпочтительный путь решения

Настроить два штатных [пула](glossary.md#term-pool) фреймворка и автоматически назначать их в генераторе DAG-ов:

- Использовать `ingest_loads` как [пул](glossary.md#term-pool) по умолчанию для всех `load`, если [сущность](glossary.md#term-entity) не указала собственный `airflow.pool.name`.
- Создать отдельный [пул](glossary.md#term-pool) `ingest_service` для `log_start`, `log_end`, `publish_asset`:
  - Каждая такая задача занимает один [слот](glossary.md#term-slot).
  - Число [слотов](glossary.md#term-slot) обоих [пулов](glossary.md#term-pool) определить при реализации с учётом лимитов стенда, не выдавая [пул](glossary.md#term-pool) за изоляцию вычислительных ресурсов.
- Сохранить область действия явных настроек:
  - `airflow.pool.name` переопределяет только [пул](glossary.md#term-pool) `load`.
  - `airflow.pool.slots` задаёт только вес `load`.
  - Эти настройки не наследуются служебными задачами и не меняют их [пул](glossary.md#term-pool) или вес.
- Обеспечить идемпотентное создание штатных [пулов](glossary.md#term-pool) при инициализации Airflow в основном и тестовом контурах. Пользовательские [пулы](glossary.md#term-pool) не создавать автоматически: они должны существовать до запуска соответствующей загрузки.
- Сохранить зависимости задач и публикацию Asset только после успешного `log_end`. Назначение [пулов](glossary.md#term-pool) для `generate_process_id` и `activate_source` не входит в эту задачу.
- Не использовать разделение [пулов](glossary.md#term-pool) как блокировку одновременной записи одной target-таблицы: это отдельный механизм взаимного исключения.

Проверки и критерии готовности:

- [Unit](glossary.md#term-unit):
  - Без переопределения `load` получает `ingest_loads`, все три служебные задачи — `ingest_service`.
  - Пользовательский [пул](glossary.md#term-pool) и число [слотов](glossary.md#term-slot) изменяют только `load`.
- Проверены создание обоих штатных [пулов](glossary.md#term-pool) и повторная инициализация без ошибок.
  - Документация описывает назначение, размеры [пулов](glossary.md#term-pool) и границы переопределения.
- [E2E](glossary.md#term-e2e):
  - Обычная загрузка и загрузка с пользовательским [пулом](glossary.md#term-pool) проходят.
  - Фактическое назначение задач совпадает с конфигурацией.
  - При заполнении [пула](glossary.md#term-pool) загрузок готовые служебные задачи не блокируются именно этим [пулом](glossary.md#term-pool).
  - Общие лимиты [executor](glossary.md#term-executor)/scheduler по-прежнему могут ограничивать их исполнение.

### Убрать пароль JDBC-источника из аргументов spark-submit

#### Контекст

`IngestFullOperator.execute()`/`IngestIncrementalOperator.execute()` в пакете `ingestion/operators/` получают реквизиты источника из Airflow Connection и передаёт пароль через `--jdbc-password` в `application_args` для `SparkSubmitOperator`. Загрузчики `ingestion/spark/raw/rdbms/full/load_entity.py` и `ingestion/spark/raw/rdbms/incremental/load_entity.py` принимают этот аргумент и используют его при JDBC-подключениях. Реквизиты pg-meta передаются процессу загрузчика одной переменной окружения `INGESTION_META_DSN` со строкой подключения, а не аргументами CLI.

В закреплённом Spark provider 6.3.2 штатное логирование команды и сообщение об ошибке её выполнения используют маскирование аргументов с `password`/`secret`. Это не удаляет настоящий пароль из аргументов запущенного процесса. Источники: `conf/airflow/requirements.txt`, `execute()` операторов загрузки, `parse_args()` загрузчика и `SparkSubmitHook._mask_cmd()` провайдера.

#### Проблема

Пароль JDBC-источника присутствует в командной строке spark-submit и доступен субъектам с соответствующими правами просмотра аргументов процессов контейнера. Маскирование штатной строки команды в task logs не устраняет этот канал раскрытия секрета. Отдельный вывод приложения или библиотек также не защищается одним лишь маскированием команды.

Пример: при запуске загрузки с тестовым паролем в реальных аргументах процесса присутствует `--jdbc-password <тестовый_пароль>`, хотя штатная строка `Spark-Submit cmd` должна отображать замаскированное значение.

Кейс воспроизведения ([runtime-проверка](glossary.md#term-runtime) не выполнялась): в изолированном тестовом контуре запустить загрузку с искусственным секретом и проверить наличие этого значения в аргументах процесса, не выводя реальные реквизиты. Наличие открытого пароля в фактических логах работающего стенда не проверено и не утверждается.

#### Предпочтительный путь решения

Передавать пароль источника через окружение процесса загрузчика вместо CLI-аргумента:

- Согласованно изменить операторы загрузки и загрузчик: убрать `--jdbc-password` из команды и обязательных CLI-параметров, передавать секрет отдельной переменной окружения, читать её при запуске приложения. Отсутствие обязательного секрета должно приводить к понятной ошибке без вывода его значения.
- Сохранить получение реквизитов из Airflow Connections во время исполнения задачи:
  - Не записывать пароль в манифесты, сгенерированные DAG-и, XCom или Spark conf.
  - Передачу в JDBC выполнять из памяти приложения, без повторного формирования CLI с секретом.
- Не считать environment защищённым хранилищем: администратор контейнера или субъект с соответствующими правами может читать окружение. Решение устраняет присутствие секрета в аргументах процесса, но не заменяет управление доступом к среде выполнения.
- Выполнить эту задачу независимо от [перехода на DockerOperator](#изолировать-spark-drivers-через-dockeroperator):
  - Не расширять её до замены системы хранения секретов.
  - При последующей смене режима запуска сохранить отсутствие пароля в командной строке.

Проверки и критерии готовности:

- [Unit](glossary.md#term-unit):
  - В сформированных `application_args` нет аргумента пароля и его значения.
  - Секрет передаётся через окружение и корректно считывается загрузчиком.
  - Ошибка отсутствующей настройки не раскрывает секрет.
- В изолированном [e2e](glossary.md#term-e2e)-контуре успешная JDBC-загрузка сохранена, тестовый секрет отсутствует в аргументах процессов. Проверены штатный запуск и отказ подключения: пароль не появляется в task logs Airflow и диагностике загрузчика.
- Для проверок использовать искусственный секрет, не печатать реальные credentials. Область проверки логов и непроверенные каналы раскрытия указывать явно.
- Документация архитектуры обновлена по фактическому способу передачи реквизитов.
  - [Unit](glossary.md#term-unit) и полный изолированный [e2e](glossary.md#term-e2e) проходят.

### Выбирать JDBC-колонку по метрикам с управляемым повторным анализом

#### Задача Jira

[DATARCH-2260](https://jira.bcs.ru/browse/DATARCH-2260)

#### Контекст

Текущая эвристика в `ingestion/sources/rdbms/jdbc_partitioning.py` выбирает
целочисленный PK, затем целочисленный UNIQUE, затем дату, затем timestamp
через номер календарного дня. В ступенях 2–4 обязательна NOT NULL, а среди
кандидатов одной ступени выигрывает нормализованное имя. JDBC-чтение и
разведка MIN/MAX выполняются через `ingestion/spark/raw/rdbms/reader.py`.
Механика и разбор фактического лога находятся в разделе 7
`docs/architecture.md`.

Spark включает NULL в первую JDBC-партицию: это подтверждено предикатом
`"transaction_id" < 27502 or "transaction_id" is null` в предоставленном
логе запуска `manual__2026-11-09T15:54:58.294859+00:00` DAG-а
`ingest__rdbms__bank__main`. Это подтверждает механизм Spark, но не является
проверкой загрузки nullable-кандидата текущей эвристикой.

#### Проблема

Ограничение NOT NULL исключает колонки, по которым Spark способен прочитать
все строки. Выбор по имени не учитывает различимость значений и долю NULL
в окне чтения. При этом точный COUNT(DISTINCT) по нескольким кандидатам на
каждом запуске способен существенно увеличить нагрузку на источник.

Высокая различимость не гарантирует равномерность диапазонов, а большое
число NULL нагружает первую партицию. Нельзя считать предлагаемые метрики
гарантией ускорения или баланса потоков.

#### Предпочтительный путь решения

Проработать и реализовать единый выбор колонки по метрикам с управляемым
повторным анализом, не выполняя дорогое профилирование на каждой загрузке:

1. Снять обязательность NOT NULL при отборе кандидатов, сохранив обработку
   NULL первой партицией Spark и приоритет ступеней PK → UNIQUE → дата →
   timestamp-день. Проверить nullable UNIQUE отдельно для MSSQL и Oracle.
2. Если ступени PK и UNIQUE не дали результата и в очередной ступени есть
   несколько кандидатов, оценивать их в окне чтения по гранулярности
   `COUNT(DISTINCT col) / COUNT(col)` и максимизировать её. При равной
   гранулярности вычислять и максимизировать заполненность
   `COUNT(col) / COUNT(*)` только для претендентов на первое место.
   Обе метрики — до двух знаков после запятой. До реализации определить
   правила округления и сравнения, нулевых знаменателей и окончательного
   равенства. Для timestamp отдельно согласовать объект оценки: исходное
   значение или календарный день, по которому фактически строятся диапазоны.
3. В рамках проектирования проработать хранение выбранной колонки и
   результатов анализа в pg-meta: первичный анализ с последующим
   переиспользованием выбора — предложенное направление, не утверждённая
   схема хранения. Определить область ключа (источник, [сущность](glossary.md#term-entity), режим/окно),
   срок актуальности, условия и способ повторного запуска эвристики,
   инвалидирование при изменении схемы и поведение параллельных запусков.
   Конкретный период обновления сейчас не согласован.
4. Разделить переиспользуемый выбор колонки и текущие границы чтения:
   сохранённые MIN/MAX прошлого окна не должны ограничивать новое окно.
   Измерить стоимость профилирования на MSSQL и Oracle, зафиксировать
   политику отказов анализа и логировать причину выбора/переиспользования
   и актуальность статистики.

Проверки и критерии готовности:

- [Unit](glossary.md#term-unit): nullable-кандидаты, порядок ступеней, сравнение округлённых метрик,
  заполненность только при равенстве, пустое окно и полностью NULL-колонки.
- Интеграционные проверки pg-meta: сохранение выбора, переиспользование,
  повторный анализ, изменение схемы и конкурирующие обращения по
  согласованному контракту.
- [E2E](glossary.md#term-e2e) через реальные MSSQL/Oracle JDBC:
  - NULL не теряются и не дублируются.
  - Окно сохраняется, сравниваются несколько кандидатов.
  - Повторный запуск не выполняет дорогое профилирование до наступления условия обновления.
- Документированы стоимость и ограничения метрик.
  - Полный изолированный `./test/test.sh` проходит.
  - Новая эвристика и статистика сейчас не реализуются.
