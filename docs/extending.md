## 1. Выбор вида изменения

| Цель | Что менять | Текущее состояние |
|---|---|---|
| Добавить таблицу уже подключённого источника | YAML-конфигурацию загрузки | Поддерживается существующим генератором |
| Подключить другую СУБД через JDBC | Диалект, реестр, драйвер и окружение | Зарегистрированы только MSSQL и Oracle |
| Читать данные иначе, например из Kafka | Контракт источника, конфигурацию, оркестрацию и исполнитель чтения | Генератор и операторы принимают только `rdbms` |
| Построить следующий слой | Каталог слоя, преобразования и оркестрацию | Реализован только [raw](glossary.md#term-raw) |

Добавление таблицы не требует нового диалекта. Правила YAML описаны в
[разделе о манифестах](architecture.md#2-манифесты-и-генерация-dag-ов).
Подключение СУБД к sydafa и поддержка её чтения загрузчиком — разные задачи.

## 2. Подключение новой JDBC-СУБД

Диалект описывает различия SQL и JDBC конкретной СУБД.
Исходный контракт — [`RdbmsDialect`](../ingestion/sources/rdbms/contracts.py).
Рабочие примеры — [`MssqlDialect`](../ingestion/sources/rdbms/dialects/mssql.py)
и [`OracleDialect`](../ingestion/sources/rdbms/dialects/oracle.py).

### Контракт диалекта

Создайте модуль `ingestion/sources/rdbms/dialects/<dbms_name>.py`
с наследником `RdbmsDialect`. Не копируйте готовый адаптер другой СУБД
без проверки типов, экранирования и метаданных.

| Часть контракта | Что определить или проверить |
|---|---|
| `conn_type_aliases`, `url_prefixes` | Типы Airflow Connection и префиксы JDBC URL, по которым выбирается диалект |
| `default_port`, `driver_class` | Порт по умолчанию и класс установленного JDBC-драйвера |
| `build_jdbc_url(ConnectionSpec)` | Формирование URL из параметров подключения |
| `quote_identifier`, `render_table` | Экранирование имён, регистр и адресация `schema.table`. Базовый `render_table` соединяет экранированные части точкой |
| `position_kind` | Отображение JDBC type name, precision и scale в [канонический тип позиции](glossary.md#term-canonical). Неподдерживаемые типы должны отклоняться |
| `_typed_literal`, `position_literal` | SQL-литералы границ чтения. Базовый метод обрабатывает NULL и целые числа, остальные семейства передаёт `_typed_literal` |
| `position_expression` | Выражение чтения [позиции инкремента](glossary.md#term-position) без потери точности. Базовый метод возвращает колонку без преобразования |
| `metadata_candidates` | Адреса поиска таблицы в JDBC-метаданных: catalog, schema, table. Базовое поведение проверяет исходный и верхний регистр некавыченных имён |
| `column_projection` | Преобразование специальных типов источника в читаемый Spark формат. По умолчанию преобразования нет |
| `day_expression` | Числовое представление календарного дня для разбиения timestamp-чтения |
| `reader_options` | Опции JDBC reader. Базовое значение — `preferTimestampNTZ=true` |

Обратите внимание:

- `integer_kind()` нормализует имена типов, но не переводит названия вроде
  `INT64` в `bigint`. Соответствие типов новой СУБД нужно задавать явно.
- `fractional_kind()` принимает точность и верхний предел, возвращает проверенное число.
  Он не создаёт строку типа `timestamp_local(p)`.
- `day_expression()` должен задавать пригодный для диапазонного разбиения номер дня.
  Не заменяйте его календарной записью вида `YYYYMMDD`: расстояния между такими числами
  не равны числу дней на границах месяцев.
- Совместимость обычных колонок и точность [позиции инкремента](glossary.md#term-position)
  проверяются отдельно. Spark ограничивает точность timestamp в данных микросекундами.

Диалект формирует выражения, но сам не читает DataFrame и не записывает Iceberg.
JDBC-соединениями и построением совместимой проекции управляет
[`jdbc.py`](../ingestion/sources/rdbms/jdbc.py).
Например, `column_projection()` может вернуть выражение для специального типа,
а общий JDBC-слой применит его, сохранив имя колонки.

### Регистрация и окружение

1. Импортируйте класс и добавьте экземпляр в `_DIALECTS`
   файла [`registry.py`](../ingestion/sources/rdbms/registry.py).
   `by_conn_type()` выбирает его в Airflow, `by_jdbc_url()` — по URL.
   Автоматического поиска модулей нет.
2. Добавьте JDBC JAR в окружение Airflow и Spark. Сейчас драйверы задаются
   в [`conf/airflow/Dockerfile`](../conf/airflow/Dockerfile)
   и [`conf/spark/Dockerfile`](../conf/spark/Dockerfile).
3. Подготовьте Airflow Connection. `ConnectionSpec` содержит host, port,
   database, user и password. Установка JDBC JAR сама по себе не регистрирует
   новый тип Connection в Airflow: проверьте необходимость provider и способ создания подключения.
4. Добавьте источник в `ingestion/conf/sources.yaml`, а его таблицы —
   в `ingestion/conf/pipelines/`. Категория JDBC-источника остаётся `type: rdbms`.
   Новый `conn_type` не является новым `type` источника.
5. Проверьте активацию источника. Сгенерированные DAG-и сейчас используют sydafa.
   Для внешней СУБД нельзя считать этот шаг автоматически подходящим:
   способ активации нужно согласовать отдельно.

### Проверки совместимости

Проверки разрабатываются и запускаются по
[скиллу e2e-testing](../.agents/skills/e2e-testing/SKILL.md).
Существующие точки проверки:

- `test/unit/test_dialects.py` — URL, имена, типы и точные SQL-выражения.
- `test/unit/test_jdbc.py` — адресация JDBC-метаданных и совместимые проекции.
- `test/unit/test_jdbc_partitioning.py` — выбор колонки и границы параллельного чтения.
- Изолированный тестовый контур — реальное чтение и запись из новой СУБД.

Для новой СУБД нужно проверить:

- [полные срезы](glossary.md#term-full), пустую таблицу и изменения схемы;
- поддерживаемые [позиции инкремента](glossary.md#term-position), NULL и несовпадение типа;
- точность времени, часовые пояса и границы [окна](glossary.md#term-window);
- [lookback](glossary.md#term-lookback), повтор незавершённой и уже успешной [партии](glossary.md#term-batch);
- параллельное чтение и переход к одному потоку при отсутствии подходящей колонки;
- вспомогательную [таблицу-снимок](glossary.md#term-snapshot), включая пустой результат.

Одних unit-тестов SQL-строк недостаточно для заявления о поддержке СУБД.
ClickHouse, Greenplum и Teradata сейчас не зарегистрированы и не становятся
поддерживаемыми только после добавления записи в YAML.

## 3. Новый тип источника

Для Kafka или файлового источника недостаточно добавить `RdbmsDialect`:
это другой способ чтения и другой контракт восстановления.

Текущие ограничения находятся в нескольких местах:

- [`manifest.py`](../ingestion/generator/manifest.py), функция `load_sources()`,
  принимает только `type: rdbms`. Для `kafka` есть явная ошибка «not implemented yet».
- [`operators.py`](../ingestion/operators.py), `IngestAppendOperator`
  и `IngestActSnapOperator`, при выполнении также проверяют `source_type == "rdbms"`.
- [`generate_dags.py`](../ingestion/generator/generate_dags.py)
  создаёт задачи с JDBC-ориентированными операторами и активацией sydafa.
- Приложения в `ingestion/spark/raw/rdbms/` читают JDBC.
  Подсистемы Kafka в текущей реализации нет.

Порядок проектирования:

1. Определите способ чтения: ограниченные выборки или непрерывный поток.
   Ни один из вариантов пока не принят как контракт Kafka.
2. Определите идентичность [партии](glossary.md#term-batch), границы чтения,
   хранение прогресса и поведение повторов. Не переносите значение
   [watermark](glossary.md#term-watermark) реляционной колонки на offsets без отдельного решения.
3. Решите, применимы ли существующий реестр pg-meta, события Asset,
   активация источника и вспомогательные [таблицы-снимки](glossary.md#term-snapshot).
4. Спроектируйте конфигурацию, выбор оператора и отдельный исполнитель чтения.
   Новую логику не помещайте в JDBC-диалект.
5. Реализуйте согласованные изменения валидатора, генератора, операторов,
   окружения и изолированных проверок. Одного снятия запрета в `load_sources()` недостаточно.

Будущие пути модулей и YAML-ключи определяются планом изменения.
Не создавайте пустые каталоги и не представляйте эскиз конфигурации как работающий API.

## 4. Новый слой данных

[ODS](glossary.md#term-ods), [DDS](glossary.md#term-dds)
и [DMA](glossary.md#term-dma) пока не реализованы.
Текущий генератор создаёт только загрузки [raw](glossary.md#term-raw)
и вспомогательные [таблицы-снимки](glossary.md#term-snapshot).
Поддерживаемого YAML-контракта для следующих слоёв нет.

Перед реализацией определите:

- отдельный каталог и размещение данных нового слоя в Nessie, Spark и Trino;
- входные таблицы, бизнес-ключи и порядок версий источника;
- правила обработки удалений и повторных записей [raw](glossary.md#term-raw);
- [идемпотентность](glossary.md#term-idempotency) преобразований и восстановление после ошибки;
- оркестрацию: расписание или зависимость от событий Asset;
- конфигурацию и способ создания DAG-ов.

Не фиксируйте заранее, кто пишет DAG-и и будут ли они генерироваться:
это ещё не реализованное решение. Не помещайте будущую конфигурацию
в `ingestion/conf/pipelines/` до изменения её контракта — существующий генератор
рассматривает эти YAML-файлы как загрузки источников в [raw](glossary.md#term-raw).

Для [ODS](glossary.md#term-ods) предполагается устранение повторов и построение
состояния записей. Одного `__load_dttm` недостаточно, чтобы определить порядок
версий источника при повторных загрузках.
Если выбран `MERGE INTO`, используйте соответствующую операцию Iceberg SQL:
`DataFrameWriter.mode("merge")` не является её заменой.

Добавление следующего слоя не должно менять смысл уже загруженного
[raw](glossary.md#term-raw) или добавлять бизнес-преобразования в его reader и writer.
Существующий [`ingestion/iceberg.py`](../ingestion/iceberg.py) описывает DDL
таблиц [raw](glossary.md#term-raw), а не универсальную конфигурацию всех слоёв.

## 5. Порядок разработки

1. Оформите функциональное изменение по спек-циклу из
   [AGENTS.md](../AGENTS.md#спецификации-изменений-github-spec-kit).
2. По графу проверьте потребителей изменяемого контракта, затем сверьтесь с исходниками.
3. Разделите реализованное и планируемое. Не выдавайте направление развития за действующий интерфейс.
4. Подготовьте проверки по скиллу e2e-testing. Не меняйте основной стенд ради тестового прогона.
5. Обновите архитектуру по контрактам, README по составу и эксплуатации,
   это руководство по точкам расширения.
6. Актуализируйте граф и оформите PR по правилам репозитория.

Устройство существующей загрузки и её гарантии не дублируются здесь:
они описаны в [архитектуре](architecture.md).
