## Подход

Отдельный `ingestion/spark/guard.py` содержит Spark-механику: строгую проверку JSON, однократный kill исходных IDs, monotonic-бюджет и проверку completedapps. Модуль получает адрес master и target, не зависит от Airflow. Каждый execute трёх операторов вызывает барьер до подготовки submit. Результат — список очищенных IDs для диагностики. Ошибка исключает submit.

Для HTTP используем стандартную библиотеку Python без новой зависимости. Redirect не является подтверждением kill. Запросы не повторяются автоматически. Адрес берётся из HTTP Connection, без extra и fallback. Guard получает только HTTP Connection. Разрешение submit Connection остаётся ответственностью SparkSubmitOperator, без предварительной проверки в guard.

Получение Connections, построение адреса из schema/host/port и диагностические callbacks остаются в `raw_rdbms.py`. Собственной проверки типов, схем, портов и реквизитов Connections нет: их корректное создание — ответственность конфигурации и её тестов. Ошибка получения Connection прерывает execute до submit.

По уточнению пользователя HTTP-ответ читается целиком через `response.read()`, без порционного чтения и произвольного лимита размера. Проверка бюджета после чтения запрещает submit при превышении, но не прерывает медленно поступающий ответ строго по общему deadline.

Callbacks уровня модуля добавляются списками к существующим callbacks. FAILED сохраняется. Диагностика не отправляет HTTP-запросов и не выводит текст исключения, потенциально содержащий credentials: только тип ошибки, target, ID и результат guard.

## Технический контекст

- Python 3.11+, Airflow SDK BaseHook, существующий SparkSubmitOperator, Spark Standalone 3.5.5.
- Новых хранилищ, зависимостей и внешних API нет. Состояние guard живёт в одном execute.
- Connections: `spark_main_submit` и `spark_main_master_http`, один логический кластер.
- Формат target задаётся генератором и загрузчиком. Guard не валидирует и не нормализует имя, только сравнивает его дословно.
- Общий бюджет 120 с. Запрос до 5 с и остатка бюджета. Ожидание 2 с и остаток бюджета.
- Состояния активного приложения берутся из Spark Standalone: WAITING/RUNNING. Подтверждённое завершение: KILLED/FINISHED. Остальные состояния целевого приложения запрещают submit.

## Проверка конституции

- Граф запрошен перед исходниками. Широкого анализа нет, неполный вывод графа не трактуется как полный.
- Unit и e2e обязательны. Полный прогон — критерий приёмки, а не обещание результата.
- Python без комментариев. Документация и артефакты на русском.
- Отдельная ветка подтверждённого GitHub login. Коммиты и публикация только с разрешения, мерж только пользователем.
- Устаревшие положения конституции о графе и ссылках в demo конфликтуют с актуальными AGENTS.md. Применяются актуальные инструкции. Конституция не меняется в функциональной задаче.
- После проектирования новых нарушений нет. Отдельная cleanup-задача, worker registry и распределённая блокировка не вводятся.

## Структура и проверка

- `ingestion/spark/guard.py`: независимая от Airflow Spark-механика.
- `raw_rdbms.py`: получение Connections, три вызова guard, диагностика и композиция callbacks.
- Три Spark entrypoints: дословное appName.
- Генератор: default_args обоих шаблонов, регенерация артефактов.
- Compose и проверки Connections: два новых ID, отсутствие старого fallback.
- Unit: переходы состояний, некорректные ответы, HTTP-ошибки, бюджет, вызов каждого execute, callbacks, настройки DAG и коллизии.
- E2E: реальные операторы и оставшееся Spark-приложение, отказ guard без submit, сохранение incremental-контрактов. Сценарии подключаются через `test/test.sh` и `test/run_flow.py`.
- Документация: архитектура, Connections и миграция в README, синхронизация существующей задачи бэклога.
