## Пользовательские сценарии

### US1 — загрузка без обязательного журнала (P1)

Оператор видит начало и результат загрузки в журнале без отдельных задач журналирования.
При недоступности журнала загрузка и публикация результата продолжаются.

Проверка: успешная загрузка публикует результат как при доступном журнале,
так и при ошибке записи события. Ошибка записи видна в стандартном логе без секретов.

### US2 — повторные попытки (P1)

Каждая попытка отмечает начало. Успешная попытка отмечает завершение,
окончательная неудача — падение. Пользовательские и диагностические обработчики сохраняются.

Проверка: повторный вызов начала создаёт повторный START с тем же `process_id`.
Неудачная промежуточная попытка не создаёт END.

## Требования

- **FR-001**: убрать отдельные задачи `log_start` и `log_end` для full, incremental и act_snap.
- **FR-002**: записывать START каждой попытки, END при успехе и FAILED при окончательной неудаче.
- **FR-003**: ошибка журналирования не меняет результат загрузки и не препятствует публикации Asset.
- **FR-004**: сохранять существующие пользовательские и диагностические обработчики.
- **FR-005**: не менять выделение `process_id`, инкрементальный реестр и watermark.
- **FR-006**: отсутствие `process_id` не создаёт событие с некорректным идентификатором.

## Критерии успеха

- **SC-001**: на каждую сущность на две задачи меньше, публикация следует за загрузкой.
- **SC-002**: проверки всех трёх режимов подтверждают FR-001—FR-006.
- **SC-003**: сквозной сценарий проверяет новую последовательность и события при доступном журнале.

## Границы

DDL журнала не меняется. Доставка событий не гарантирована при аварийном завершении процесса
и ручной смене состояния задачи. Номер попытки в журнал не добавляется.
Журнал DAG и выделение идентификатора остаются без изменений.
