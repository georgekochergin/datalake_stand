# Конституция проекта datalake_stand

## Базовые принципы

### I. Граф кодовой базы прежде чтения файлов
Любой анализ кода — поиск, навигация по зависимостям, оценка влияния изменений —
начинается с запросов к графу кодовой базы (`graphify-out/graph.json`):
`graphify query`, `graphify explain`, `graphify path`, `graphify affected`.
Сплошное чтение файлов допускается только когда ответа из графа недостаточно.

### II. Изменения подтверждаются тестами
Любой новый или изменённый функционал пайплайнов, источников и оркестрации
обязан сопровождаться соответствующими проверками в сценарии e2e-тестирования
(`test/run_flow.py`, `test/test.sh`). Разработка, изменение и диагностика
тестов ведутся по скиллу `e2e-testing`; тестовый контур `dlh-test` изолирован
от живого стенда.

### III. Чистый Python без комментариев
В коде на Python запрещены комментарии (строки с `#` и inline-комментарии,
кроме шебанга `#!/usr/bin/env python3` первой строки исполняемых скриптов).
Допустимы исключительно структурированные docstring модулей, классов и функций.

### IV. Дисциплина Git: ветка → Pull Request → мерж пользователем
Рабочие ветки создаются с префиксом `<github-login>/`. Коммиты в `main`
запрещены; изменения попадают в `main` только через Pull Request.
Pull Request никогда не мержится исполнителем самостоятельно — мерж выполняет
только пользователь. Описание PR обязательно детальное и структурированное:
контекст и решаемая проблема; изменения по компонентам; изменения интеграций,
окружения и конфигов; свидетельства тестирования (включая явно указанные
пропущенные и неприменимые проверки).

### V. Перестроение графа после каждого коммита
После каждого коммита принимается решение по изменённым файлам: ничего не
делать (менялись только документация и служебные файлы) / локальное
`graphify update .` без токенов (типовые правки кода) / перестроение с LLM
для семантически значимых изменений. Обновлённый `graphify-out/graph.json`
коммитится один раз — финальным коммитом PR.

### VI. Документация на русском языке
Вся документация проекта пишется на русском без кальки с английского.
Единственный проектный README.md лежит в корне и содержит пять разделов;
тематические руководства — в `docs/`. В документации фиксируются только
принятые решения, без истории обсуждений и отклонённых альтернатив.

## Стандарты артефактов спек-цикла

Все артефакты спек-цикла — конституция, `spec.md`, `plan.md`, `tasks.md`,
чек-листы, аналитические отчёты — пишутся на русском языке. Технические
идентификаторы (имена файлов, команд, каталогов, коды ошибок) остаются
в оригинальном написании. Спецификация описывает «что» и «зачем» для
заказчика результата, без деталей реализации.

## Процесс разработки

Спек-цикл: constitution → specify → clarify (при необходимости) → plan →
tasks → analyze (при необходимости) → implement → converge. Спек-цикл не
отменяет общие правила репозитория: анализ кода — через граф; изменения
функциональности сопровождаются e2e-проверками; финализация — по скиллу
`pull-request`. Артефакты спеков в `specs/` версонируются в git наравне
с кодом.

Спек-цикл доступен в обоих агентах команды — opencode (команды
`/speckit.<имя>`) и zcode (скиллы `$speckit-<имя>`); состояние цикла — файлы
репозитория, поэтому работу можно переключать между агентами без
дополнительных действий.

## Управление

Конституция первична относительно локальных практик: при противоречии
побеждают конституция и `AGENTS.md`. Изменения конституции оформляются
отдельным Pull Request'ом с обоснованием каждой поправки, обновлением
версии и даты ниже.
